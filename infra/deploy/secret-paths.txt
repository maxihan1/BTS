# 파이프라인(= 저장소 코드)이 **읽으면 안 되는** 것.
#
# `protected-paths.txt` 와 무엇이 다른가. 그쪽은 「배포가 지우면 안 되는 것」이고
# 이쪽은 「젠킨스가 읽으면 안 되는 것」이다. 겹치지만 같지 않다 —
#   backups/         지워지면 안 되지만 **배포가 거기에 DB 덤프를 쓴다.** 읽기·쓰기가 필요하다.
#   infra/prod/.env  지워지면 안 되지만 **배포가 compose 에 넘겨 읽는다.** 읽기가 필요하다.
#   젠킨스 자격증명   지워져도 안 되고 읽혀서도 안 된다. 이 목록은 그것만 남는다.
#
# 2026-09-11 실측. 둘을 한 목록으로 다뤘더니 `bootstrap.sh` 의 chown 복구가 backups 까지
# root 로 잠갔고, 배포 5단계 DB 덤프가 쓰기 불가로 죽을 상태가 됐다. 의미가 다른 둘을
# 한 목록에 누른 것이 원인이다.
#
# ★★2026-09-14 실측(빌드 #55). 같은 원인이 한 겹 더 있었다 — `infra/prod/.env` 다.
#   이 목록에 있어 root 600 으로 잠겼는데 `bts-deploy.sh` 의
#   `docker compose --env-file infra/prod/.env` 가 바로 그 파일을 읽는다.
#   rsync 와 DB 덤프까지 다 끝난 뒤 마지막 한 줄에서 `permission denied` 로 죽었다.
#
#   그래서 뺐다. 근거는 `docs/runbooks/jenkins.md` §4-7 에 이미 있다 — `docker.sock`
#   마운트가 젠킨스에 **이미 호스트-root 등가 권한**을 준다. 운영 `.env` 를 uid 1000 이
#   읽게 해도 실질 공격면은 늘지 않는다. 반대로 이 목록에 두면 배포가 성립하지 않는다.
#
#   ★젠킨스 **자신의** 자격증명(`infra/jenkins/.env` · `.deploy-key`)은 그대로 둔다.
#     저장소 코드가 그것을 읽을 이유가 없고, 읽히면 CI 를 통째로 탈취당한다.
#
# ★이 목록은 `protected-paths.txt` 의 **부분집합**이어야 한다. 읽히면 안 되는 것은
#   당연히 지워져도 안 된다. 계약. scripts/workflow/deploy-protected-paths-single-source.test.ts
#
# 형식. 한 줄에 경로 하나. `/opt/bts` 기준 상대경로. `#` 주석과 빈 줄은 무시된다.

infra/jenkins/.env          # 젠킨스 관리자 자격증명
infra/jenkins/.deploy-key   # GitHub 배포키(개인키)
infra/secrets               # JWT 서명키 등
