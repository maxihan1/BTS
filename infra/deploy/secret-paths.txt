# 배포 대상에서 **정해진 소유자만 읽어야 하는** 것.
#
# `protected-paths.txt` 와 무엇이 다른가. 그쪽은 「배포가 지우면 안 되는 것」이고
# 이쪽은 「정해진 소유자 말고는 읽으면 안 되는 것」이다. 겹치지만 같지 않다 —
#   backups/         지워지면 안 되지만 **배포가 거기에 DB 덤프를 쓴다.** 읽기·쓰기가 필요하다.
#   infra/prod/.env  지워지면 안 되지만 **배포가 compose 에 넘겨 읽는다.** 읽기가 필요하다.
#
# 2026-09-11 실측. 둘을 한 목록으로 다뤘더니 chown 복구가 backups 까지
# root 로 잠갔고, 배포 5단계 DB 덤프가 쓰기 불가로 죽을 상태가 됐다. 의미가 다른 둘을
# 한 목록에 누른 것이 원인이다.
#
# ★★2026-09-14 실측(빌드 #55). 같은 원인이 한 겹 더 있었다 — `infra/prod/.env` 다.
#   이 목록에 있어 root 600 으로 잠겼는데 `bts-deploy.sh` 의
#   `docker compose --env-file infra/prod/.env` 가 바로 그 파일을 읽는다.
#   rsync 와 DB 덤프까지 다 끝난 뒤 마지막 한 줄에서 `permission denied` 로 죽었다.
#   그래서 뺐다 — 이 목록에 두면 배포가 성립하지 않는다.
#
# ★이 목록은 `protected-paths.txt` 의 **부분집합**이어야 한다. 읽히면 안 되는 것은
#   당연히 지워져도 안 된다. 계약. scripts/workflow/deploy-protected-paths-single-source.test.ts
#
# ★★2026-09-14 실측. 배포는 성공했는데 **운영 백엔드가 크래시루프**에 빠졌다.
#   이 목록을 `chown -R root:root` 로 일괄 되돌렸는데, `infra/secrets`
#   안의 JWT 서명키를 **백엔드 컨테이너(uid 999)가 읽어야 했다.**
#
#     PEM 파일 파싱 실패: /secrets/bts-jwt.pem ... (Permission denied) (EC-19)
#
#   목록의 뜻은 「아무나 읽으면 안 된다」인데 구현은 「root 말고 아무도 못 읽는다」
#   였다. 의도보다 범위가 넓었다. 잠긴 시각은 9/11 이고 증상은 9/14 에
#   나왔다 — 이미 떠 있던 백엔드가 기동 때 읽은 키를 메모리에 들고 있었기 때문이다.
#   사흘 동안 「운영 정상」이면서 **재시작하면 죽는** 상태였다.
#
#   그래서 목록이 「무엇을」에 더해 **「누구에게」**까지 말한다. 소유자를 정확히 지정하면
#   백엔드(999)만 읽는다 — 원래 의도가 그제서야 구현된다.
#
# 형식. 한 줄에 `<경로> <소유자 uid>`. `/opt/bts` 기준 상대경로. `#` 주석과 빈 줄은 무시된다.
#   소유자는 **숫자**여야 한다. 계정 이름은 호스트마다 다른 uid 로 풀린다.

infra/secrets        999   # 백엔드 컨테이너(uid 999)가 JWT 서명키를 읽는다. Dockerfile.backend 와 대조된다
