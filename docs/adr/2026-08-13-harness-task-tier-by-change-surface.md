# ADR — 작업 절차 강도를 「변경 파일 수」가 아니라 「변경 표면」으로 정한다

> 날짜. 2026-08-13
> 상태. **채택 (Active)**
> 영역. 개발 하네스 (Claude Code 워크플로우) — 제품 도메인 아님
> 관련 FR. 없음 (제품 요구사항이 아니라 개발 절차 결정이다)
> 관련 문서. `.claude/MIGRATION.md` · `docs/rules/behavior-rules.md` · `CLAUDE.md` §작업 티어
> 대체 관계. **대체하는 기존 ADR 없음.** `docs/adr/` 34건을 전수 확인한 결과 전부 제품 도메인 결정이고, 하네스 결정을 ADR 로 남기는 것은 이번이 처음이다

## 맥락

이 저장소의 작업 절차는 **모든 작업에 같은 강도**로 걸려 있었다. CSS 한 줄을 고치는 일과
데이터베이스 마이그레이션을 추가하는 일이 똑같이 스펙 문서 · 계획서 · 계획 승인 게이트 · 독립 리뷰 2종을 밟았다.

2026-08-13 실측이 그 비용을 숫자로 보여 줬다.

- 머지된 PR 60건(#312~#378)을 재판정한 결과, **기존의 「변경 파일 5개」 기준으로는 83%가 무거운 절차(T2 이상)** 로 분류된다.
- 작업 1건당 워크플로우 스킬 호출은 가중 평균 **7.70회**였다.
- 그런데 그 무거운 절차가 걸린 작업 중 상당수는 문서 수정이나 프론트 화면 조정이었다.

**「변경 파일 수」가 기준으로 부적합한 이유는 명확하다.** 파일 수는 **위험과 상관이 약하다.**
번역 문구 파일 8개를 고치는 것은 파일 수로는 크지만 위험은 거의 0 이고,
권한 검사 파일 1개를 고치는 것은 파일 수로는 최소인데 위험은 최대다.
게다가 **착수 시점에는 변경 파일 수를 알 수 없다** — 다 고치고 나야 세어진다. 판정 기준이 판정 시점에 존재하지 않았다.

## 결정

### D1. 절차 강도는 **변경 경로가 속한 표면**으로 정한다 — T0 / T1 / T2 / T3

「표면(surface)」이란 위험 성격이 같은 경로들의 묶음이다. 예를 들어 「마이그레이션」 표면은
`backend/modules/*/src/main/resources/db/migration/**/*.sql`, 「문서」 표면은 `docs/**` 와 루트의 `*.md` 다.

| 티어 | 대표 표면 | 절차 |
|---|---|---|
| **T0** | 문서 · 스타일/문구 | 계획서 없음 · 린트와 타입 검사 · 독립 리뷰 1종 · 머지 전 승인만 |
| **T1** | 프론트 소스 · 하네스 · 테스트 | 계획서 없음 · 재현 테스트 1개 먼저 · 리뷰 1종 · 머지 전 승인만 |
| **T2** | 보안 · 공개 API · 백엔드 본체 · 의존성 · 가드/CI | 계획서 1파일 → 승인 · 정식 TDD · 리뷰 2종 · 승인 2회 |
| **T3** | 마이그레이션 · 공용 커널 · 모듈 구조 | 위 + 설계 문서(ADR) · 마이그레이션 검증 · 리뷰 3종 |

같은 PR 이 여러 표면을 건드리면 **가장 높은 티어를 따른다.** 분류되지 않은 경로는 T1 로 두되
경로를 그대로 게이트 요약에 실어 사람이 본다 — 조용히 삼키지 않는다.

**근거.**
- 표면은 **착수 시점에 알 수 있다.** 「어디를 고칠 것인가」는 첫 문장부터 정해진다.
- 표면은 **위험과 직결**된다. 권한 파일 1줄이 T2 로 뜨고, 문구 파일 8개가 T0 로 뜬다 — 이것이 의도한 방향이다.
- 재판정 결과 **가벼운 작업(T0+T1)이 17% → 50%** 로 올라간다. 호출 수는 7.70 → **5.00(−35%)** 이 된다.

### D2. 표면 목록의 정본은 **코드 파일 한 곳**이다 — `scripts/workflow/surfaces.ts`

경로 패턴(글로브)은 `SURFACES` 라는 상수 15키에만 적는다.
판정 함수도, 검사 테스트도, CI 도 그 상수를 **import** 할 뿐 패턴을 다시 쓰지 않는다.

**근거.** 이 저장소가 반복해서 겪은 사고 양식이 **「두 목록이 서로를 검사하지 않는다」**이다.
같아야 하는 두 목록을 두 파일에 각각 적어 두면 한쪽만 고쳐진 채 몇 달이 지나간다.
글로브는 특히 위험하다 — 문자열이라 오타가 나도 「매칭 0건」으로 조용히 통과하기 때문이다.

문서에도 표면 이름을 전수로 적지 않는다. 사람이 읽는 표는 `docs/rules/behavior-rules.md` 한 곳에만 두고,
**그 표와 코드 상수의 차집합이 0 인지를 검증 스크립트가 대조**한다. 대조 하한도 함께 둔다 —
파서가 고장 나서 0건을 읽으면 차집합이 자동으로 0 이 되어 통과해 버리기 때문이다.

### D3. 선언한 티어를 **믿지 않는다** — 자동 승격도 하지 않는다

계획서 머리에 `티어: T2` 같은 선언을 적지만, 그것을 쓰는 주체는 모델 자신이다. 그래서 두 가지를 건다.

1. **표면 기준 하한을 CI 가 강제한다.** 보안 경로를 건드렸는데 T0/T1 로 선언했거나, 마이그레이션을 추가했는데 T3 이 아니면 빨간불이다. 계획서가 **아예 없으면** T0/T1 선언으로 간주하고 같은 검사를 건다 — 파일을 안 만드는 것으로 검사를 피할 수 없게 한다.
2. **실측이 선언보다 높아도 자동으로 올리지 않는다.** 머지 전 승인 지점에서 **정지하고 사람이 정한다.**

**근거.** 자동 승격은 「구현이 끝난 뒤에 계획 승인을 받는」 절차 역전을 만든다.
승인 게이트는 어차피 전 티어에 걸려 있으므로 사람이 보는 비용은 늘지 않는다.
그리고 하한 검사는 **보안·마이그레이션 표면만** 잡는다는 한계를 그대로 인정한다 —
선언 티어와 실측 티어를 승인 요약에 **나란히** 출력해 사람이 눈으로 대조한다.

### D4. 기존 작업 유형 분류(`TaskType`)와 **병존**한다

`TaskType`(자연어 제목 → 어느 서브에이전트, 어느 리뷰 렌즈)과 `Tier`(변경 경로 → 절차 강도, 게이트, CI 범위)는
**서로 직교하는 축**이다. 하나로 합치지 않는다.

**근거.** 둘은 답하는 질문이 다르다. 「누가 할 일인가」와 「얼마나 조심할 일인가」는 독립이다.
`ui` 유형이면서 보안 화면을 고치는 작업이 실재한다. 합치면 그런 조합이 표현 불가능해진다.

## 결과

- 새 파일 `scripts/workflow/surfaces.ts` 1개가 늘고, 대신 두 곳에 흩어져 있던 글로브 상수가 사라진다.
- `CLAUDE.md` 에는 4행짜리 요약표와 판정 3줄만 남는다. 표면 이름 전수와 글로브는 **적지 않는다**.
- 계획 문서 생성이 줄어든다 — T0/T1 은 0파일, T2 는 스펙을 흡수한 1파일, T3 만 기존대로다.
- **이득이 어디에 있는지 정직하게 적는다.** 사람이 멈춰 서는 횟수는 거의 그대로다. 줄어드는 것은 **스킬 호출 수**다.
- 검증은 2주 파일럿에서 한다(`.claude/pilot-log.md`). 실패 신호는 **T0/T1 에서 재작업이 몰리는 것**이다.

## 대안 (기각)

- **변경 파일 수 유지 + 임계값만 올린다.** 판정 시점에 값이 존재하지 않는다는 근본 문제가 그대로다. 위험과의 상관도 약하다.
- **작업 유형(`TaskType`)에 절차 강도를 얹는다.** 유형은 자연어 제목에서 추론하므로 「제목을 다르게 쓰면 절차가 가벼워진다」가 성립한다. 경로는 그렇게 속일 수 없다.
- **사람이 매번 티어를 정한다.** 판정 비용이 작업마다 붙고, 기준이 사람의 그날 상태에 좌우된다. 지금도 사람이 **뒤집을 수는** 있다 — 기본값을 기계가 정할 뿐이다.
- **표면 목록을 문서에만 둔다.** 문서는 기계가 안 읽는다. 그러면 판정과 문서가 갈라져도 아무도 모른다.
