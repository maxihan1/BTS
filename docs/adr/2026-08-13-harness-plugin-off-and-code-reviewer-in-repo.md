# ADR — superpowers 플러그인을 비활성하고 code-reviewer 를 저장소 안으로 옮긴다

> 날짜. 2026-08-13
> 상태. **채택 (Active)** — 설정 적용은 벤치마크 후 (`.claude/MIGRATION.md` 부록 A·B)
> 영역. 개발 하네스 (Claude Code 워크플로우) — 제품 도메인 아님
> 관련 FR. 없음 (제품 요구사항이 아니라 개발 환경 결정이다)
> 관련 문서. `.claude/MIGRATION.md` 부록 A · `.claude/agents/code-reviewer.md`
> 대체 관계. **대체하는 기존 ADR 없음** (`docs/adr/` 34건 전수 확인 — 전부 제품 도메인 결정)

## 맥락

**superpowers** 는 외부 마켓플레이스에서 설치한 플러그인이다. 스킬 14종 · 세션 시작 훅 2개 ·
서브에이전트 1개 · 커맨드 3개를 이 저장소의 작업 환경에 얹는다.
**플러그인 파일은 홈 디렉터리(`~/.claude/`)에 있어 git 이 추적하지 않는다.**

2026-08-13 실측이 세 가지를 드러냈다.

1. **비용.** 세션이 시작될 때마다 **1,362토큰**이 자동 주입되고, 스킬 목록에 **691토큰**이 더 붙는다. 합계 2,053토큰이 매 세션·매 컨텍스트 압축마다 재차 들어간다. 이는 전체 고정 비용 14,794토큰의 **14%** 다.
2. **실제 사용률.** BTS 스킬이 「호출한다」고 선언해 둔 하위 스킬의 36일 창 발동률은 3.0% · 0% · 0% 였다. 계획 작성 보조(34.3%)만 실질적으로 쓰인다. **선언과 실행이 이미 갈라져 있었고, 실행 쪽이 사실상 이 플러그인을 안 쓰고 있었다.**
3. **지침 모순.** 플러그인 문서는 「1% 가능성이라도 스킬을 반드시 먼저 호출하라」고 지시하고, 이 저장소의 `CLAUDE.md` 는 「단순 질문은 그냥 답변하고 임의 호출을 금지한다」고 지시한다. 우선순위 선언이 **플러그인 쪽 문서 안에만** 있어서, 어느 쪽을 따를지 판정하는 비용이 매 작업마다 붙었다.

동시에 문제가 하나 더 있었다. 머지 전 독립 리뷰 2종 중 하나가 **플러그인 안의 서브에이전트**(`code-reviewer`)다.
플러그인을 끄면 이 리뷰가 통째로 사라진다 — 즉 **비활성은 리뷰 검출력 절반을 잃는 결정과 묶여 있었다.**

## 결정

### D1. superpowers 를 **프로젝트 설정 1줄**로 비활성한다

`.claude/settings.json` 에 `"enabledPlugins": { "superpowers@superpowers-marketplace": false }` 를 넣는다.
**전역 설정(`~/.claude/settings.json`)은 열지 않는다.**

**근거.**
- 전역을 고치면 **다른 프로젝트까지 꺼진다.** 이 판정은 BTS 에서 안 쓰인다는 측정에 근거한 것이지 플러그인 자체의 판정이 아니다.
- 전역 파일은 git 밖이라 되돌림의 근거가 남지 않는다. 프로젝트 파일이면 **되돌림이 `git revert` 한 번**이다.
- 세션 시작 훅도 함께 사라진다. 훅을 따로 지울 필요가 없다.
- 플러그인 캐시는 그대로 두므로 **재활성이 즉시**다.

### D2. 리뷰용 서브에이전트를 **저장소 안으로 이관**한다 — `.claude/agents/code-reviewer.md`

플러그인 안의 48줄 영문 정의를 저장소 안 26줄 한국어 파일로 옮긴다.
호출하는 쪽의 대상 이름 지정도 같은 커밋에서 전수 교체한다.

**근거.**
- 이관하지 않으면 D1 이 **리뷰 2종 중 1종을 소리 없이 없앤다.**
- 저장소 안으로 오면 리뷰어 정의가 **버전 관리·코드리뷰 대상**이 된다. 지금까지는 홈 디렉터리 파일이라 아무도 그 변경을 못 봤다.
- **BTS 고유 계약은 이 파일에 넣지 않는다.** 호출하는 스킬이 그때그때 프롬프트로 주입한다. 리뷰어 정의에 프로젝트 규칙을 박으면 규칙이 바뀔 때마다 두 곳을 고쳐야 한다.

### D3. 이관 실패를 **기계가 잡게** 한다 (순증 1건)

서브에이전트 이름 목록과 실제 파일, 그리고 호출부의 이름 문자열이 **서로를 대조**하도록 검사 하나를 새로 만든다.
비교 기준은 파일명이 아니라 파일 안의 `name` 값이다 — 파일명은 이동으로 바뀌지만 `name` 은 실제로 불리는 식별자다.

**근거(순증을 감수하는 이유).** `.claude/agents/**` 는 이 저장소에서 **가장 조용히 깨지는 자산**이다.
어떤 CI 트리거에도 들어 있지 않아서, 파일을 지우거나 이름을 바꿔도 **아무 곳도 빨간불이 나지 않는다**.
이름 하나가 어긋나면 리뷰 요청이 실패하고, 그 사실은 **런타임에만**, 그것도 「리뷰 결과가 안 왔다」는 형태로 나타난다.
이 커밋에서 `.claude/agents/**` 를 CI 트리거 경로에도 함께 넣는다.

### D4. 전역 스킬 55종을 **비노출**로 돌린다 — 값은 `off` 가 아니라 `user-invocable-only`

같은 프로젝트 설정 파일의 `skillOverrides` 로 처리한다. 노출 65종 중 55종을 끄고 10종을 남긴다.

**근거.**
- **유지 기준은 36일 창의 실제 발동 이력**이다. 이름만 불리고 한 번도 안 돈 것은 비노출로 보낸다.
- `off` 대신 `user-invocable-only` 를 쓰는 이유는 **사람이 `/이름` 으로 부르는 길을 남기기 위해서**다. 두 값의 토큰 절감은 같다. 「필요해지면 타이핑으로 부른다」가 비노출 판정의 보완책이었으므로 그 길을 막으면 안 된다.
- ⚠ 이 값은 **모델의 자동 호출도 막는다.** 그래서 발동 이력이 있는 10종은 절대 넣지 않는다.
- 전역 스킬 파일 자체는 **한 바이트도 고치지 않는다.** 예전에 파일을 직접 고치는 방식을 검토했으나, 업그레이드 도구가 조용히 되돌려 놓는 문제가 있었다. 프로젝트 설정으로 하면 그 문제가 통째로 사라진다.

### D5. 적용은 **벤치마크 이후**로 미룬다

설정 내용은 확정하되 파일에는 아직 반영하지 않는다. 문서(`MIGRATION.md` 부록 A)에만 둔다.

**근거.** `.claude/settings.json` 은 저장소 안 파일이라 **브랜치를 바꾸는 것만으로 하네스가 바뀐다.**
구/신 대조 벤치마크가 바로 그 성질에 기대고 있어서, 지금 고치면 대조군이 오염된다.

## 결과

- 고정 컨텍스트에서 **2,053토큰(플러그인) + 1,681토큰(전역 스킬) = 3,734토큰**이 빠진다. 단 **벤치마크 이후**다.
- 리뷰 2종 체계는 유지된다. 대신 리뷰어 정의가 저장소 안으로 들어와 리뷰 대상이 된다.
- 지침 모순 6건이 소멸한다 — 한쪽 문서가 사라지므로 우선순위를 정할 필요 자체가 없어진다.
- **되돌림 비용이 사실상 0 이다.** git 밖 파일을 한 바이트도 고치지 않았으므로 `git revert` 한 번과 재적재 명령 한 번이면 원상태다.
- **⚠ 남는 위험 — 설정 키 오타는 조용히 무효**다. 기계 방어가 없다. 적용 직후 스킬 목록을 눈으로 한 번 확인하는 것이 유일한 검증이며, 그 확인을 절차로 못 박았다.
- **축약 손실은 미검증이다.** 리뷰어 정의를 48줄에서 26줄로 줄이면서 무엇을 잃었는지는 코드를 읽어서 판단한 것이지 실제 리뷰 결과를 비교한 것이 아니다. Phase 4 벤치마크에서 구/신 리뷰 산출물을 대조해야 한다.

## 대안 (기각)

- **전역 설정에서 끈다.** 다른 프로젝트까지 영향을 받고, git 밖이라 되돌림 근거가 남지 않는다.
- **전역 스킬 파일의 frontmatter 를 직접 고친다.** 업그레이드 도구가 되돌려 놓는다. 되돌림을 막으려면 재적용 스크립트를 또 만들어야 하는데, 그 스크립트가 새로운 유지 부담이 된다.
- **플러그인을 남기고 지침 우선순위만 명문화한다.** 모순은 줄지만 토큰 2,053 은 그대로다. 그리고 실제 발동률이 0~3% 라 명문화의 이득이 거의 없다.
- **리뷰어를 이관하지 않고 리뷰 1종으로 줄인다.** 독립 리뷰는 이 저장소에서 반복적으로 실제 결함을 잡아 온 장치다. 검출력 절반을 비용 없이 버리는 선택이라 기각한다.
- **빌트인 스킬 15종(1,596토큰)도 함께 끈다.** 기술적으로 가능하지만 어느 것이 실사용인지 전수 판정이 없다. 목표 달성에 불필요하므로 손대지 않는다.
