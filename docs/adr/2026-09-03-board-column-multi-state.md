# ADR — 보드 컬럼이 워크플로우 상태를 여러 개 매핑한다 (컬럼:상태 1:1 → 1:N)

> 날짜 2026-09-03 · BC agile-planning · PR #444 · 티어 T3
> spec [`2026-09-03-board-column-multi-state`](../specs/2026-09-03-board-column-multi-state.md) ·
> plan [`2026-09-03-board-column-multi-state`](../plans/2026-09-03-board-column-multi-state.md)

## 맥락

`board_columns` 각 행이 워크플로우 상태 **1개**에 1:1 매핑된다. `UNIQUE (board_id, state_key)` 가
강제하고 `V500__boards.sql:26` 주석이 「상태 1:1 매핑」이라고 명시한다.

그래서 지라의 흔한 구성인 「진행 중 컬럼에 `in_progress` + `in_review` 를 함께」를 만들 수 없고,
컬럼이 상태 수만큼 늘어난다.

**그 1:1 은 지라와 대조된 적이 없다.** 원 스펙 `docs/specs/2026-06-20-fr-bd-01-kanban-board.md:10`
이 설계로 못박았으나 그 문서에는 `## Jira 대조` 절이 **아예 없다** — 작성일이
`jira-parity-contract` 컷오프(2026-08-27)보다 빨라 강제 대상이 아니었다. 지라를 보고 내린 결정도,
의도적 편차로 등재된 것도 아니다.

발단은 Maxi 의 질문이었다 — 「이슈 상태가 변경되면 보드에도 자동 반영되나」. 답은 **반영된다,
동기화가 아니라 저장 자체를 안 한다**(`placeCards` 가 조회 시점에 `groupBy` 로 배치한다). 그 확인
과정에서 1:1 제약이 드러났다.

## 결정

### D1. 컬럼:상태를 1:N 으로 만든다 — 연결 테이블 `board_column_states`

`board_columns.state_key` 를 별도 테이블로 분리한다. 컬럼 1개가 상태 **0개 이상**을 담는다.

**서식 정본은 발명하지 않았다.** `V203__add_global_status_catalog.sql:36-60` 의 `workflow_statuses`
가 같은 저장소 안의 같은 형태 선례다 — 부모 FK CASCADE · 대상 키 · `display_order` ·
`UNIQUE(부모, 대상)` · FK 인덱스 명시. 그것을 복제한다.

### D2. `moveCard` 가 `toStateKey` 를 받는다 — 서버는 상태를 추론하지 않는다

**이 ADR 에서 가장 중요한 조항이다.**

착수 시점에 이렇게 판단했다 — 「컬럼에 상태가 여럿이면 `toStateKey = targetColumn.stateKey`
(`BoardApplicationService.kt:413`)가 **결정 불가**가 된다」. 후보를 셋 세웠다. ①컬럼의 첫 상태 고정
②현재 상태에서 허용된 전환이 있는 상태 ③사용자 선택.

**지라는 셋 중 어느 것도 아니었다.**

> *"each status will be represented as a drop zone on your board's column"*
> — Bryan Lim(**Atlassian Team 배지 · Jira Software PM**) · 2026-09-03 · Cloud

컬럼을 상태별 **드롭존**으로 쪼개고 사용자가 드롭 지점으로 직접 고른다. 즉 지라에는
「컬럼으로 드롭」이라는 조작 **자체가 없고** 「컬럼 안의 특정 상태로 드롭」만 있다.

**결정 불가 문제가 API 계약 층에서 사라진다.** 클라이언트가 `toStateKey` 를 보내고 서버는 그 상태가
그 보드의 어느 컬럼엔가 매핑돼 있는지만 검증한다.

내 후보 3개는 전부 **「서버가 정한다」는 전제**를 깔고 있었다. 기억으로 답했으면 틀렸을 자리다.

### D3. 한 상태는 한 컬럼에만 매핑된다 — `UNIQUE (board_id, state_key)` 유지 (편차 X1)

지라 문서가 「한 상태를 두 컬럼에」를 **다루지 않는다.** 매핑 절차가 「Unmapped 패널 ↔ 컬럼 이동」과
「컬럼 삭제 시 Unmapped 복귀」로만 서술돼 단일 배정을 함의하나 **원문 확증이 없다.**

계약 §5 가 근거 없는 자체 발명을 금지하므로 **현행 제약을 유지한다. 푸는 쪽이 발명이다.**

실질 근거도 있다 — 풀면 `placeCards` 가 같은 이슈를 두 컬럼에 넣어 **사용자가 카드를 두 번 본다.**

연결 테이블에 **`board_id` 를 비정규화**해 이 불변식을 DB 가 지게 한다. `column_id` 만 두면
「한 상태가 같은 보드의 두 컬럼에」를 막지 못한다. `V500:39` 가 지키던 것을 **그대로 옮기는**
것이지 새 제약이 아니다.

### D4. 미매핑 상태를 1급 개념으로 들인다 (Maxi 확정)

지라에는 `Unmapped statuses` 패널이 있고 컬럼을 지우면 그 상태들이 그리로 돌아간다(J2·J5).
**BTS 에는 이 개념이 아예 없었다** — `seedColumns` 가 워크플로우 상태 **전량**을 컬럼으로 만들어
미매핑이 생길 수 없었기 때문이다.

1:N 을 도입하면 「컬럼에서 상태를 뺀다」가 가능해지고, 그 순간 **뺀 상태를 둘 곳**이 필요하다.
미매핑 없이는 상태를 빼는 조작 자체가 성립하지 않는다.

부수 효과로 기존 결함 하나가 닫힌다 — 워크플로우에 상태를 추가하면 그 상태의 이슈가
`unplacedCount` 로만 세어지고 **왜 사라졌는지 알 길이 없던** 것이, 이제 미매핑 목록에 이름과 함께
드러난다(`V500:28` 이 「후속 FR」로 미뤄 둔 자리).

### D5. 완료 판정을 「최우측 컬럼」으로 옮기지 않는다 (편차 X2)

지라는 컬럼 **위치**로 완료를 판정한다 — *"Jira only considers work items in the right-most column
of your board as complete."* BTS 는 `category` 스냅샷으로 판정한다.

위치 기반으로 바꾸면 스프린트 완료·번다운·백로그 완료 판정이 전부 흔들린다. 이 PR 범위 밖이다.

**실측으로 안전을 확인했다** — `category` 는 표시용이고 로직 판정에 안 쓰인다. `agile-planning` 의
`.category` 참조 8곳이 전부 DTO 변환·매핑이다(`V500:27` 이 「표시용 스냅샷」이라 적었고 일치).
따라서 1:N 에서 한 컬럼에 서로 다른 category 가 섞여도(예: 「완료」에 `done`+`wont_fix`)
파급이 표시에 한정된다.

### D6. UI 는 후속 PR · 대신 프론트를 최소 수정한다 (편차 X3)

드롭존·미매핑 패널 **화면**은 별도 PR 이다(Maxi 확정). FR-BD-04 가 #421(스키마·백엔드) →
#422·#424(UI)로 쪼갠 선례와 같다.

**단 하위 호환만으로는 부족하다는 것이 sanity check 에서 드러났다(G4).** 이 PR 이 매핑 변경 API 를
주므로, 사용자가 상태 2개를 묶는 순간 기존 화면이 400 을 받는다 — 「기능은 있는데 쓰면 화면이
깨진다」. 그래서 프론트가 `toStateKey`(컬럼의 첫 상태)를 보내도록 **최소 수정**한다(R12).
상태 1개인 오늘의 보드에서는 동작이 완전히 같다.

## 기각한 대안

**A-1. 컬럼당 상태를 배열 컬럼(`TEXT[]`)으로 둔다.** 테이블을 안 늘려도 된다.
기각 — `UNIQUE(board_id, state_key)`(D3)를 DB 가 못 진다. 배열 원소의 유일성은 제약으로 표현되지
않아 애플리케이션이 지게 되는데, 그것이 정확히 「DB 가 막아 주지 않는」 상태다.
`display_order`(드롭존 순서)도 배열 인덱스에 얹으면 재정렬이 전체 쓰기가 된다.

**A-2. `moveCard` 를 그대로 두고 서버가 상태를 고른다.** 프론트를 안 바꿔도 된다.
기각 — D2 의 지라 근거와 정면으로 어긋난다. 어떤 규칙을 골라도 사용자가 의도하지 않은 상태로
카드가 간다. 「첫 상태 고정」이면 `in_review` 로 옮길 방법이 영영 없다.

**A-3. `UNIQUE` 를 풀어 한 상태를 여러 컬럼에.** 유연하다.
기각 — D3. 근거 없는 발명이고 카드가 두 번 보인다.

**A-4. `board_columns.state_key` 를 이 PR 에서 DROP.** 이중 기록이 없어 깔끔하다.
기각 — `DATA.md §4` 3단 분할 위반. 신설과 DROP 을 한 PR 에 넣으면 롤백 창이 사라진다.

**A-5. 카드 표시 필드 설정을 이 PR 에 함께.** 같은 「보드 설정」 표면이다.
기각 — 서로 안 거드리는 독립 기능이고(별도 테이블·API·UI) PR 이 두 배가 된다. 지라도 Board
settings 안에 `Columns` 와 `Card layout` 을 따로 둔다. **부채 177 로 등재하고 별도 PR**(Maxi 확정).

## 영향

### 긍정

- 「진행 중」에 `in_progress`+`in_review` 를 묶는 지라의 흔한 구성이 가능해진다.
- 워크플로우에 상태를 추가했을 때 이슈가 **왜** 보드에서 사라졌는지 드러난다(D4).
- 컬럼 CRUD 가 생겨 보드가 만들어진 순간의 모습으로 굳지 않는다.

### 부정 / 위험

- **마이그레이션 + 코드 전환이 한 PR 에 든다.** 이중 기록 창(E5)이 생기고 그동안 두 곳이 갈릴 수 있다.
- **프론트 17파일이 `stateKey` 를 쓴다.** learning 2026-05-30 「Zod 스키마 강화가 산재한 인라인
  mock 을 깬다」의 양식이라 `tsc --noEmit` 동반이 필수다(vitest 는 타입체크를 안 한다).
- **`BoardRepository.kt` 가 이미 443줄로 §2.1 상한 초과**(부채 157). 새 쿼리를 별도 파일로 빼야 한다.
- **UI 가 없는 채로 머지된다.** D6 의 최소 수정이 그 간극을 메우지만, 상태 2개짜리 컬럼의 사용자
  경험은 드롭존 PR 전까지 「첫 상태로만 간다」이다.
