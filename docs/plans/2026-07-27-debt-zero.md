### DZ-1. 부채의 정의 범위

### DZ-2. worktree 대신 브랜치
`/bts` 의 worktree-per-작업은 **절대 규칙 19개에 없다**(CLAUDE.md §핵심 패턴). 이번은 동시 작업이

단일 브랜치로 진행했다. **절대 규칙 14(TDD)는 전 항목에 적용**했다.

### DZ-3. 가드는 반드시 뮤테이션으로 확증한다
신설한 봉인 전부 **위반을 주입해 FAILED 를 확인**했고, 기준선 EXIT=0 을 선확인했다.
ArchUnit·커버리지 판별식처럼 "위반이 없어서 green" 인 경우에는 **비-공허 테스트를 별도로** 뒀다.

### DZ-4. baseline 은 늘리지 않는다
detekt MaxLineLength · ktlint argument-list-wrapping 위반이 내 변경으로 발생했을 때
baseline 에 추가하지 않고 **코드로 해소**했다. ktlint baseline 은 633→632 로 줄었다.

## 6. 종결 — 부채 0 판정 (2026-07-27)

### 6.1 ★ 최초의 "부채 0" 판정은 틀렸다 — 판별식이 헤딩만 셌다

**이 절에 처음 적었던 문장 (2026-07-27, 오류로 판명).**

> `TODOS.md` **28항목 전부 ✅, 열림 0건.** 착수 시점 27건 + 작업 중 실측으로 신규 등재 1건(flaky).

**그 판정을 만든 명령.**

```bash
grep -c "^## "   TODOS.md   # → 28
grep -c "^## ✅" TODOS.md   # → 28   ⇒ "열림 0건"
```

**왜 틀렸나.** 한 항목은 `## ` 헤딩 하나로 **시작**하지만, 미해결은 헤딩이 아니라 **본문 안에서
살아 있다.** 항목을 닫으면서 그 과정에 갈라져 나온 잔여·후속을 같은 절 안에 `### 잔여` /
`**후속 작업**` / `**남은 후속**` 으로 적어 두는 것이 이 파일의 관례이기 때문이다.
⇒ 헤딩만 세면 **✅ 절 안에 묻힌 열린 항목이 전부 0 으로 집계된다.**
판별식이 보는 층(헤딩)과 사실이 사는 층(본문)이 달랐다.

이건 「세다가 실수했다」가 아니다. **측정 대상을 잘못 고른 것**이라, 몇 번을 다시 돌려도 같은
0 이 나온다. 재실행으로는 절대 안 잡힌다.

**올바른 판별식 — 두 층을 모두 본다.**

```bash
# 1층. 항목 헤딩 상태
grep -cE "^## "   TODOS.md
grep -cE "^## ✅" TODOS.md

# 2층. ★✅ 절 안에 묻힌 열린 잔여 — 이 층을 빼먹어서 틀렸다
grep -nE "^### (잔여|남은|후속)|^\*\*(잔여|남은 후속|후속 작업)" TODOS.md
```

**2층은 세는 게 아니라 열거하는 것이다.** 뽑힌 줄마다 해소 / 기각 / 존치를 하나씩 판정해야
열림 건수가 나온다. grep 이 뱉은 줄 수를 그대로 「열림 N건」으로 쓰면 1층에서 저지른 실수를
2층에서 반복하는 것이다.

**처방 (후속 제안).** 위 정규식은 지금 쓰이는 표기를 사후에 긁어모은 것이라, 새 잔여가 다른
문구로 적히면 조용히 빠진다 — **판별식이 눈감는 조건이 문서 저자의 표기 습관에 달려 있다.**
잔여 표기를 마커 하나(예: `- [ ] 잔여.`)로 고정하면 2층도 기계적 판정이 된다. 채택 여부는
`TODOS.md` 관리 주체가 정한다.

**최종 수치는 이 문서가 확정하지 않는다.** 위 2층 판별식으로 뽑은 잔여의 판정이 끝나야
열림 건수가 나온다. **오케스트레이터가 최종 확정한다** — 여기에 숫자를 다시 지어 넣지 않는다.

### 6.3 마지막 항목 — flaky 는 "느림" 이 아니라 "메시지 도둑질" 이었다

다른 쪽은 **영원히 0건**을 본다.

`awaitility` 타임아웃이라는 증상만 보면 "여유를 늘리자" 로 간다. 그 처방은 **절대 안 듣는다** —
메시지가 늦게 오는 게 아니라 아예 안 오기 때문이다.

⇒ **판별 질문**. 「늦게 오나, 아예 안 오나」. 이걸 먼저 가르면 처방이 정반대가 된다.
