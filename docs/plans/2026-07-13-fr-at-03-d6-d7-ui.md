## 도메인 정리

- **BC**. automation
- **영향 엔티티**. `AutomationRule.condition`(기존, PR #262 확립) — sealed `Condition` 트리:
  `And(conditions[])` / `Or(conditions[])` / `Not(condition)` / `Comparison(var, op, value)`.
- **모델 규정(ADR 2026-07-12-fr-at-03-automation-conditions)**.
  - Comparison `var` 화이트리스트 9종: `issue.key / issue.type / issue.status / issue.priority /
    issue.assignee / issue.reporter / issue.labels / issue.summary / issue.projectKey`.
  - 제약: `MAX_DEPTH=10`, `MAX_NODES=100`, 리터럴 배열 원소 ≤100 (저장 시점 검증).
  - 저장: `V304__automation_conditions`(rule_id PK · expression JSONB · ON DELETE CASCADE).
  - 평가: `ConditionEvaluator` 순수 트리워크 fail-safe. 조건 미설정=게이트 통과, 불충족=`SKIPPED`.
  - 보안: 평가 주체=`createdBy`(위조 불가), actorUserId 아님(§12.4 read 오라클 차단).
- **새 용어**. 없음. "조건 빌더 / 트리 편집기 / 노드"는 UI 표현 계층 용어 — 도메인 엔티티 아니라
  glossary 추가 불필요.
- **기존 결정 충돌**. 없음. ADR 2026-07-12-fr-at-03-automation-conditions 준수(뷰 계층 소비).
- **관련 ADR**. [docs/decisions/2026-07-12-fr-at-03-automation-conditions.md](../decisions/2026-07-12-fr-at-03-automation-conditions.md) (기존, 신규 ADR 불필요)
- **grill-with-docs**. 스킵 — 모델이 PR #262에서 완전 확립·소비만 하는 뷰 계층이라 신규 용어 0.

### spec 단계로 이월할 열린 질문
1. **조건 제거 3-state**. 백엔드 PATCH가 `condition=null`을 "미변경"으로 해석(plan #262 §296:
   "명시 제거 3-state는 D6 후속"). 조건을 **명시적으로 제거**하려면 set/clear/unchanged 3-state가
   필요 — 백엔드 소량 터치(clear 시맨틱) 필요 여부 확정. issue-tracking DatePatch 3-state 선례 참고.
2. **백엔드 API 정확한 계약**. condition JSON 직렬화 shape(sealed 클래스 판별자 형식) + operator 집합 +
   PATCH 엔드포인트 경로/요청 형식을 backend 소스 grep으로 확정(Frontend Zod↔backend DTO 계약갭 방지).

### Task 1. condition Zod 확장 + ConditionNode 타입 + parse/serialize 왕복 헬퍼

**메타**.
- agent: `frontend-engineer`
- files: [`apps/web/src/api/automation-rules.types.ts`, `apps/web/src/api/automation-rules.types.test.ts`]
- depends-on: []

**RED**. `automation-rules.types.test.ts`에 실패 테스트 추가.
- `automationRuleResponseSchema.parse`가 `condition: "{\"and\":[]}"` / `condition: null` 둘 다 통과.
- `parseConditionExpression(null)` → 빈 트리, `parseConditionExpression('{"and":[]}')` → 빈 트리(왕복 EC2).
- `serializeConditionExpression(빈 트리)` → `'{"and":[]}'`([D1]).
- 왕복: 중첩 And/Or/Not + Comparison(이항·`in`역순 EC4·단항 `!`/`!!` EC5) → serialize → parse === 원본.
- 빈 그룹 prune(G2): `Or([])` 포함 트리 serialize → 빈 그룹 제거 확인.

**GREEN**.
- `automationRuleResponseSchema`에 `condition: z.string().nullable()` 추가.
- `CreateAutomationRuleInput`·`PatchAutomationRuleInput`에 `condition?: string` 추가.
- `ConditionNode` union 타입: `Group{ op:'and'|'or'; not?:boolean; children:ConditionNode[] }` |
  `Comparison{ field:string; operator:ComparisonOperator; value?:unknown }`. `ComparisonOperator` 9종 상수.
- `parseConditionExpression`/`serializeConditionExpression` — JSONLogic 부분집합 ↔ 트리. 빈 그룹 prune,
  `in` 역순 정규화, priority/impact 숫자 강제(EC6).

**REFACTOR**. 연산자 메타(jsonKey↔arity↔라벨) 테이블 상수 추출. `parseActionConfig` 선례 주석.

**리뷰 보강(E1·E2)**.
- **E1(계약갭 방지, 필수)**. 왕복 대칭만이 아니라 `serializeConditionExpression` 출력을 백엔드
  `Condition.kt` 와이어 shape와 **하드코딩 기대 JSON**으로 대조 — 이항 `{">":[{"var":"issue.priority"},3]}`
  (var 선두), `in` 정규형 `{"in":[{"var":field},리터럴]}`, 단항 `{"!":{"var":field}}`. 프론트끼리만
  일관하고 백엔드 400 나는 케이스 차단(Frontend Zod↔backend DTO 계약갭).
- **E2**. 숫자 강제는 `in` 배열 원소(priority/impact 배열 `[1,2,3]`)까지 적용.

**검증**. `pnpm --filter web test -- automation-rules.types`
