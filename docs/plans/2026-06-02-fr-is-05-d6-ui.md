## Brief

이슈 목록에서 다중 선택 + 일괄 액션 바(일괄 편집 / 일괄 상태 전환)를 구현한다.
요청을 `POST /api/v1/issues/bulk-update`(202 + bulkOperationId)로 접수한 뒤,
`GET /api/v1/bulk-operations/{id}`로 진행률/결과를 폴링해 표시한다(actor 본인 한정).

- 백엔드 API는 PR #54(접수/조회) + #56(처리)로 이미 main 머지 완료.
- 비동기 "진동벨" 아키텍처: 접수 202 → pgmq 워커 백그라운드 처리 → 진행률 폴링 조회.
- best-effort 부분성공: 이슈별 독립 처리, 실패만 reasonCode 반환.

분류 결과: type=ui, agent=frontend-engineer, primary_bc=issue-tracking.

### 백엔드 API 계약 (grep 검증 완료 — invent 금지, 계약갭 방지)

**1) 접수 — `POST /api/v1/issues/bulk-update`**
- 요청 바디(`BulkUpdateWebRequest`):
  - `operationType`: `"BULK_EDIT"` | `"BULK_TRANSITION"` (필수)
  - `issueKeys`: `string[]` (필수, 1~1000개, 중복은 서버가 dedup)
  - `editPayload`: `{ priority: number|null, impact: number|null } | null` — BULK_EDIT 전용. priority 1..5, impact 1..3, null=무변경(merge-patch)
  - `transitionPayload`: `{ toStateKey: string } | null` — BULK_TRANSITION 전용
  - 규칙: operationType ↔ payload 일치 필수(불일치 시 400)
- 응답 **202 Accepted**, 봉투 `DataResponse<T>` = `{ data: T }`:
  - `data.bulkOperationId`: UUID 문자열
  - `data.status`: 항상 `"PENDING"`
  - `data.totalCount`: dedup 후 대상 수(number)

**2) 조회 — `GET /api/v1/bulk-operations/{id}`**
- 응답 **200 OK**, 봉투 `{ data: BulkOperationResponse }`:
  - `id`: UUID 문자열
  - `operationType`: `"BULK_EDIT"` | `"BULK_TRANSITION"`
  - `status`: `"PENDING"` | `"RUNNING"` | `"COMPLETED"` | `"FAILED"`
  - `payload`: **타입 구분자 없는 객체** — operationType으로 판별. EDIT면 `{priority,impact}`, TRANSITION이면 `{toStateKey}`
  - `totalCount` / `processedCount` / `succeededCount` / `failedCount`: number (진행률 계산 = processedCount/totalCount)
  - `items`: `{ issueKey: string, status: "PENDING"|"SUCCEEDED"|"FAILED", failureReasonCode: string|null }[]`
    - failureReasonCode(FAILED일 때만): `NOT_FOUND` | `FORBIDDEN` | `TRANSITION_NOT_ALLOWED` | `VERSION_CONFLICT` | `WORKFLOW_NOT_CONFIGURED` | `TYPE_NOT_FOUND`(dead) | `UNKNOWN`

**3) 에러 — RFC 7807 ProblemDetail** (issue 도메인과 동일 형태):
- 400 `ISSUE_BULK_VALIDATION_FAILED` (issueKeys 비어있음/1000초과/payload 불일치/enum 오타)
- 403 `ISSUE_BULK_FORBIDDEN` (작업 owner 아님)
- 404 `ISSUE_BULK_NOT_FOUND`
- 500 `ISSUE_BULK_INTERNAL_ERROR`
- 본문: `{ type, title, status, detail, errorCode, timestamp }`

### 도메인 주의 사항 (spec/plan에 반영)

- **계약갭 위험 #1 (payload 판별)**: Zod 스키마는 payload를 operationType 기준 분기 union으로. payload 내부 discriminator 없음.
- **계약갭 위험 #2 (인증 미연동)**: 컨트롤러가 현재 `SYSTEM_ACTOR_UUID`(00000000-...-001) 하드코딩. 실제 SecurityContext 미연동 → D6 프론트는 "본인 작업만 조회" 동작을 실서버에서 검증 불가. E2E(D7)는 MSW mock 기반이어야 함(메모리 e2e-fixture-whoami-userid-alignment 정합 주의).
- **진행률 폴링**: status가 종단(COMPLETED/FAILED) 도달 전까지 GET 폴링. 폴링 중지 조건/주기는 spec에서 확정. 응답이 매번 전체 items를 주므로 setQueryData 부분교체 플리커 함정(메모리) 회피 — invalidate/refetch 기반 권장.
- **관련 ADR**: [docs/adr/2026-06-02-bulk-operation-async-architecture.md](../adr/2026-06-02-bulk-operation-async-architecture.md)
