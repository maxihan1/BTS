### §1-1 추가 조회 결과 (2026-09-02) — **대응 없음 확정**

「이관 **진행 상황·실패 항목**을 Jira 는 **화면에서** 어떻게 보여주는가」를 조회했다. J6 는
*API 레벨*(location link 로 task 를 좇는다)만 답하고 화면 표현은 답하지 않아, 이번 변경이 새로

**결과 — 대응 없음.** `move-issues-to-new-statuses-while-updating-your-workflow` 전문을 다시 읽었으나
진행률 표시 · 완료 알림 · 실패 항목 목록에 해당하는 서술이 **한 문장도 없다**. 문서가 이관에 대해

## 스펙

### 사용자 시나리오 (Given-When-Then)

**S1. 이관이 필요 없는 발행** (10a 가 이미 냄 — 회귀 방지 기준선)
> **Given** 초안이 상태를 빼지 않았거나 뺀 상태에 이슈가 0건
> **When** 발행을 누른다
> **Then** 마법사 없이 곧바로 발행되고 회차가 토스트에 뜬다

**S2. 이관이 필요한 발행 — 마법사가 뜬다** (J2 · 이 PR 이 닫는 행)
> **Given** 초안이 상태 2개를 뺐고 각각에 이슈가 남아 있다
> **When** 발행을 누른다
> **Then** 미리보기가 `removedStatusKeys` 2건과 `pendingIssueCounts` 를 돌려주고,
> **빠지는 상태마다 도착지를 각각 고르는** 마법사가 뜬다(J7). 상태별 잔여 건수가 함께 보인다(J3)

**S3. 도착지를 고르고 이관을 시작한다**
> **Given** 마법사가 떠 있고 사라지는 상태 2개 중 1개만 도착지를 골랐다
> **When** 이관 시작 버튼을 본다
> **Then** **비활성**이다 — 전부 고르기 전에는 시작할 수 없다(서버 가드 「빈 목록」·「빠지지 않는
> 출발지」와 짝을 이룬다). 둘 다 고르면 활성화되고, 누르면 202 로 `bulkOperationId` 를 받는다

**S4. 진행률을 폴링한다** (J6 · ADS A1)
> **Given** 이관이 접수됐다
> **When** 화면이 `GET /api/v1/bulk-operations/{id}` 를 주기적으로 부른다
> **Then** `processedCount / totalCount` 로 진행률이 갱신되고, `COMPLETED` 또는 `FAILED` 에
> 도달하면 폴링이 **멈춘다**

**S5. 이관이 끝나면 발행을 이어 부른다** (X5 · G-1 결정)
> **Given** 이관이 `COMPLETED` 이고 `failedCount == 0`
> **When** **사용자가 다시** 발행 버튼을 누른다 (자동으로 이어 부르지 않는다)
> **Then** `POST /publish` 가 성공한다 — 서버의 `requireNoPending` 이 이제 통과한다

**S6. 일부가 옮겨지지 않았다** (ADS A2)
> **Given** 이관이 끝났으나 `failedCount > 0`
> **When** 결과를 본다
> **Then** 실패 항목이 **이슈 키 + 실패 사유**로 나열된다(`failureReasonCode` 9종).
> 발행을 눌러도 서버가 `MappingRequired` 로 막으므로, 화면이 **먼저** 그 사실을 고지한다

**S7. 규칙 미발화 고지** (J8 — 표시 의무)
> **Given** 마법사가 떠 있다
> **When** 사용자가 도착지를 고른다
> **Then** 「이관은 전환 규칙(조건·검증기·후처리)을 타지 않는다」가 상시 보인다.
> 사용자가 「검증기가 막아 주겠지」로 오해하면 **그 오해가 데이터에 남는다**

**S8. 보드 컬럼 고지 — 무조건부** (X4)
> **Given** 사라지는 상태가 1건 이상이다
> **When** 마법사가 뜬다
> **Then** 「이 상태를 쓰는 보드 컬럼이 있으면 함께 확인하라」가 **조건 없이** 보인다.
> 조건 판정을 흉내 내면 그것이 거짓말이 된다

스펙을 스스로 흔들어 **gap 3건**을 찾았고 셋 다 「사용자가 무엇을 보게 되는가」를 가르는 제품
결정이라 추정하지 않고 물었다. 추정으로 정하면 그 추정이 화면에 굳는다.

**❓ G-1 → 결정. 이관 후 발행은 사용자가 다시 누른다 (2단 노출)**
서버가 `migrate`/`publish` 를 2조작으로 가른 이유(BC 경계)를 화면이 감추지 않는다.
**자동 이어부르기를 기각한 근거** — 일부 실패가 섞이면 이어지는 발행이 **반드시** 409(`MappingRequired`)
로 죽고, 그때 사용자는 **자기가 누르지 않은 조작의 실패**를 본다. 원인과 조작이 어긋나면 사용자는
무엇을 고쳐야 할지 알 수 없다.

**❓ G-2 → 결정. `bulkOperationId` 를 URL 쿼리에 보관한다 (`?migration=<id>`)**
쿼리 캐시에만 두면 새로고침 한 번에 진행률이 사라지고, 서버 작업은 계속 도는데 화면만 몰라
사용자는 **이관이 실패한 줄 안다**. URL 은 별도 저장소가 없고 새로고침·링크 공유에 견디며 상태가
주소에 보여 디버깅도 쉽다. localStorage 는 다른 탭·기기와 어긋나고 만료 정책을 따로 정해야 해 기각.

**❓ G-3 → 결정. 폴링 중 「초안 폐기」를 비활성화한다**
비가역 조작이 진행 중일 때 그것을 무효화하는 버튼을 누를 수 있게 두지 않는다. 폐기하면 이어지는
발행이 404 이고 **이미 옮겨진 이슈는 되돌아오지 않는다** — 반쯤 진행된 비가역 상태가 조용히 남는다.
이관이 종료 상태에 도달하면 다시 활성화한다.

스펙의 나머지(F1~F12 · E1~E10 · 완료 기준)는 서버 계약과 Jira 근거로 결정돼 있어 추가 gap 이 없다.
