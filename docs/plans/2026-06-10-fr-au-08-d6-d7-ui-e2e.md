소비 API (백엔드 완료, #103/#104).

- `POST /api/v1/auth/account/links` — LDAP 동기 연결 (step-up 필요, 신규201/멱등200)
- `DELETE /api/v1/auth/account/links/{id}` — 해제 (step-up 필요, 204, 마지막수단 409)
- `POST /api/v1/auth/account/links/sso/start` — SSO 연결 시작 (step-up 필요, XHR → authorizeUrl + JSESSIONID)
- `POST /api/v1/auth/account/reauth/sso/start` — SSO 재인증 시작 (XHR → authorizeUrl)
- SSO 콜백 복귀 → `/settings/account-links?link=success|already_linked|conflict|error` 또는 `?reauth=success|failed`

- **새 프론트 개념**. (1) 계정 연결 설정 페이지(`/settings/account-links`) (2) step-up 재인증 흐름(민감동작 전 재인증→5분 윈도우) (3) SSO 리다이렉트 2단계(XHR start→`window.location.assign`) (4) SSO 콜백 복귀 쿼리 처리.

### 백엔드 API 계약 (실측 — Zod 1:1 정합 대상, frontend-zod-backend-dto-contract-gap)

| 메서드·경로 | 요청 | 성공 | 에러코드 |
|---|---|---|---|
| `GET /api/v1/auth/account/links` | — | 200 `{links:[{id,providerId,providerName?,providerType?,providerEnabled,externalSubjectMasked,linkedAt,lastLoginAt?}], hasLocalPassword}` | 403 `account_linking_requires_interactive_login`(PAT) |
| `POST /api/v1/auth/account/reauth` | `{method:"LOCAL"\|"LDAP", password, providerId?, username?}` | 200 `{stepUpExpiresAt}` | 400 `reauth_fields_required` / 401 `reauth_failed` / 403 PAT |
| `POST /api/v1/auth/account/links` | `{providerId(UUID), username, password}` | 201 신규 / 200 멱등 `AccountLinkResponse` | 403 PAT\|`step_up_required` / 401 `link_authentication_failed` / 409 `account_already_linked` / 503 `provider_unavailable` |
| `DELETE /api/v1/auth/account/links/{id}` | — | 204 | 403 PAT\|`step_up_required` / 409 `last_login_method` / 404 |
| `POST /api/v1/auth/account/links/sso/start` | `{registrationId, providerType:"SAML"\|"OIDC"}` | 200 `{authorizeUrl}` | 403 PAT\|`step_up_required` / 400 `invalid_sso_request` / 404 `provider_not_found` |
| `POST /api/v1/auth/account/reauth/sso/start` | 동일 | 200 `{authorizeUrl}` | 403 PAT\|sid부재 / 400 / 404 |

- **ProviderType enum**. `LOCAL` / `LDAP` / `SAML` / `OIDC` / `PAT` / `OAUTH`.
- **SSO 콜백 복귀(백엔드 고정 경로 실측)**. `/settings/account-links` + `?link=success\|already_linked\|conflict\|error` 또는 `?reauth=success\|failed`. ⟹ **프론트 라우트는 반드시 `/settings/account-links`** (SsoLinkingCallbackProcessor `SETTINGS_PATH` 상수).
- **CSRF**. mutation은 `X-XSRF-TOKEN` 수동(identity-access self-service 관례, `sessions.ts` 선례). JWT는 apiFetch가 Authorization 자동.

### 🔴 Contract gap (Maxi 결정 필요) — 연결 추가 UI의 provider 출처

"계정 추가" UI를 만들려면 프론트가 연결 가능한 provider 식별자를 알아야 함. 실측 결과.
- **SSO(SAML/OIDC)** — ✅ 해결됨. `GET /api/v1/auth/saml/idps`·`GET /api/v1/auth/oidc/providers`가 `{registrationId, displayName}` 반환(permitAll, 인증 사용자도 호출 가능). SSO 연결 = registrationId+type로 `/links/sso/start` 호출 가능.
- **LDAP** — ❌ gap. `POST /links`는 `providerId: UUID` 필요. 그런데 인증 사용자에게 LDAP provider UUID를 주는 엔드포인트가 **전무**(로그인용 `/providers`는 `id="ldap"` 토큰만·UUID 아님·LOCAL/LDAP만). ⟹ LDAP 연결 추가 UI 불가.

**✅ Maxi 결정 (2026-06-10) — 옵션 A**. 백엔드 엔드포인트 `GET /api/v1/auth/account/linkable-providers`(인증, security-engineer) 추가. LDAP(UUID+displayName)+SAML/OIDC(registrationId+displayName+type) 통합 목록. D6 = 프론트 + 백엔드 view-layer 엔드포인트 1개. **same-BC view layer 예외**(learnings 2026-05-22 — frontend PR에서 same BC backend view layer patch 자연스러움). 단일 "계정 추가" 피커로 모든 provider 타입 커버.

- **작업 구성 확정**. 백엔드 1 task(security-engineer, linkable-providers 엔드포인트) + 프론트 다수(frontend-engineer, 페이지/api/hooks/MSW/i18n) + E2E(qa-engineer, Playwright). 한 PR(identity-access BC view layer + 그 프론트 소비자).
- **응답 형태(결정)**. `{ linkable: [{ kind:"LDAP", providerId:UUID, displayName } | { kind:"SAML"|"OIDC", registrationId, displayName }] }`. enabled provider만. spec 단계에서 정확 필드 확정.
