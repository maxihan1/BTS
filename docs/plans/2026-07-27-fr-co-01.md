### 착수 전 실측 (2026-07-27, 코드 직접 확인)

**댓글 백엔드는 Import 의 부산물이며 쓰기 REST 노출이 0 이다.**

| 계층 | 파일 | 실제 |
|---|---|---|
| DB | `V035__comments.sql` | 있음 (`deleted_at` 소프트삭제 컬럼 포함) |
| 도메인 | `comment/domain/Comment.kt` | 전 필드 `val` — 본문 수정 메서드 없음 |
| 저장소 | `comment/repository/CommentRepository.kt` | `insert` · `listByIssue` **2개뿐** (update/delete 없음) |
| 서비스 | `comment/application/CommentApplicationService.kt` | `create()`(:78) · `list()`(:138). 수정·삭제 메서드 없음 |
| **컨트롤러** | `comment/web/CommentController.kt` | **`@GetMapping` 1개뿐.** 패키지 전체에서 POST/PATCH/DELETE **0건** |
| 프론트 | `apps/web/src` | `api/comments.ts` 없음 · `/comments` 호출 grep **0건** · MSW 핸들러 0건 |

`create()` 의 프로덕션 호출자 — **REST 가 아닌 내부 경로 2개**.
1. `IssueImportAdapter.kt:729` — Import 시 원본 작성자·작성시각 보존 (FR-IM-01 PR3, #224)
2. `AutomationIssueMutationAdapter.kt:144` — 자동화 규칙 "댓글 추가" 액션 (FR-AT-02)

### 🔴 이 작업의 가장 큰 함정 — 알림이 자동으로 켜진다

`CommentApplicationService.create()` 는 **이미 `IssueCommented` 를 발행한다**(`:102-110`,
`Propagation.MANDATORY` 같은 트랜잭션). 따라서 POST 를 노출하는 순간 사람이 만든 댓글이
`issue.commented` 이벤트를 타고 **인앱 알림 경로를 활성화**한다.

사전 시드가 이미 존재한다 — 새로 만드는 게 아니라 **잠자던 것이 깨어난다**.
- `NotificationEventType.ISSUE_COMMENTED("issue.commented")` (notification BC)
- automation `COMMENTED` 트리거 — `V300__automation_rules.sql` CHECK 제약
- `GadgetType.COMMENTS_RECENT` — 카탈로그에 있으나 `enabled = false`, 데이터 조회 구현 0

→ **"순수 추가라 무해" 전제 금지.** 메모리 `preseeded-event-producer-activates-notifications`.
알림 수신자 규칙(REPORTER/ASSIGNEE/WATCHER, 작성자 제외)이 실제로 발화하는지 스펙에서 명시하고
검증 대상으로 잡아야 한다.
