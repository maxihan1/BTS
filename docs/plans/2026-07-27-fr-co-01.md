`create()` 의 프로덕션 호출자 — **REST 가 아닌 내부 경로 2개**.
1. `IssueImportAdapter.kt:729` — Import 시 원본 작성자·작성시각 보존 (FR-IM-01 PR3, #224)
2. `AutomationIssueMutationAdapter.kt:144` — 자동화 규칙 "댓글 추가" 액션 (FR-AT-02)

### 🔴 이 작업의 가장 큰 함정 — 알림 경로는 이미 살아 있고, 사람이 두 번째 생산자가 된다

> **정정 (2026-07-27).** 이 절의 초안은 "POST 노출이 잠자던 알림을 깨운다" 였다. **실측으로 기각.**
> 경로는 **이미 프로덕션에서 발화 중**이다. 정확한 위험은 "활성화" 가 아니라 **"기존 소비자에게
> 사람 저작(human-authored) 이라는 새 입력 분포가 유입된다"** 는 것이다.

`CommentApplicationService.create()` 는 **이미 `IssueCommented` 를 발행한다**
(`:102-110`, `Propagation.MANDATORY` 같은 트랜잭션).

**이미 살아 있음의 근거 3축 (실측).**

| 축 | 근거 |
|---|---|
| 정책 시드 | `V401__seed_default_policies.sql:24-26` — `issue.commented` × REPORTER/ASSIGNEE/WATCHER × `IN_APP` × **`enabled=TRUE`** |
| 프로덕션 생산자 | `ActionExecutor.kt:233-236` `AddCommentAction` → `issueMutationPort.addComment()` → `AutomationIssueMutationAdapter:144` → `create()`. automation FR-AT-02 완결 = **도달 가능** |
| 소비자 | `NotificationTitleBuilder.kt:31` — `"$issueRef 에 댓글이 작성되었습니다"` 문구 보유. notification 모듈에 `IssueCommentedNotificationIntegrationTest` 존재 |

**위험 범위는 인앱 한정.** `NotificationEventType.ISSUE_COMMENTED("issue.commented", publishable = **false**)`
— `publishable=false` 는 외부 웹훅·이메일 채널 **불가**, 내부 인앱 채널 전용이라는 뜻이다(enum KDoc).
따라서 사외 유출·메일 폭주 종류의 위험은 구조적으로 없다.

**그래서 스펙에서 확정·검증해야 하는 것.**
1. **작성자 제외가 사람 저작에서도 성립하는가.** automation 경로는 `actor = 룰 actor` 였다. 사람 경로는
   `actor = 작성자` 이므로 "작성자 제외" 규칙이 처음으로 **실제 의미를 갖는다** — 자기 댓글에 자기가
   알림받는 회귀가 여기서 처음 드러날 수 있다.
2. **REPORTER/ASSIGNEE/WATCHER 3역할 fanout 이 실제 발화하는지** 통합 테스트로 고정.
3. `create()` 의 `authorId` 파라미터는 Import 용으로 `actor` 와 분리돼 있다. **사람 경로에서는
   `authorId == actor` 강제**가 필요하다(임의 저작자 위조 차단) — 현재 서비스 시그니처는 이를 막지 않는다.

관련 메모리. `preseeded-event-producer-activates-notifications` ("무해" 전제 금지) — 결론은 유지되나
기전은 위와 같이 정정한다.

**부수 확인.** `GadgetType.COMMENTS_RECENT` 는 카탈로그에 있으나 `enabled = false` 이고 데이터 조회
구현이 0 이다. 이 PR 범위 밖(FR-DB-02 가 자기 FR 에서 해제).

### ★ grill 과정에서 발견한 구조 결함 (FR-CO-01 의 실질 과제)

`create()` 가 `authorId` 를 **호출자 지정**으로 열어두고 있다. 이대로 POST 를 노출하면
**남의 이름으로 댓글을 쓸 수 있는 표면**이 생긴다.

Worklog 는 이 문제를 **메서드 분리**로 해결했다.

| | Worklog | Comment (현재) | Comment (목표, D4) |
|---|---|---|---|
| 사람 경로 | `create()` — `authorId = actor.value` 강제 (`:120`) | `create(…, authorId, createdAt)` | `create(actor, issueKey, body)` — 강제 |
| Import 경로 | `createImported(…, authorId, …)` (`:178`) | 같은 `create()` 재사용 | `createImported(…)` 분리 |

**리팩토링이 아니라 보안 요구다.** 파라미터를 열어둔 채 노출하면 컨트롤러의 성실성에만 의존하게
되고 그 의존은 테스트로 고정되지 않는다.

### FR-CO-02 에 선례가 예고하는 것 (이 PR 범위 밖)
