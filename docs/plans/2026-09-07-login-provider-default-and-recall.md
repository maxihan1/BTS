# 로그인 방식 기본값을 Local 로 · 마지막 성공 방식을 기억한다

> 티어: T2 · type: auth · BC = 없음(`apps/web` 전용) · 마이그레이션 0건 · 신규 의존성 0
> FR — FR-AU-01(로그인) · FR-AU-06(다중 provider) · FR-PF-01(개인 환경설정 관례 승계)

## 왜 T2 인가

`apps/web/src/auth/**` 가 `surfaces.ts` 의 `SEC_FE` 다. 로그인 폼의 **제출 값 하나**를 저장소에서
읽어 채우는 변경이므로 보안 렌즈를 생략할 수 없다 — 아래 §보안 렌즈.

## Maxi 지시 (2026-09-07)

> 「로그인 페이지 로그인방식 디폴트를 Local 을 디폴트로 설정 해주고 로컬 스토리지로 저장해서
> 다음 로그인시 불러오도록 해줘」

## Jira 대조

**대응 없음 — ADS `Select` 준용.**

Jira Cloud 의 로그인은 **Atlassian 계정 하나**로 들어간다. 로그인 화면에 「로그인 방식」을 고르는
드롭다운이 없고, SSO 라우팅은 이메일 도메인으로 서버가 정한다. 즉 이 PR 이 고치는 컨트롤에
대응하는 Jira 화면이 **존재하지 않는다.** 계약 §1-5 가 그 경우를 위해 둔 경로를 따른다 —
Jira 를 흉내내지 않고 ADS 패턴을 준용한다.

| 항목 | 판정 | 근거 |
|---|---|---|
| 로그인 방식 선택 컨트롤 | **대응 없음** — Jira Cloud 는 단일 Atlassian 계정이라 이 컨트롤이 없다 | 조회 2026-09-07 |
| 준용 패턴 | ADS [`Select`](https://atlassian.design/components/select/usage) — "Select allows users to make a single selection or multiple selections from a list of options" | 조회 2026-09-07 |

⚠️ **ADS 문서가 「기본값을 무엇으로 두라」까지 적지는 않는다** (같은 날 조회 — Select 문서는 컴포넌트
개요와 선택 동작까지다). 그래서 기본값을 `local` 로 정한 근거는 ADS 가 아니라 **Maxi 지시**이고,
그 사실을 여기 그대로 적는다. 「ADS 가 그렇게 하라고 했다」는 하지 않은 주장이 되지 않게 한다
(선례 = `2026-09-07-jira-parity-project-header-and-scoped-tabs.md` 의 편차 X-J5-15 와 같은 분리).

### 의도적 편차

- **X-LP-1 — 「기억」의 범위를 방식 하나로 좁힌다.** 사용자명 기억(`remember me`)은 이 PR 밖이다.
  요구는 「로그인 방식」이었고, 사용자명은 자격 증명에 가까워 보안 판단이 별도로 필요하다.
- **X-LP-2 — 로그아웃이 저장값을 지우지 않는다.** 지우면 「다음 로그인시 불러온다」가 성립하지
  않는다. provider id 는 자격 증명이 아니므로 세션 수명과 묶지 않는다(계획 §보안 렌즈 S5).

## 지금 동작

`LoginCredentialsForm` 의 기본값은 `providers[0]?.id` 다 — 서버가 `priority` 순으로 주는 목록의
**첫 원소**. 그래서 조직에 LDAP 이 우선순위 0 으로 등록되면 Local 계정 사용자가 매번 드롭다운을
바꿔야 하고, 그 선택은 새로고침하면 사라진다.

## 해소 — 3단 해소 + 성공 시 저장

`src/lib/active-project.ts` 의 4단 해소를 **그대로 승계한다.** 같은 저장소 안에 같은 모양의
문제가 이미 풀려 있고, 그 파일의 판단(저장값은 목록 대조를 거친다 · 출처를 함께 돌려준다)이
여기서도 그대로 옳다.

```
① 저장값이 현재 목록에 실재하면 그것      → source 'stored'
② 목록에 `local` 이 있으면 그것            → source 'local'   ← Maxi 지시의 기본값
③ 목록의 첫 원소                           → source 'first'
④ 목록이 비면 ''                           → source 'none'
```

**저장은 로그인이 실제로 성공했을 때만 한다.** 선택이 바뀔 때마다 쓰면 사용자가 눌러 보다 만
방식이 기억되고, 다음 방문에 **틀린 기본값**을 받는다. MFA 챌린지(`mfa_required`)도 자격 증명이
받아들여진 것이므로 성공으로 친다 — 거기서 안 쓰면 2FA 사용자만 기억이 안 된다.

**출처가 `stored` 면 다시 쓰지 않는다** (`active-project.ts` E7 과 같은 판단). 값이 같은데
매 로그인마다 write 를 한 번 더 하는 것은 이득이 없다.

## 보안 렌즈 (T2 필수)

| # | 물음 | 판정 |
|---|---|---|
| S1 | 무엇이 저장되나 | **provider id 문자열 하나**(`local`·`ldap`). 사용자명·비밀번호·토큰은 **저장하지 않는다** — 이 PR 은 그 필드들을 읽지도 않는다 |
| S2 | 저장값을 신뢰하나 | **아니다.** localStorage 는 같은 오리진의 스크립트가 쓸 수 있다(XSS 시 공격자 통제). 그래서 저장값은 **서버가 준 provider 목록과 대조**해서 실재할 때만 쓴다. 대조에 떨어지면 ②로 내려간다 |
| S3 | 왜 대조가 필요한가 | 대조가 없으면 임의 문자열이 `provider` 필드로 제출된다. 서버가 거부하겠지만, **폼이 모르는 값을 보내는 상태**를 만들 이유가 없다. 입구에서 막는다 |
| S4 | 정보 노출 | 「이 브라우저 사용자는 사내 LDAP 을 쓴다」가 로컬에 남는다. 기기 접근자에게만 보이고 자격 증명이 아니다 — 「로그인 방식 기억」의 통상 범위다. 공유 PC 우려는 로그아웃이 아니라 **브라우저 프로필** 문제이고, 같은 저장소가 이미 테마·활성 프로젝트를 같은 방식으로 남긴다 |
| S5 | 로그아웃 시 지우나 | **지우지 않는다.** 지우면 기능 자체가 없어진다(다음 로그인에 불러오는 것이 요구사항). 자격 증명이 아니므로 세션 수명과 묶을 이유가 없다 |

## 컨텍스트 노트

### D1 — 저장 시점을 「선택 변경」이 아니라 「로그인 성공」으로 (2026-09-07)
선택 변경에 쓰면 드롭다운을 열어 훑어본 것만으로 기본값이 바뀐다. 사용자는 자기가 **성공했던**
방식을 기대하지, 마지막으로 **쳐다본** 방식을 기대하지 않는다.

### D2 — 저장값을 목록과 대조한다 (2026-09-07)
`active-project.ts` 가 같은 이유로 이미 그렇게 한다(S6/E3 자가 치유). provider 는 조직 설정이
바뀌면 사라질 수 있고, 사라진 값을 그대로 채우면 드롭다운이 **빈 값**으로 뜬다.
보안 근거는 위 S2·S3.

### D3 — 배포를 막던 flake 를 같은 PR 에서 고쳤다 (2026-09-07)
`use-workflow-scheme-assignment.test.tsx` 의 「배정 후보 캐시에서 정합한 낙관값」이 낙관값을
관측하려고 PUT 을 50ms 붙잡은 채 끝나, 전역 미결 mutation 가드에 teardown 에서 걸렸다.
**단독 실행은 통과한다** — 워커에 여유가 있어 스스로 정착하기 때문이다. 전량 병렬에서만 red 가
되는 flake 였고, 실제로 이날 프로덕션 배포를 프론트 게이트에서 **한 번 중단시켰다.**
처방은 가드의 오류 메시지가 이미 적고 있던 `await settlePendingMutations()` 한 줄이다.

**왜 이 PR 에 넣었나.** 범위 밖이지만, 이 결함이 살아 있는 한 **어떤 배포도 무작위로 막힌다.**
별건으로 미루면 다음 배포에서 같은 자리를 다시 만난다.

### D4 — 200줄 래칫이 또 한 번 쪼개게 했다 (2026-09-07)
저장 판단을 `onSuccess` 안에 두자 `LoginCredentialsForm` 이 201줄이 됐다. 주석을 지우는 대신
`rememberLoginProvider()` 로 뺐고, 그 함수의 KDoc 이 「왜 `mfa_required` 보다 위에 두는가」를
호출부보다 잘 설명하게 됐다. 앞선 PR 의 D4 와 같은 패턴이다.
