## 사용자 시나리오 (Given-When-Then)

**S1. 관리자가 전역 알림 정책 목록을 본다**
- Given SYSTEM_ADMIN으로 로그인, When `/admin/notification-policies` 진입, Then 현재 전역 정책 목록(이벤트·수신자·채널·활성여부)이 테이블로 표시된다.

**S2. 관리자가 새 정책을 생성한다**
- Given 정책 페이지, When 이벤트/수신자/채널을 선택하고 "추가"를 누르면, Then POST → 201 → 목록에 새 행이 나타난다.
- 동일 조합이 이미 있으면 409 → "동일한 조합의 알림 정책이 이미 존재합니다." 표시.

**S3. 관리자가 정책을 활성/비활성 토글한다**
- Given 목록의 한 행, When 활성 스위치를 토글하면, Then PATCH → 204 → 행 상태가 갱신된다.

**S4. 관리자가 정책을 삭제한다**
- Given 목록의 한 행, When "삭제"를 누르고 인라인 확인하면, Then DELETE → 204 → 행이 사라진다.

**S5. 비-관리자 차단**
- Given 일반 사용자, When `/admin/notification-policies` 진입 시도, Then requireSystemAdmin 가드가 차단(리다이렉트). Header 관리 nav에 링크 미표시.

**S6. (범위 결정에 따라) 프로젝트 범위 정책 관리** — §결정 D1 참조.

- **FR-7** 컴포넌트: `NotificationPolicyTable`(목록+토글+삭제) + `NotificationPolicyForm`(생성). 200줄 제약 시 분리.

## 비기능 요구사항 (NFR)

- TypeScript strict, 200줄/컴포넌트, i18n 정본 셀렉터(E2E hardcoded 문자열 금지).
- CSRF: 변이 3종은 `X-XSRF-TOKEN: readXsrfToken()` 헤더 필수(GET 불요). mfa.ts 선례.
- 인증 전 401 자동 refresh 이슈 없음(이 페이지는 세션 후 admin 전용) → 일반 `apiFetch` 사용 가능.

## 엣지 케이스

- **E1 조합 수정 불가**: PATCH는 enabled만. event/role/channel 변경은 삭제+재생성 (UI는 inline edit 폼 없음 — 토글/삭제/생성만). 백엔드 강제.
- **E2 중복 생성(409)**: 폼 제출 시 NOTIF_POLICY_DUPLICATE → 폼 에러 메시지.
- **E3 빈 목록**: 해당 범위 정책 0건 → "정책이 없습니다" 빈 상태.
- **E4 미지 enum 값**: 목록 응답의 eventType 등이 라벨 미정의면 원문 그대로 표시(audit-log 전방호환 선례, eventType은 z.string()).
- **E5 projectKey null 직렬화**: 응답에서 전역이면 키 생략(NON_NULL) → Zod `.nullish()`.
- **E6 권한 상실 중 조작**: 토글/삭제 중 403 → 에러 토스트/메시지, 목록 invalidate.
