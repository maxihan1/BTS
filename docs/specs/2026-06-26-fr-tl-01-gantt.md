## 새 용어 (Maxi 승인 대기)

**타임라인 아이템 (TimelineItem)** — 타임라인(Gantt) 위에 막대 하나로 표현되는 단위. 이슈 1개에 대응하며, `start_date`~`due_date` 기간을 가진다. 두 날짜 중 하나라도 있어야 타임라인에 올라간다(둘 다 없으면 시간 축 정박점이 없어 제외). Epic 은 부모 그룹, Story/Task 는 `epicKey` 로 자식 연결.

## 사용자 시나리오 (Given-When-Then)

### S1. 프로젝트 타임라인 조회 (happy path)
- **Given** 프로젝트 ATLAS 에 BROWSE 권한이 있는 사용자
- **And** ATLAS 에 시작일/마감일이 설정된 가시 이슈 여러 건 존재
- **When** `GET /api/v1/timeline?project=ATLAS` 호출
- **Then** 200 + 날짜가 있는 가시 이슈 목록(타임라인 아이템)을 반환한다.

### S2. 날짜 없는 이슈 제외
- **Given** ATLAS 에 start_date / due_date 둘 다 NULL 인 이슈 존재
- **When** 타임라인 조회
- **Then** 해당 이슈는 결과에 포함되지 않는다(시간 축 정박점 없음).

### S3. 한쪽 날짜만 있는 이슈 포함
- **Given** start_date 만 있고 due_date 는 NULL 인 이슈 (또는 그 반대)
- **When** 타임라인 조회
- **Then** 해당 이슈는 결과에 포함되고, 누락된 날짜는 `null` 로 반환한다(막대 렌더 방식은 프론트 책임).

### S4. 비가시 이슈 누출 차단
- **Given** viewer 가 볼 수 없는 보안 등급 이슈가 ATLAS 에 존재(날짜 있음)
- **When** 타임라인 조회
- **Then** 해당 이슈는 결과에서 SQL 수준으로 제외된다.

### S5. 권한 없는 접근 거부
- **Given** ATLAS 에 BROWSE 권한이 없는 인증 사용자
- **When** 타임라인 조회
- **Then** 403 Forbidden.

### S6. 미인증 접근 거부
- **Given** 미인증/익명 요청
- **When** 타임라인 조회
- **Then** 401 Unauthorized (리소스 조회 이전에 차단 — 존재 probe 방지).

### S7. project 파라미터 누락
- **When** `GET /api/v1/timeline` (project 없음)
- **Then** 400 Bad Request.

### S8. 결과 상한 초과 (truncated)
- **Given** 날짜 있는 가시 이슈가 TIMELINE_FETCH_LIMIT(500) 을 초과
- **When** 타임라인 조회
- **Then** 최대 500건 반환 + `truncated: true`.

## 기능 요구사항 (FR)

- **FR1**. `GET /api/v1/timeline?project={projectKey}` 는 프로젝트의 "타임라인 아이템" 목록을 반환한다.
- **FR2**. 타임라인 아이템 = `start_date` 또는 `due_date` 중 하나 이상이 NOT NULL 인 가시·미삭제 이슈.
- **FR3**. 각 아이템은 다음 필드를 포함한다 — `key`, `summary`, `issueType`, `currentStateKey`, `assigneeId`(nullable), `startDate`(nullable), `dueDate`(nullable), `epicKey`(nullable).
- **FR4**. 응답 정렬 — `startDate` ASC NULLS LAST → `dueDate` ASC NULLS LAST → `key` ASC.
- **FR5**. BROWSE 권한이 없으면 403, 미인증이면 401, project 누락이면 400.
- **FR6**. viewer 가 볼 수 없는 보안 등급 이슈는 결과에서 제외(SQL 푸시다운, 보드 adapter 와 동일 2단 게이트).
- **FR7**. 결과는 TIMELINE_FETCH_LIMIT(500) 으로 상한. 초과 시 `truncated: true`.
- **FR8**. cross-BC 통신은 shared-kernel 포트만 사용(BC 격리). agile-planning 은 issue-tracking 을 직접 의존하지 않는다.

## 비기능 요구사항 (NFR)

- **NFR1 (성능)**. 타임라인 500건 조회 p95 < 2s (product §4.1 NFR). cross-BC 호출 1회 + 권한 판정 1회, N+1 없음.
- **NFR2 (보안)**. 보안 등급 필터는 adapter 가 SQL 수준에서 적용. agile-planning 은 필터 여부를 알지 못한다.
- **NFR3 (격리)**. ArchUnit BC 격리 룰 유지(agile-planning → issue-tracking 직접 import 0).

## API 인터페이스 (REST)

```
GET /api/v1/timeline?project={projectKey}
권한: BROWSE (해당 프로젝트)
```

성공 200.
```json
{
  "data": {
    "items": [
      {
        "key": "ATLAS-12",
        "summary": "결제 모듈 리팩토링",
        "issueType": "story",
        "currentStateKey": "in_progress",
        "assigneeId": "0a8d...uuid",
        "startDate": "2026-06-01",
        "dueDate": "2026-06-20",
        "epicKey": "ATLAS-1"
      }
    ],
    "truncated": false
  }
}
```

에러.
- 400 — `project` 쿼리 파라미터 누락.
- 401 — 미인증/익명.
- 403 — BROWSE 권한 미충족.

## cross-BC 설계 (핵심 결정)

### 결정 D1 — 전용 `TimelineLookupPort` 신설 (vs `BoardIssueView` 확장)

- shared-kernel 에 `TimelineLookupPort` + `TimelineItemView` + `TimelineItemPage` 신설.
- issue-tracking 에 `TimelineLookupAdapter` (`BoardIssueLookupAdapter` 형제) 구현.
- **사유**. 타임라인은 날짜·issueType 필드가 필요하고 fetch limit(500)·필터 조건(날짜 NOT NULL)이 보드와 다르다. `BoardIssueView` 에 타임라인 전용 필드를 섞으면 책임 오염. 전용 포트가 단일 책임·독립 limit 에 부합.
- **대안(기각)**. `BoardIssueView` 에 startDate/dueDate/issueType 추가 — rank/epicKey 확장 선례는 있으나, 보드 카드와 타임라인은 limit·필터 의미가 달라 한 뷰로 묶으면 의미 모호.
- **fail-safe default**. 포트 default 메서드는 빈 페이지 반환(adapter 미등록 환경 안전). 조회는 보안 판정이 아니므로 fail-safe 방향(보드 포트와 동일).

### 결정 D2 — visibility 보안 경로 재사용

- adapter 는 `IssueSecurityDirectory.accessibleLevels(viewer, project)` + 신규 `IssueRepository.listVisibleForTimeline(...)` SQL 푸시다운으로 비가시 행 제외. 보드 adapter 와 **동일 2단 게이트** 재사용(새 보안 판정 경로 신설 금지, FR-NT-03 BLOCKER 재발 방지).
- WHERE 술어. `project = ? AND deleted_at IS NULL AND (start_date IS NOT NULL OR due_date IS NOT NULL) AND <보안등급 IN access>`. LIMIT 501 로 truncated 판정.

### 결정 D3 — 평면 목록 반환 (트리 조립은 프론트)

- 백엔드는 타임라인 아이템 평면 목록 + 각 아이템의 `epicKey` 만 반환.
- Epic 부모 라인 / 자식 라인 **시각적 그룹핑은 프론트(D6) 책임**.
- **사유**. 그룹핑은 표현 계층 관심사. 데이터 API 는 평면 목록이 단순·테스트 용이. epicKey 로 프론트가 트리 조립 가능. epic 자신도 날짜 있으면 목록에 포함됨.

## 엣지 케이스

- **EC1**. start/due 둘 다 NULL → 제외 (S2).
- **EC2**. 한쪽만 NULL → 포함, null 그대로 반환 (S3).
- **EC3**. epicKey 가 cross-project epic → null (보드 adapter 의 P1-A 누출 방지 동일 정책).
- **EC4**. 가시 이슈 0건 → `items: [], truncated: false` (빈 200).
- **EC5**. 존재하지 않는 projectKey → BROWSE 판정에서 권한 없음 → 403 (존재 여부 노출 안 함, 백로그와 동일).
- **EC6**. 결과 정확히 500건 → truncated false. 501건째 존재 → 500건 + truncated true.
- **EC7**. soft-deleted 이슈 → 제외.

## 제약 조건

- BC 격리 — agile-planning 은 shared-kernel 포트만 의존. issue-tracking 직접 import 금지(ArchUnit).
- 읽기 전용 — `@Transactional(readOnly = true)`. 부수 효과 0.
- actor 추출 → 권한 판정 → 조회 순서(미인증 존재 probe 차단, memory: auth-extraction-before-resource-lookup).
