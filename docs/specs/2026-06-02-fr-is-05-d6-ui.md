## 결정 사항 (Maxi 확정 2026-06-02)

- **D1 전환 대상 선택** = 선택 이슈들의 가용 전환 **교집합만** 노출. (전체 상태 목록 아님)
- **D2 선택 범위** = **페이지 교차 누적**. 페이지 이동해도 선택 유지.
- **D3 결과 표시** = **토스트(접수 알림) + 별도 결과 패널**(폴링으로 진행률/결과).

## 사용자 시나리오 (Given-When-Then)

### S1. 일괄 편집(BULK_EDIT) happy path
- **Given** 이슈 목록에서 사용자가 체크박스로 이슈 3건을 선택했다.
- **When** 액션 바의 "일괄 편집"을 눌러 우선순위=2(High)로 설정하고 적용한다.
- **Then** `POST /api/v1/issues/bulk-update`(operationType=BULK_EDIT, editPayload={priority:2,impact:null})가 202를 반환하고, "일괄 작업이 접수되었습니다" 토스트가 뜬다. 결과 패널이 열려 진행률을 폴링하며, 완료 시 성공 3 / 실패 0을 표시한다.

### S2. 일괄 상태 전환(BULK_TRANSITION) — 교집합
- **Given** 사용자가 상태가 제각각인 이슈 4건을 선택했다.
- **When** "일괄 전환"를 누르면 4건 각각의 가용 전환을 조회해 **교집합**을 드롭다운으로 보여준다.
- **Then** 사용자가 교집합 중 하나(예: "완료로")를 선택하고 적용하면 `POST bulk-update`(operationType=BULK_TRANSITION, transitionPayload={toStateKey})가 202를 반환한다. 결과 패널이 진행률을 폴링한다.

### S3. 교집합이 비어 있음
- **Given** 선택 이슈들의 가용 전환 교집합이 0건이다.
- **When** "일괄 전환"를 누른다.
- **Then** "선택한 이슈들이 공통으로 이동할 수 있는 상태가 없습니다" 안내를 표시하고 적용 버튼을 비활성화한다.

### S4. 부분 실패
- **Given** 일괄 전환 접수가 완료됐고 일부 이슈가 실패했다(예: VERSION_CONFLICT).
- **When** 결과 패널 폴링이 종단 상태(COMPLETED)에 도달한다.
- **Then** 성공/실패 카운트와 함께 실패한 이슈별 `issueKey` + 사유(`failureReasonCode`를 한국어로 매핑)를 목록으로 보여준다.

### S5. 페이지 교차 선택
- **Given** 사용자가 1페이지에서 2건, 2페이지로 이동해 1건을 추가 선택했다.
- **When** 액션 바를 본다.
- **Then** "총 3건 선택됨"이 유지되고, 적용 시 3건 모두 issueKeys에 포함된다.

## 기능 요구사항 (FR)

- **FR1** 이슈 목록의 각 항목에 체크박스. 선택 상태는 **라우트 레벨**에서 issueKey Set으로 관리(페이지 교차 누적).
- **FR2** "전체 선택"(현재 페이지) 체크박스. 현재 페이지 항목만 토글.
- **FR3** 1건 이상 선택 시 액션 바 노출: 선택 수, "일괄 편집", "일괄 전환", "선택 해제".
- **FR4** 일괄 편집 폼: priority(1~5, null=무변경), impact(1~3, null=무변경). merge-patch 시맨틱 — 건드리지 않은 필드는 보내지 않음/null.
- **FR5** 일괄 전환 폼: 선택 이슈들의 가용 전환 **교집합**을 `fetchIssueTransitions(key)` N회 조회 후 계산해 드롭다운 노출. 교집합 0건이면 안내 + 비활성화(S3).
- **FR6** 접수 성공(202) 시 토스트 + 결과 패널 오픈. 결과 패널은 `GET /api/v1/bulk-operations/{id}`를 폴링.
- **FR7** 폴링은 status가 종단(COMPLETED/FAILED) 도달 시 중지. 진행률 = processedCount/totalCount.
- **FR8** 결과 패널: 총/성공/실패 카운트 + 실패 항목(issueKey + 사유 한국어). 적용 후 목록 invalidate(refetch)로 최신화 + 선택 해제.
- **FR9** 에러(400/403/404/500 ProblemDetail) 시 errorCode 기반 한국어 메시지 + 토스트.

## 비기능 요구사항 (NFR)

- **NFR1** TypeScript strict. Zod 스키마는 백엔드 DTO와 1:1 (payload는 operationType 분기 union, 내부 discriminator 없음).
- **NFR2** 폴링 주기 기본 1.5s, 종단 도달 또는 패널 닫힘 시 중지(누수 방지). TanStack Query `refetchInterval` 사용.
- **NFR3** 접근성 — 체크박스 aria-label, 결과 패널 role, 진행률 aria-live. WCAG AA.
- **NFR4** 단위 테스트 + 기존 이슈 목록 E2E 회귀 동시 검증(메모리: UI PR이 E2E 미루면 회귀 잠복). 텍스트 중복 버튼은 컨테이너/testid 한정.
- **NFR5** `tsc -p tsconfig.app.json` typecheck 동반(vitest는 타입 미검증, 메모리: Zod mock 파급).

## API 인터페이스 (프론트가 소비)

| 용도 | 메서드/경로 | 비고 |
|---|---|---|
| 접수 | `POST /api/v1/issues/bulk-update` | 202 `{data:{bulkOperationId,status:"PENDING",totalCount}}` |
| 조회(폴링) | `GET /api/v1/bulk-operations/{id}` | 200 `{data: BulkOperationResponse}` |
| 전환 교집합 | `GET /api/v1/issues/{key}/transitions` | 기존 `fetchIssueTransitions`, N회 호출 |

요청/응답/enum/에러코드 전체는 plan §도메인 정리 참조.

## 엣지 케이스

- **EC1** 선택 0건 → 액션 바 숨김.
- **EC2** 일괄 편집에서 priority/impact 둘 다 무변경(빈 폼) → 적용 비활성화(보낼 게 없음).
- **EC3** 전환 교집합 0건 → S3.
- **EC4** 폴링 중 GET 403/404 → 에러 표시 + 폴링 중지.
- **EC5** 접수 400(issueKeys 1000 초과 등) → 토스트로 사유.
- **EC6** 선택한 이슈가 다른 페이지에서 삭제/이동된 경우 → 접수는 그대로 진행, 백엔드가 NOT_FOUND로 실패 처리(best-effort).
- **EC7** transitions N회 조회 중 일부 실패 → 해당 이슈를 교집합 계산에서 보수적으로 제외할지/에러로 막을지: 보수적으로 "조회 실패 이슈 있음" 경고 후 성공분만 교집합(적용은 허용).
- **EC8** payload 직렬화 — BULK_EDIT는 editPayload만, BULK_TRANSITION은 transitionPayload만 채워 전송(operationType↔payload 일치, 불일치 시 백엔드 400).

## 제약 조건

- 인증 미연동(백엔드 SYSTEM_ACTOR 하드코딩) → E2E(D7)는 MSW mock 기반. fixture userId 정합 주의(메모리).
- BC 격리 — issue-tracking same-BC view layer 작업. 다른 BC 직접 import 금지.
- MSW mutation stateful refetch — POST/폴링 mock은 상태를 영속해 PENDING→RUNNING→COMPLETED 진행 시뮬레이션(D7).

## 측정 가능한 완료 기준

1. 이슈 목록에서 체크박스로 다중 선택(페이지 교차) 가능, 액션 바에 선택 수 표시.
2. 일괄 편집(priority/impact) 접수 → 토스트 → 결과 패널 진행률 → 성공/실패 표시.
3. 일괄 전환 교집합 노출, 교집합 0건 시 안내+비활성화, 접수→폴링→결과.
4. 부분 실패 시 실패 이슈별 사유(한국어) 표시.
5. 단위 테스트 통과 + 기존 이슈 목록 E2E 회귀 없음 + `tsc -p tsconfig.app.json` 통과.
