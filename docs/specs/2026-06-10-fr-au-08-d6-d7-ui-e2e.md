# FR-AU-08 D6/D7 — 계정 통합 프론트 UI + E2E — 스펙

> slug: fr-au-08-d6-d7-ui-e2e · type: ui · 생성: 2026-06-10
> 백엔드 완료. #103(LDAP 동기 연결)·#104(SSO 리다이렉트 연결). 본 작업 = D6(프론트 UI) + D7(E2E) + 백엔드 view-layer 엔드포인트 1개(linkable-providers, Maxi 옵션A).
> 대상 페이지. `/settings/account-links`.

## 배경 / 범위

로그인한 사용자가 자신의 외부 계정(LDAP/SAML/OIDC) 연결을 셀프서비스로 **조회·추가·해제**하고, 민감 동작 전 **재인증(step-up)** 한다. 백엔드 정책(ADR `account-linking-policy`·`sso-account-linking`)은 확정 — 명시적 수동 연결만, 타계정 선점 거부, 마지막 수단 해제 거부, 계정 열거 0.

**범위 안**. (1) 연결 목록 페이지 (2) LDAP 동기 연결(인라인 폼) (3) SSO 연결(리다이렉트 2단계) (4) 해제(확인) (5) step-up 재인증(LOCAL/LDAP 동기 모달 + SSO 리다이렉트) (6) SSO 콜백 복귀 쿼리 처리 (7) 백엔드 `linkable-providers` 엔드포인트 (8) Playwright E2E.

**범위 밖**. LOCAL 비밀번호 추가/제거(`/settings/password` 별도), 감사 로그(FR-AU-10), 리다이렉트를 가로지르는 "대기 동작 자동 재개"(콜백 후 사용자가 재클릭 — 본 라운드 비목표).

## 사용자 시나리오 (Given-When-Then)

- **S1 목록 조회**. Given 로그인 사용자. When `/settings/account-links` 진입. Then 연결된 외부 계정이 카드 목록으로 표시(provider 이름·타입 배지·마스킹된 외부 식별자·연결 시각·마지막 로그인). 비활성 provider 링크는 "비활성" 배지. 연결 0건이면 빈 상태 안내.

- **S2 LDAP 연결(step-up 보유)**. Given 유효 step-up 윈도우. When "계정 추가" → LDAP provider 선택 → username/password 입력 → 연결. Then 201/200 후 목록 갱신 + 성공 토스트. 이미 본인 소유면 멱등(200) "이미 연결됨" 안내.

- **S3 LDAP 연결(step-up 없음)**. Given step-up 윈도우 없음. When LDAP 연결 시도. Then 재인증 먼저 요구(모달) → 재인증 성공 후 연결 진행.

- **S4 SSO 연결**. Given 유효 step-up. When "계정 추가" → SAML/OIDC provider 선택 → 연결. Then `POST /links/sso/start`로 authorizeUrl 받아 `window.location.assign`(전체 페이지 이동) → IdP 인증 → 콜백 → `/settings/account-links?link=success` 복귀 → 성공 토스트 + 목록 갱신.

- **S5 해제**. Given 유효 step-up + 연결 2개 이상(또는 LOCAL 비번 보유). When 링크의 "해제" → 확인 다이얼로그 → 확인. Then 204 후 목록에서 제거 + 토스트.

- **S6 마지막 수단 해제 거부**. Given 로그인 수단이 그 링크 하나뿐(LOCAL 비번 없음, enabled 링크 1개). When 해제 시도. Then 409 `last_login_method` → "마지막 로그인 수단은 해제할 수 없습니다" 안내, 목록 불변.

- **S7 타계정 선점(SSO)**. Given 다른 사용자가 이미 그 외부 신원에 연결. When SSO 연결 콜백 복귀. Then `?link=conflict` → "이미 다른 계정에 연결된 신원입니다" 안내(어느 계정인지 비노출), 연결 0.

- **S8 SSO 재인증(SSO 전용 사용자)**. Given LOCAL 비번 없음 + LDAP 링크 없음(SSO 링크만). When 해제/연결로 step-up 필요. Then 동기 재인증 불가 → "SSO로 재인증" → `POST /reauth/sso/start` → 리다이렉트 → 콜백 `?reauth=success` → "재인증 완료, 작업을 다시 시도하세요" 안내(step-up 부여됨).

- **S9 PAT 차단**. Given PAT 인증(상호작용 로그인 아님). When 페이지 진입/동작. Then 403 `account_linking_requires_interactive_login` → "계정 연결은 상호작용 로그인 필요" 안내.

## 기능 요구사항 (FR)

- **FR1 목록**. `GET /api/v1/auth/account/links` 호출 → 카드 목록 렌더. `hasLocalPassword`는 해제 가능 판단·재인증 수단 선택에 사용. providerType 배지(LDAP/SAML/OIDC), `providerEnabled=false`면 비활성 배지. `lastLoginAt=null`이면 "로그인 기록 없음".
- **FR2 linkable-providers(백엔드 신규)**. `GET /api/v1/auth/account/linkable-providers` (JWT 전용, PAT→403) → enabled provider 통합 목록. "계정 추가" 피커가 소비.
- **FR3 LDAP 연결**. LDAP provider 선택 시 username/password 인라인 폼 → `POST /links {providerId, username, password}`. 201 신규/200 멱등 구분 안내. 401 `link_authentication_failed`·409 `account_already_linked`·503 `provider_unavailable` 분기 메시지.
- **FR4 SSO 연결**. SSO provider 선택 → `POST /links/sso/start {registrationId, providerType}` → 응답 `authorizeUrl`로 `window.location.assign`. (CSRF 토큰 동반, JSESSIONID는 백엔드가 세팅.)
- **FR5 해제**. "해제" → 확인 다이얼로그 → `DELETE /links/{id}`. 204 성공·409 `last_login_method`·404 미존재 분기.
- **FR6 step-up 게이팅**. 모든 mutating 동작(LDAP 연결/SSO 연결/해제)은 step-up 필요. 프론트는 (a) 마지막 재인증 응답의 `stepUpExpiresAt`로 사전 게이팅하고, (b) **403 `step_up_required`를 진실 출처로** 받아 재인증 흐름을 트리거(서버가 최종 판정). 둘 다 충족.
- **FR7 재인증(동기)**. step-up 필요 시 재인증 모달. 수단 선택은 보유 자격으로 결정 — `hasLocalPassword`면 LOCAL(비번), 아니고 LDAP 링크 있으면 LDAP(providerId/username/password). `POST /reauth` → 200 `{stepUpExpiresAt}` 저장 후 원 동작 재개. 400 `reauth_fields_required`·401 `reauth_failed` 분기.
- **FR8 재인증(SSO)**. 동기 자격 없음(SSO 전용)이면 "SSO로 재인증" → `POST /reauth/sso/start {registrationId, providerType}` → `authorizeUrl`로 리다이렉트. 콜백 `?reauth=success` 복귀 시 step-up 부여 완료 안내.
- **FR9 콜백 쿼리 처리**. 페이지 마운트 시 `?link=success|already_linked|conflict|error`·`?reauth=success|failed` 읽어 토스트/배너 표시 후 **쿼리 제거**(history.replace — 새로고침 재표시 방지). `?reauth=success`면 step-up이 막 부여됐음을 사용자에게 알림.
- **FR10 라우트**. `/settings/account-links` 등록(requireAuth). 백엔드 SSO 콜백 고정 복귀 경로와 일치(필수).

## 비기능 요구사항 (NFR)

- **NFR1 Zod↔DTO 1:1**. 모든 응답 스키마는 백엔드 DTO와 정확히 일치(필드 invent 금지, `frontend-zod-backend-dto-contract-gap`). `AccountLinkResponse`·`AccountLinksResponse`·`ReauthResponse`·`SsoLinkStartResponse`·linkable-providers 신규 DTO.
- **NFR2 CSRF**. mutation(`POST`/`DELETE`)은 `X-XSRF-TOKEN` 수동 동반(identity-access self-service 관례, `sessions.ts` 선례). JWT는 apiFetch가 Authorization 자동.
- **NFR3 PII**. 외부 식별자는 백엔드가 마스킹한 `externalSubjectMasked`만 표시. 프론트는 원본 추정/복원 금지.
- **NFR4 보안 메시지**. 계정 열거 0 — conflict/auth 실패 메시지는 "어느 계정/원인"인지 노출하지 않는 일반 문구.
- **NFR5 i18n**. 모든 사용자 노출 문자열은 기존 i18n 컨벤션 따름(하드코딩 금지, 기존 settings 페이지 관례 확인).
- **NFR6 접근성**. 다이얼로그/폼은 기존 shadcn/Radix 컴포넌트 + 라벨 연결. 위험 동작(해제)은 확인 다이얼로그.
- **NFR7 토스트/라우트 인프라(실측)**. 성공/에러 안내는 `sonner` `toast()`(`useRevokeSessionMutation` 선례). 라우트는 `staticData:{requireAuth:true}, beforeLoad: requireAuth`(settings.password 동형). null `providerName`/`providerType`은 "알 수 없는 provider" fallback.

## API 인터페이스

소비(기존, #103/#104). 도메인 정리 표 참조 — `GET /links`, `POST /reauth`, `POST /links`, `DELETE /links/{id}`, `POST /links/sso/start`, `POST /reauth/sso/start`. SSO 콜백 복귀 `/settings/account-links?link=…|?reauth=…`.

신규(백엔드, 본 PR). **`GET /api/v1/auth/account/linkable-providers`** (JWT 전용, PAT→403, 읽기전용·step-up 불요).
```
200 { linkable: [
  { kind: "LDAP", providerId: "<uuid>", displayName: string },
  { kind: "SAML", registrationId: string, displayName: string },
  { kind: "OIDC", registrationId: string, displayName: string }
] }
```
- LDAP — enabled LDAP `authn_providers` 행(id=UUID, displayName). SAML — `SamlIdpConfigRepository` enabled IdP(registrationId, displayName). OIDC — `OidcProviderConfigReader` enabled provider(registrationId, displayName).
- enabled provider 전체 반환(이미 연결된 것도 포함 — 중복 시도는 link 엔드포인트의 멱등/충돌 의미로 처리, 엔드포인트는 per-user 필터 없이 단순). 계정 열거 0 — 어차피 enabled 목록은 로그인 화면(`/providers`·`/saml/idps`·`/oidc/providers`)서도 노출되는 공개 정보.

## 엣지 케이스

- **EC1 빈 목록**. 연결 0건 → 빈 상태 + "계정 추가" CTA.
- **EC2 linkable 0건**. enabled provider 없음 → "추가 가능한 provider 없음" 안내, 추가 버튼 비활성.
- **EC3 step-up 만료 중간**. 사전 게이팅 통과했으나 동작 시 403 `step_up_required` → 재인증 흐름 트리거(FR6b).
- **EC4 SSO 콜백 에러**. `?link=error`(intent 불일치/만료) → "연결 세션이 만료되었습니다, 다시 시도" 안내.
- **EC5 503 provider 불가**. LDAP 연결 중 503 → "인증 서버 일시 불가" 안내(재시도 가능), 목록 불변.
- **EC6 마지막 수단 + SSO 전용**. SSO 링크 1개만(LOCAL 없음) → 그 링크 해제 시 409. UI는 시도 전 막지 않고 서버 판정 신뢰(409 안내).
- **EC7 새로고침 재표시 방지**. 콜백 쿼리 처리 후 즉시 `history.replaceState`로 쿼리 제거.
- **EC8 동시 mutation**. 진행 중 버튼 disabled(중복 클릭 방지), invalidate-only 재조회.
- **EC9 E2E SSO 왕복 불가(적대적 갭)**. Playwright+MSW는 진짜 SAML/OIDC IdP 왕복 불가 → S4는 (a) SSO 선택 시 `/links/sso/start` 호출+`window.location.assign` 시도 검증, (b) `/settings/account-links?link=success`로 **직접 진입**해 SPA 콜백 쿼리 처리(토스트+쿼리 제거) 검증으로 분리. 진짜 IdP 왕복은 비목표(백엔드 통합테스트도 동일 제외, `worktree-stale-base-rebase-and-e2e-msw-traps`).
- **EC10 재인증 providerId 출처**. LDAP 동기 재인증의 providerId는 사용자의 기존 LDAP 링크에서 취득(다건이면 첫 enabled LDAP 링크). LDAP 링크도 LOCAL 비번도 없으면 SSO 재인증만 가능(FR8).

## 제약 조건

- 백엔드 변경 = `linkable-providers` 엔드포인트 1개로 한정(same-BC view layer). 기존 6 엔드포인트·정책 무변경.
- 프론트 라우트 경로 `/settings/account-links` **고정**(백엔드 `SETTINGS_PATH` 일치 — 변경 시 SSO 플로우 단절).
- `window.location.assign`(전체 페이지 이동)은 SSO 연결/재인증에서만. 그 외는 SPA 내 TanStack Query.
- step-up 윈도우 TTL은 서버 소유(5분). 프론트는 `stepUpExpiresAt`를 신뢰하되 403을 최종 판정으로.

## Brainstorming Check

✅ 통과 (1회 iteration, 적대적 기술 갭 분석). 발견 3건 전부 스펙 반영(Maxi 결정 불요 — 기술 갭).
- **G1(최우선)** — E2E가 진짜 SSO IdP 왕복을 흉내 내려다 불가능/가짜그린 위험 → EC9로 분리(start 호출 + 콜백 쿼리 직접진입). 백엔드 통합테스트가 같은 이유로 왕복을 E2E에 위임한 선례와 일치.
- **G2** — step-up 사전게이팅(`stepUpExpiresAt`)과 403 진실출처의 관계 모호 → FR6에서 403을 최종 판정으로 명시(사전게이팅은 round-trip 절감 최적화). SSO 전용 사용자는 `?reauth=success` 후 재클릭 시 step-up 유효라 spurious 403 없음.
- **G3(마이너)** — 토스트=sonner 실측, null providerName fallback, 재인증 providerId 출처(기존 LDAP 링크), E2E CSRF 쿠키 수동시드 명시.
- **OK 확인** — 라우트 경로 백엔드 SETTINGS_PATH 일치(SSO 단절 차단), CSRF 수동 토큰, PII 마스킹 백엔드 위임, 계정 열거 0 메시지, linkable enabled 공개정보(열거 위험 0).
