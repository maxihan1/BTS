# FR-AC-01 D6/D7 — 첨부 프론트 UI + E2E 스펙

> slug: fr-ac-01-ui-e2e · type: ui · BC: issue-tracking · 작성: 2026-06-15
> 백엔드 D1~D5 완료(#145). 본 스펙은 D6(프론트 UI) + D7(E2E)만 다룬다.
> 기술 결정: 네이티브 HTML5 파일선택(의존성0) + 단순 로딩 상태(fetch) — Maxi 확정 2026-06-15.

## 사용자 시나리오 (Given-When-Then)

- **S1 업로드**. Given 이슈 상세 화면(UPDATE 권한 보유), When 첨부 영역에 파일을 드래그앤드롭 또는 클릭 선택, Then 서버로 multipart 업로드되고 목록에 새 첨부가 나타난다.
- **S2 목록**. Given 첨부가 있는 이슈, When 상세 화면 진입, Then 첨부 목록(파일명·크기·업로드 시각)이 표시된다.
- **S3 다운로드**. Given 첨부 목록, When 다운로드 버튼 클릭, Then 브라우저가 파일을 다운로드한다(Content-Disposition: attachment).
- **S4 삭제**. Given UPDATE 권한 보유, When 삭제 버튼 클릭 → 확인, Then 첨부가 하드삭제되고 목록에서 사라진다.
- **S5 권한 없음**. Given UPDATE 권한 미보유(읽기 전용 사용자), When 상세 진입, Then 업로드/삭제 UI는 비활성(미표시), 목록·다운로드는 가능.
- **S6 크기 초과**. Given 100MB 초과 파일, When 선택, Then 클라이언트가 사전 차단(토스트)하고 업로드하지 않는다.
- **S7 빈 상태**. Given 첨부 0개, When 진입, Then "첨부 없음" 빈 상태가 표시된다.

## 기능 요구사항 (FR)

- **FR-1**. 이슈 상세 화면 좌측 본문(IssueDescription) 하단에 "첨부" 섹션을 추가한다.
- **FR-2 업로드**. 네이티브 `<input type="file" multiple>` + 드롭존(drag/drop 이벤트). 선택/드롭한 파일을 각각 `POST /api/v1/issues/{key}/attachments`(multipart, part명 `file`)로 전송. 다중 선택 시 파일별 순차/병렬 업로드.
- **FR-3 목록**. 진입 시 `GET /api/v1/issues/{key}/attachments`로 목록 조회. 파일명·크기(KB/MB 포맷)·업로드 시각 표시. 다운로드/삭제 액션.
- **FR-4 다운로드**. `GET /api/v1/issues/{key}/attachments/{id}` → `res.blob()` → `triggerBlobDownload`(기존 `lib/download.ts` 재사용). 파일명은 응답 헤더 기준이나, 단순화를 위해 목록의 `filename` 사용.
- **FR-5 삭제**. `DELETE /api/v1/issues/{key}/attachments/{id}`. **하드삭제(복구 불가)이므로 확인 단계 필수**(인라인 확인 또는 다이얼로그).
- **FR-6 권한 게이팅**. 기존 `fetchIssuePermissions`의 `UPDATE` 플래그로 업로드 드롭존·삭제 버튼 게이팅. 목록/다운로드는 상세 진입(VIEW) 시 항상 노출.
- **FR-7 클라이언트 크기 검증**. 선택 파일 `size > 100MB(104857600)`면 업로드 전 차단 + 토스트. (백엔드 413 안전망 보존.)
- **FR-8 mutation 동기화**. 업로드/삭제 성공 시 첨부 목록 쿼리 invalidate(낙관적 업데이트보다 invalidate-only — 기존 BC 컨벤션).

## 비기능 요구사항 (NFR)

- **NFR-1 의존성 0**. react-dropzone 등 신규 외부 의존성 도입 금지(Maxi 확정). 네이티브 API만.
- **NFR-2 apiFetch FormData 지원**. `client.ts`의 `apiFetch`는 body가 있으면 무조건 `JSON.stringify` + `Content-Type: application/json`을 강제한다. **body가 `FormData`면 직렬화/Content-Type 자동설정을 건너뛰도록 확장**한다(브라우저가 multipart boundary 설정). 기존 JSON 호출 동작은 불변. 401 자동 refresh 인프라 재사용.
- **NFR-3 한글 파일명**. 백엔드가 RFC5987 UTF-8 Content-Disposition 처리. 프론트는 목록 `filename`(UTF-8) 그대로 표시/다운로드.
- **NFR-4 메모리 누수 방지**. 다운로드 Blob URL은 `triggerBlobDownload`의 `finally revokeObjectURL`로 해제(기존 헬퍼 보장).
- **NFR-5 i18n**. 모든 UI 문자열은 i18n 사전(`ko`)에 등록. 콜론 종결 금지(ko.test 자동검증).

## API 인터페이스 (REST) — 백엔드 #145 실측, 변경 없음

| 동작 | 메서드/경로 | 요청 | 응답 | 권한 |
|---|---|---|---|---|
| 업로드 | `POST /api/v1/issues/{key}/attachments` | multipart, part `file` | 201 `{data: AttachmentResponse}` + Location | UPDATE |
| 목록 | `GET /api/v1/issues/{key}/attachments` | — | 200 `{data: AttachmentResponse[]}` | VIEW |
| 다운로드 | `GET /api/v1/issues/{key}/attachments/{id}` | — | 200 바이트스트림(Content-Disposition: attachment) | VIEW |
| 삭제 | `DELETE /api/v1/issues/{key}/attachments/{id}` | — | 204 | UPDATE |

에러: 401(미인증) / 403(권한) / 404(이슈·첨부 없음) / 413(크기 초과).
`AttachmentResponse = { id: UUID, filename: string, contentType: string, sizeBytes: number, uploadedBy: UUID, createdAt: string }`.

## 엣지 케이스 (self-review 점검)

1. 100MB 초과 → 클라 사전 차단(FR-7) + 백엔드 413 안전망.
2. 빈 파일(0byte) → 백엔드 검증 위임(클라 차단 안 함).
3. 다중 업로드 일부 실패 → 파일별 결과 토스트(성공 N/실패 M).
4. 동일 파일명 중복 업로드 → 백엔드 UUID PK라 허용. 목록에 동명 2건 공존 정상.
5. 삭제 하드삭제 → 확인 단계 필수(FR-5).
6. UPDATE 권한 없음 → 업로드/삭제 UI 미표시 + (우회 시) 서버 403 토스트.
7. 다운로드 네트워크 실패 → 에러 토스트.
8. 한글/특수문자 파일명 → 정상 표시/다운로드(NFR-3).
9. 업로드 중 언마운트 → fetch 자연 중단, 상태 정리.
10. 첨부 0개 → 빈 상태(S7).
11. 긴 파일명 → CSS truncate.
