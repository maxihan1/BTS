## 배경 — 이미 머지된 백엔드 계약 (프론트가 소비만)

- `GET /api/v1/users/me/whoami` 응답에 `mfaEnrollmentRequired: Boolean` 필드 노출
  (`WhoamiResponse.kt:30`). 값은 access JWT 클레임 `mfa_enrollment_required`를 **읽기만** 한다(재계산 X).
- `MfaEnrollmentGateFilter` — 클레임 true인 요청을 **ALLOW_LIST 외 모든 경로에서 403**
  `{"error":"mfa_enrollment_required"}`로 차단. ALLOW_LIST = `/api/v1/auth/mfa/**` ·
  `/api/v1/users/me/whoami` · `/api/v1/auth/logout` · `/api/v1/auth/refresh`.
- 클레임 재계산 chokepoint = `JwtIssuer` 발급 4경로(local/refresh/OIDC/SAML). **등록 완료 후 클레임이
  false로 풀리는 유일한 경로 = 토큰 refresh**(또는 재로그인).

## 사용자 시나리오 (Given-When-Then)

- **S1 강제 진입**. Given 관리자/민감 프로젝트 멤버(`mfaEnrollmentRequired=true`)가 MFA 미등록.
  When 로그인 후 임의 보호 라우트로 진입. Then `/settings/mfa`로 강제 리다이렉트되고 상단에 강제 안내 배너가 보인다.
- **S2 게이트 고정**. Given S1 상태. When `/dashboard` 등 다른 라우트로 이동 시도.
  Then 다시 `/settings/mfa`로 되돌려진다(등록 전까지 탈출 불가).
- **S3 등록 후 해제**. Given S1 상태. When MFA(TOTP)를 정상 등록(setup→enable 성공).
  Then 토큰 refresh + whoami 재조회로 `mfaEnrollmentRequired=false`가 되고, 게이트가 풀려 `/dashboard`(또는 returnTo)로 진입한다. 배너 사라짐.
- **S4 비강제 회귀**. Given 일반 사용자(`mfaEnrollmentRequired=false`). When 로그인/이동.
  Then 어떤 리다이렉트·배너도 없다(기존 동작 그대로). `/settings/mfa` 자율 등록 흐름도 변화 없음.

## 기능 요구사항 (FR)

### D6 — 프론트 UI

- **FR-D6-1 (whoami 계약 동기화)**. `WhoamiResponseSchema`(api/schemas.ts)에 `mfaEnrollmentRequired: z.boolean()`
  추가(백엔드 non-null과 1:1, required·non-optional — `mustChangePassword`/`isSystemAdmin` 선례 동형).
  중앙 픽스처 `aliceUser`/`bobUser`(auth-fixtures.ts) + 팩토리 미사용 인라인 리터럴 전수 + MSW whoami 핸들러
  갱신. `pnpm typecheck` + `pnpm test` 그린(Zod parse 실패 0).
- **FR-D6-2 (강제 게이트 가드)**. `requireMfaEnrolled` 가드 신설(auth/routeGuard.ts) — `requirePasswordChanged` 동형.
  - `user === null` → 통과(미인증은 requireAuth 담당).
  - `location.pathname === '/settings/mfa'` → 통과(무한 redirect 방지).
  - `user.mfaEnrollmentRequired === true` → `/settings/mfa`로 `throw redirect`.
  - 보호 라우트의 beforeLoad 체인에 `composeGuards(requireAuth, requirePasswordChanged, requireMfaEnrolled)`로 합성.
  - 적용 대상 = `requirePasswordChanged`가 이미 걸린 보호 라우트와 동일 집합(`/settings/mfa` 자신은 제외).
- **FR-D6-3 (강제 안내 배너)**. `MfaSettings`(또는 `MfaSettingsPage`)에서 `useAuthUser()?.mfaEnrollmentRequired === true`
  일 때만 상단에 안내 배너 표시(role="status"). 문구는 i18n(`mfaStrings`)에 추가, 한국어. 비강제 사용자는 배너 없음.
- **FR-D6-4 (등록 후 게이트 해제 — 정합성 필수)**. enable 성공 시 강제 모드(`mfaEnrollmentRequired===true`)였다면
  **(1) 토큰 refresh(POST /api/v1/auth/refresh) → (2) whoami 재조회 → (3) setSession(새 token+user) → (4)
  `/dashboard`로 네비게이션**. (returnTo 보존은 `requirePasswordChanged` 선례와 동일하게 미도입 — 단순성.)
  이 단계가 없으면 store의 `mfaEnrollmentRequired`가 stale(true)로
  남아 가드가 영구 리다이렉트 → 사용자가 등록하고도 갇힌다. (선례 `ChangePasswordForm`은 이 해제가 없는 갭이 있으나
  범위 밖 — 손대지 않는다.) 비강제 모드의 enable은 기존 동작(status invalidate)만, refresh·네비게이션 없음.

### D7 — E2E (Playwright)

- **E2E-1**. S1 — 강제대상 미등록 로그인 → `/settings/mfa` 리다이렉트 + 배너 노출.
- **E2E-2**. S2 — 강제 상태에서 `/dashboard` 이동 시도 → `/settings/mfa`로 되돌림.
- **E2E-3**. S3 — 등록 완료 → 게이트 해제 → `/dashboard` 진입 + 배너 사라짐.
- **E2E-4**. S4 회귀 — 비강제 사용자는 리다이렉트·배너 없음. 기존 mfa/login E2E 회귀 0.
- E2E 인프라 = 기존 `MFA_E2E_ENABLED_KEY` 토글 + 공유 `mfaStore`(auth-fixtures.ts) 패턴 확장
  (`__bts_e2e_mfa_enforcement` localStorage 플래그 + whoami 핸들러가 플래그·등록상태로 `mfaEnrollmentRequired`
  파생 + refresh 핸들러가 등록 후 false 반환). `e2e-msw-scenario-toggle-localstorage-flag` ·
  `msw-derived-behavior-shared-store-e2e` 준수(addInitScript로 goto 전 시드).

## 비기능 요구사항 (NFR)

- **NFR-1 (방어 심층)**. 프론트 가드는 UX 편의일 뿐 권위 출처가 아니다. 직접 API 호출 차단은 백엔드 게이트(403)가 담당.
  프론트는 비-ALLOW_LIST API의 403 `{"error":"mfa_enrollment_required"}`를 만나도 **크래시하지 않는다**(기존 에러 처리로 흡수).
- **NFR-2 (계약 정합)**. whoami 필드는 백엔드 DTO와 1:1. 임의 invent 금지(`frontend-zod-backend-dto-contract-gap`).
- **NFR-3 (접근성)**. 배너 role="status"/aria-live, 기존 컴포넌트 컨벤션 준수.
- **NFR-4 (회귀 0)**. 기존 whoami/login/mfa/route-guard 단위·E2E 전부 그린.

## 엣지 케이스

- **EC-1 (레이아웃 403 소음)**. `/settings/mfa` 강제 체류 중 Header/레이아웃이 비-ALLOW_LIST API(알림·프로젝트 등)를
  호출하면 403. 페이지·등록 흐름은 깨지지 않아야 한다(MFA·whoami·logout·refresh가 모두 ALLOW_LIST라 등록 자체는 가능).
  E2E-1에서 페이지 정상 렌더(배너+활성화 버튼)로 검증.
- **EC-2 (무한 redirect 방지)**. 가드는 `/settings/mfa`에서 통과(자기 경로 예외). `requirePasswordChanged`와
  동시 적용 시 순서 — mustChangePassword가 우선(비밀번호 먼저), 그 다음 MFA. 둘 다 true면 password로 먼저 보냄.
- **EC-3 (refresh 실패)**. 등록 후 refresh가 401 등으로 실패하면 기존 `doRefresh` 정책(clearSession→로그인)으로 폴백.
  사용자에게 재로그인 유도(데이터 손상 없음).
- **EC-4 (sessionStorage 영속)**. authStore는 sessionStorage persist. 새로고침 시 store 재수화로
  `mfaEnrollmentRequired`가 유지된다 → 가드 동작 일관. 정책 변경 반영은 다음 로그인/refresh까지 지연(ADR fail-safe와 일치).
