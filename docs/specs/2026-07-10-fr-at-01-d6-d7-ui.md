## §1 개요

프로젝트 관리자가 자동화 **룰**(무엇이 룰을 발화시키는가 = 트리거)을 생성/관리하는 프론트 화면. 백엔드 5 엔드포인트(프로젝트 스코프)를 소비한다. 액션·조건 빌더는 이번 범위 밖 — 이 UI로 만든 룰은 트리거 매칭 시 `q_automation_execution`에 enqueue만 하고 실제 동작은 FR-AT-02에서 붙는다(점진적 완성).

## §2 사용자 시나리오

- **S1 (목록)**. PROJECT_ADMIN이 프로젝트 설정 → 자동화 탭에 들어가면 해당 프로젝트의 룰 목록(이름·트리거타입·활성여부·다음발화시각)을 본다. 룰이 없으면 빈 상태 CTA.
- **S2 (생성)**. "룰 추가"로 이름 입력 + 트리거 타입 5종 중 선택 → 타입별 설정 폼(아래 §3)을 채우고 저장하면 201로 목록에 추가된다.
- **S3 (WEBHOOK 토큰)**. WEBHOOK 트리거 룰 생성 시 응답의 `webhookToken` 원문을 **1회성 모달**로 보여주고 복사 버튼 제공. 모달을 닫으면 다시 볼 수 없음을 경고.
- **S4 (수정)**. 룰의 이름/활성여부/트리거설정을 인라인 또는 편집 폼에서 변경 → PATCH(OCC `version`). 다른 곳에서 먼저 바뀌었으면 409 → "최신 정보를 불러온 뒤 다시" 안내 + refetch.
- **S5 (활성 토글)**. 목록에서 룰을 즉시 활성/비활성 토글(PATCH enabled).
- **S6 (삭제)**. 확인 후 soft delete(204) → 목록에서 제거.
- **S7 (권한)**. MANAGE_AUTOMATION 없는 사용자가 API 호출 시 403 → "권한이 없습니다" 상태 렌더(존재 은닉 메시지 그대로).

## §3 트리거 타입별 폼 필드 (백엔드 `TriggerConfig.validate` 기준)

| 트리거 | 폼 필드 | triggerConfig 직렬화 |
|---|---|---|
| ISSUE_CREATED | 없음 | `{}` |
| ISSUE_COMMENTED | 없음 | `{}` |
| ISSUE_UPDATED | fields (선택, 태그 입력 — 비면 전체 필드) | `{"fields":["status","priority"]}` 또는 `{}` |
| SCHEDULED | cron (필수, 6필드 텍스트 + 형식 힌트) | `{"cron":"0 0 9 * * *"}` |
| WEBHOOK | 없음 (생성 시 토큰 발급) | `{}` |

트리거별 설정은 폼에서 구조화 입력 → **JSON 문자열로 직렬화**해 `triggerConfig`로 전송. 백엔드 형식 검증(400)을 신뢰하되, 프론트도 최소 형식(cron 비어있음 금지) 사전 검증으로 왕복 절감.

## §4 기능 요구사항 (FR)

- **FR-1** 프로젝트 스코프 라우트 `projects/$projectKey/settings/automation` 신설(RouteAdapter + Page 분리, 라우터 비의존 단위테스트).
- **FR-2** api 레이어 `api/automation-rules.ts` — list/get/create/patch/delete, Zod 응답 스키마(`AutomationRuleResponse`·`CreateAutomationRuleResponse`). `apiGet/apiPost` + `apiFetch`(PATCH/DELETE) 관례.
- **FR-3** TanStack Query 훅 — 목록 쿼리(`['automation-rules', projectKey]`), create/patch/delete mutation. mutation 성공 시 **invalidate-only**(부분응답 setQueryData 플리커 회피 — learnings 2026-05-30).
- **FR-4** 룰 생성 폼 — 이름 + 트리거 셀렉트 + 타입별 조건부 필드(§3). 생성은 `enabled=true`로 시작(백엔드 고정), 이후 토글로 비활성 가능.
- **FR-5** WEBHOOK 토큰 1회 노출 모달 + 복사. 토큰은 상태에만 잠깐 보관, 재조회 불가 명시.
- **FR-6** 목록: 활성 토글·편집·삭제(확인 모달). 삭제/토글은 낙관적 대신 invalidate.
- **FR-7** 에러 처리: 403/404/409/400을 각 상태 메시지로. 409는 refetch 유도.

## §5 비기능 요구사항 (NFR)

- **N1 보안**. 토큰 원문은 로그·URL·localStorage에 저장 금지. 모달 상태에만. `AutomationRuleResponse`에 토큰 필드 없음(백엔드가 이미 차단).
- **N2 접근성**. 폼 라벨/aria, 셀렉트 키보드 조작, 삭제 확인 모달 focus trap(기존 Dialog 컴포넌트 재사용).
- **N3 E2E 견고성**. 텍스트 중복 액션 버튼('저장'·'삭제')은 `data-testid`/컨테이너 한정(learnings 2026-05-31 strict mode violation 회귀).
- **N4 계약 정합**. Zod 스키마는 백엔드 DTO를 invent하지 말고 grep한 실 필드만(learnings `frontend-zod-backend-dto-contract-gap`). MSW fixture는 응답 스키마 required 전 필드 채움.

## §6 엣지 케이스

- **E1** SCHEDULED cron 형식 오류 → 백엔드 400 `AUTOMATION_RULE_INVALID` → 폼 필드 인라인 에러.
- **E2** 이름 빈 문자열 → 백엔드 400(도메인 검증). 프론트도 required.
- **E3** 목록 비어있음 → 빈 상태 CTA(회귀: 빈 그리드 버튼 dead path 방지 — 실제 모달 연결).
- **E4** WEBHOOK 토큰 모달 닫은 뒤 재생성 불가 — UI에 "다시 볼 수 없음" 경고. 분실 시 룰 삭제 후 재생성 안내.
- **E5** 409 OCC — PATCH 시 stale version → 에러 토스트 + 자동 refetch로 최신 version 확보.
- **E6** 403 — 권한 없는 사용자. 페이지 자체는 라우팅되나 API 403 → 권한 없음 상태(field-permissions 선례처럼 라우트단 하드가드 없이 API 위임).
- **E7** enabled=false 룰도 목록에 표시(비활성 배지). 트리거 감지 제외는 백엔드 책임.

## §7 D7 E2E 시나리오 (Playwright + MSW)

- **T1** 목록 로드 + 빈 상태.
- **T2** ISSUE_CREATED 룰 생성 → 목록 반영.
- **T3** SCHEDULED 룰 생성(cron 입력) → nextFireAt 표시.
- **T4** WEBHOOK 룰 생성 → 토큰 모달 노출 + 복사 → 닫기 후 미표시.
- **T5** 활성 토글(PATCH enabled) → 배지 변화.
- **T6** 삭제 확인 → 목록 제거.
- **T7** 409 OCC 시나리오(MSW stateful override) → 에러 + refetch.

MSW는 stateful 공유 store(생성/수정/삭제 반영)로 파생동작 검증(learnings `msw-derived-behavior-shared-store-e2e`). 시나리오 토글=localStorage 플래그.
