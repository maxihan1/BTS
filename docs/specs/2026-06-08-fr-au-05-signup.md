# FR-AU-05 회원가입 (관리자 로컬 계정 생성) — 스펙

> slug: fr-au-05-signup · BC: identity-access · type: auth
> 도메인/ADR: [docs/decisions/2026-06-08-local-account-signup.md](../decisions/2026-06-08-local-account-signup.md)
> 작성 방식: 직접 기술 스펙 (완료 진행 중 FR 슬라이스 — office-hours 부적합, 메모리 `bts-spec-office-hours-mismatch`)

## 사용자 시나리오 (Given-When-Then)

- **S1 (가입 정상)**. Given SYSTEM_ADMIN으로 로그인한 관리자, When 가입 폼에 username·(선택)email·displayName을 입력하고 생성, Then 서버가 `users`+`local_credentials` 행을 만들고 정책 충족 임시 비밀번호를 생성해 응답으로 **1회 반환**, 관리자 화면에 임시 비밀번호가 1회 표시된다.
- **S2 (권한 거부)**. Given 일반 사용자(비 SYSTEM_ADMIN), When `POST /api/v1/users` 호출, Then `403 Forbidden`, 계정 생성되지 않음.
- **S3 (중복 username)**. Given 이미 존재하는 username, When 같은 username으로 생성, Then `409 USERNAME_TAKEN`, 기존 계정은 변경되지 않음(덮어쓰기 금지).
- **S4 (첫 로그인 강제 변경)**. Given 임시 비밀번호로 만들어진 계정(`must_change_password=true`), When 협력사 사용자가 그 비번으로 로그인, Then 앱이 `mustChangePassword=true`를 인지해 `/settings/password`로 강제 이동시키고 다른 보호 페이지 접근을 막는다.
- **S5 (변경 후 해제)**. Given 강제 변경 상태 사용자, When 비밀번호 변경(`POST /api/v1/users/me/password`) 성공, Then `must_change_password=false`로 해제되어 정상적으로 앱을 사용한다.
- **S6 (입력 검증)**. Given SYSTEM_ADMIN, When username 누락/형식 위반 또는 email 형식 위반으로 생성, Then `400` 검증 에러, 계정 생성되지 않음.

## 기능 요구사항 (FR)

- **FR1**. `POST /api/v1/users` 엔드포인트 추가(UsersController 확장). `@PreAuthorize("hasRole('SYSTEM_ADMIN')")`.
- **FR2**. 요청 본문 `{ username, email?, displayName }`. 서버가 정책 충족(12자 이상 + 3종 복잡도) 랜덤 임시 비밀번호 생성.
- **FR3**. 계정 생성 = INSERT 전용. `users` 신규 행 + `local_credentials` 행(`must_change_password=true`, Argon2id 해시). 한 트랜잭션.
- **FR4**. 중복 username → `409 USERNAME_TAKEN`. 기존 계정 덮어쓰기 금지(UPSERT 재사용 금지).
- **FR5**. 응답 `201 { id, username, temporaryPassword }`. `temporaryPassword`는 이 응답에서만 노출(평문 미저장/미로깅).
- **FR6**. `WhoamiResponse`에 `mustChangePassword: Boolean` + `isSystemAdmin: Boolean` 추가. `mustChangePassword`는 `local_credentials.must_change_password` 반영(행 없으면 false). `isSystemAdmin`은 `SystemPermissionResolver.isSystemAdmin(userId)` 결과(PAT 인증은 전역역할 제외 → false, 메모리 `session-management-pat-exclusion`).
- **FR7**. `ChangePasswordService.changePassword` 성공 시 `must_change_password=false`로 갱신.
- **FR8 (프론트 가입 폼)**. SYSTEM_ADMIN만 접근 가능한 가입 폼 화면(`/admin/users/new` 등). username·email·displayName 입력 → 생성 → 임시 비밀번호 1회 표시(복사 안내). 비 admin은 `requireSystemAdmin` 라우트 가드(`authStore.user.isSystemAdmin`)로 차단. BTS 첫 SYSTEM_ADMIN 프론트 게이팅(기존엔 프로젝트 단위 권한 게이팅만).
- **FR9 (프론트 강제 변경 가드)**. whoami `mustChangePassword=true`이면 `/settings/password` 외 보호 라우트 접근 시 강제 리다이렉트. 구현 — 로그인 흐름이 이미 `login → whoami → authStore.setSession({accessToken, user:WhoamiResponse})`로 저장하므로, `routeGuard.ts`에 `requirePasswordChanged` 가드를 추가해 `authStore.user.mustChangePassword`를 동기 읽기(기존 `requireAuth`와 동일 패턴).
- **FR10 (E2E)**. 관리자 가입 → 임시 비번 표시, 협력사 첫 로그인 → 강제 변경 흐름을 Playwright로 검증.

## 비기능 요구사항 (NFR)

- **N1 (비밀번호 보안)**. 임시 비밀번호는 `SecureRandom` 기반 생성, Argon2id 해시만 저장, 평문은 응답 1회 외 어디에도(DB·로그·감사) 남기지 않음.
- **N2 (CSRF)**. `POST /api/v1/users`는 상태 변경 — CSRF 토큰(`X-XSRF-TOKEN`) 필요(기존 비번 변경 API와 동일 관례, 메모리 `frontend-api-convention-per-bc`).
- **N3 (권한 최소노출)**. 403/권한 예외 message는 일반 메시지(상세 누출 금지, 메모리 `fr-pm-04-guard-exception-message-http-leak`).
- **N4 (에러 코드 관례)**. 에러 응답은 대문자 코드 `{ code, message }`(예 `USERNAME_TAKEN`), 프론트 Zod 스키마와 대문자 정합(메모리 `frontend-zod-backend-dto-contract-gap`).

## API 인터페이스 (REST)

### POST /api/v1/users (신규)
- 권한: `SYSTEM_ADMIN`
- 요청: `{ "username": string, "email": string|null, "displayName": string }`
- 응답 201: `{ "id": UUID, "username": string, "temporaryPassword": string }`
- 에러: 403(비 admin) · 409 `{ "code": "USERNAME_TAKEN", ... }` · 400(검증)

### GET /api/v1/users/me/whoami (확장)
- 응답에 `mustChangePassword: boolean` + `isSystemAdmin: boolean` 추가. PAT 인증은 둘 다 false(local_credentials 무관 + 전역역할 제외).

## 데이터 모델 변경

- **V018** `ALTER TABLE local_credentials ADD COLUMN must_change_password BOOLEAN NOT NULL DEFAULT FALSE;`
- 기존 행은 DEFAULT FALSE로 영향 없음. 외부(LDAP/SSO) 계정은 `local_credentials` 행 자체가 없어 무관.

## 엣지 케이스

- **EC1 (username 검증)**. NotBlank + 길이 3~255(`users.username VARCHAR(255)`) + 허용 문자(영숫자·`.`·`_`·`-`). 위반 400.
- **EC2 (email 선택)**. email은 nullable(`users.email`). 제공 시 형식 검증, 미제공 시 null 허용.
- **EC3 (TOCTOU 중복)**. 사전 존재검사와 INSERT 사이 경합 → `users.username UNIQUE` 제약이 최종 방어 → 충돌을 `409 USERNAME_TAKEN`으로 변환.
- **EC4 (임시 비번 정책 보장)**. 생성기는 항상 정책(12자+3종) 충족 비번을 반환(생성 후 `PasswordPolicy.validate`로 self-check).
- **EC5 (강제 변경 우회 범위)**. 프론트 가드가 1차 강제 수단. 백엔드 전역 차단(비번 변경 외 모든 쓰기 차단)은 본 슬라이스 제외 — 제약에 명시.
- **EC6 (displayName 기본값)**. displayName NotBlank 요구(빈 값 400). username과 별개.

## 제약 조건

- 리셋(비번 재설정)은 이메일 인프라(notification BC) 부재로 제외.
- 강제 변경 enforcement는 프론트 라우트 가드 기준(백엔드 전역 인터셉터는 후속 하드닝 후보) — EC5.
- 한 PR = 한 BC(identity-access). 프론트(D6)/E2E(D7)는 same-BC view layer로 같은 PR 처리.
- **감사 로그 위임**. 계정 생성 감사 이벤트는 FR-AU-10(인증 감사 로그) 소관 → 본 슬라이스 제외. 근거 — `AuthEventType` enum에 ACCOUNT_CREATED 부재, 추가 시 cross-module 카운트 가드 깨짐(메모리 `enum-add-breaks-crossmodule-count-guard`). FR-AU-10에서 일괄.
- **Zod/mock 파급**. `mustChangePassword` + `isSystemAdmin`(required boolean 2개) 추가 시 backend `WhoamiResponse` + 프론트 Zod 스키마(`@/api/schemas`) + 모든 `WhoamiResponse` mock/fixture(`auth-handlers.ts`, `auth-fixtures.ts`, 인라인 mock) + 백엔드 `WhoamiControllerTest` 전수 갱신(메모리 `zod-schema-strengthen-inline-mock-fanout`).
- **email 유니크 아님**. `users`는 username만 UNIQUE(V001). email 중복 허용 — 별도 제약 없음.

## 측정 가능한 완료 기준

- 백엔드 통합테스트: 201+임시비번 반환+`must_change=true` / 403 비admin / 409 중복 / 400 검증 / whoami `mustChangePassword` 노출 / 변경 시 해제.
- 임시 비번 생성기 단위테스트: 정책 충족 + 무작위성.
- 프론트 단위테스트: 가입 폼(검증·제출·임시비번 표시) + 강제 변경 가드.
- E2E: 관리자 가입(임시비번 표시) + 협력사 첫 로그인 강제 변경.
- `pnpm verify`(lint+typecheck+test+build) 그린 + `./gradlew test` 그린 + V018 마이그레이션.
