# FR-AT-02 D6 액션 빌더 UI + D7 E2E — 스펙

> slug: fr-at-02-d6-d7-ui · type: ui · BC: automation · 생성: 2026-07-12
> 선행: FR-AT-02 D1~D5(PR #256, 백엔드 계약 확정) · FR-AT-01 D6/D7(PR #254, 트리거 CRUD UI)
> 범위: 순수 프론트(apps/web). 백엔드 변경 0.

## 배경

기존 `projects/$projectKey/settings/automation` 룰 설정 화면(`AutomationRuleFormDialog`)은
트리거만 편집한다. FR-AT-02 백엔드가 룰에 **액션 리스트(`actions[]`)** 와 **실행 주체(`actorUserId`)** 를
추가했고, 룰 CRUD payload도 이미 확장됐다. 이 작업은 그 확정 계약을 소비하는 **액션 빌더 UI**를 폼에
추가하고, 프론트 Zod 스키마를 계약에 맞춘다.

## 사용자 시나리오 (Given-When-Then)

**S1. SET_FIELD 액션 추가 (필드 타입별 위젯)**
- Given: 프로젝트 관리자가 자동화 룰 생성 다이얼로그를 연다
- When: "액션 추가" → SET_FIELD 선택 → 필드 `priority` 선택 → 값 `3`(1~5 select) → 저장
- Then: `actions:[{type:"SET_FIELD", config:'{"field":"priority","value":3}'}]` 로 POST, 목록에 반영

**S2. ASSIGN 액션 + 담당자 해제**
- Given: 액션 추가 다이얼로그
- When: ASSIGN 선택 → 담당자 피커에서 프로젝트 멤버 선택(또는 "담당자 해제")
- Then: `config:'{"assigneeId":"<uuid>"}'`(해제 시 `{"assigneeId":null}`)

**S3. ADD_COMMENT 액션 + 템플릿 변수**
- Given: 액션 추가
- When: ADD_COMMENT 선택 → body에 `{{ issue.key }} 자동 처리됨` 입력
- Then: `config:'{"body":"{{ issue.key }} 자동 처리됨"}'`. 폼은 사용 가능한 템플릿 변수 힌트를 보여준다

**S4. CALL_WEBHOOK 액션**
- Given: 액션 추가
- When: CALL_WEBHOOK 선택 → url `https://hooks.example.com/x` + method POST + 헤더 `X-Token: abc` + body 입력
- Then: `config:'{"url":"...","method":"POST","headers":{"X-Token":"abc"},"body":"..."}'`

**S5. 다중 액션 + 순서변경**
- Given: 룰에 SET_FIELD, ADD_COMMENT 두 액션이 있다
- When: ADD_COMMENT를 위로 이동(↑) → 저장
- Then: `actions[0]=ADD_COMMENT, actions[1]=SET_FIELD` 순서로 저장(position 반영)

**S6. rule actor(실행 주체) 선택**
- Given: 룰 생성/수정 다이얼로그
- When: 실행 주체 피커에서 프로젝트 멤버 선택(기본=생성자/현재 사용자)
- Then: 생성 시 `actorUserId=<uuid>`, 수정 시 PATCH `actorUserId=<uuid>`

**S7. 편집 모드 초기값 로드**
- Given: 액션 2개 + actor가 설정된 기존 룰
- When: 수정 다이얼로그를 연다
- Then: 액션 리스트·각 config·actor가 폼에 정확히 로드됨(응답 config는 **객체** → 폼 상태로 역직렬화)

**S8. 409 동시 수정 충돌**
- Given: 다른 세션이 같은 룰을 먼저 변경(version 증가)
- When: 액션을 수정해 저장 → 409
- Then: 기존 처리 재사용 — 목록 invalidate + 폼 닫기 + 토스트("다른 곳에서 먼저 변경되었습니다")

## 기능 요구사항 (FR)

- **FR1. Zod 계약 정합** — `automationRuleResponseSchema`에 `actions: ActionResponse[]`(`{type, config:object}`)와
  `actorUserId: string(uuid)` 추가. 요청 입력 타입(`CreateAutomationRuleInput`/`PatchAutomationRuleInput`)에
  `actions?`·`actorUserId?` 추가. **backend DTO invent 금지** — 아래 계약에 1:1.
- **FR2. 액션 타입 4종 편집 UI** — SET_FIELD / ASSIGN / ADD_COMMENT / CALL_WEBHOOK. 타입 선택 시 조건부 필드 전환
  (`TriggerConfigFields` 선례 동형).
- **FR3. SET_FIELD 필드 타입별 값 위젯** — 필드 드롭다운(6종: summary/description/environment/priority/impact/labels).
  - summary·description·environment → 텍스트 입력(문자열 값)
  - priority → 1~5 select(정수 값), impact → 1~3 select(정수 값)
  - labels → 태그 입력(문자열 배열, 폼 내 기존 fields 태그칩 패턴 재사용)
- **FR4. ASSIGN 담당자 피커** — `use-project-members` 재사용. 멤버 목록 + "담당자 해제"(null) 옵션.
- **FR5. ADD_COMMENT 본문 + 템플릿 힌트** — textarea. `{{ issue.key }}` 등 사용 가능 변수 힌트 텍스트 표시.
- **FR6. CALL_WEBHOOK 필드** — url(text)·method(GET/POST/PUT/PATCH/DELETE select, 기본 POST)·headers(키-값 쌍 목록)·body(textarea).
- **FR7. 다중 액션 리스트 + 순서변경** — 액션 추가/삭제 + 위(↑)/아래(↓) 이동. 저장 시 배열 순서 = position.
  drag-drop 라이브러리 미사용(버튼 방식).
- **FR8. rule actor 피커** — `use-project-members` 재사용.
  - **생성 모드 기본값 = 미설정(null)** → 백엔드가 생성자로 폴백. 사용자가 명시 선택 시에만 actorUserId 전송
    (생성자가 project-members에 없을 수 있는 시스템 관리자 케이스 회피 — brainstorming gap#2).
  - 수정 모드는 저장된 actorUserId 로드. actorUserId → displayName 해석(멤버 목록), 미해석 시 "알 수 없는 사용자"
    표시하되 값 보존.
- **FR9. config 직렬화(비대칭)** — 읽기: 응답 config(객체) → 폼 상태. 쓰기: 폼 상태 → `JSON.stringify`로 각
  ActionRequest.config(JSON 문자열). `serializeTriggerConfig` 선례 동형 헬퍼(`serializeActionConfig`).
- **FR10. 프론트 사전검증** — 저장 전 필수값 검사: SET_FIELD field/value, ASSIGN(해제 아니면 멤버 선택),
  ADD_COMMENT body 비어있지 않음, CALL_WEBHOOK url http(s) prefix. 백엔드 400 방지(중복 방어, 백엔드가 최종 방어선).
- **FR11. 목록 표시** — `AutomationRuleList`에 액션 개수/타입 배지 표시(예: "SET_FIELD · ASSIGN").
- **FR12. 409/에러 처리** — 기존 `handleSubmitFailure` 재사용(409=폼닫기+invalidate+토스트, 그 외=submitError 유지).

## 비기능 요구사항 (NFR)

- **NFR1. 계약 무결성** — Zod가 backend DTO를 invent하지 않음. `frontend-zod-backend-dto-contract-gap` 회귀 방지.
- **NFR2. 접근성** — 모든 입력에 label/aria-label, 순서변경 버튼에 aria-label("위로"/"아래로"), role="alert" 에러.
- **NFR3. 상태 격리** — Dialog key 재마운트(기존 패턴 유지)로 편집 대상 전환 시 stale 액션 잔존 없음.
- **NFR4. i18n** — automation BC 관례(고정 한국어 문구, i18n 미도입).

## 백엔드 계약 (정본, 변경 없음)

응답 `AutomationRuleResponse`:
```
actions: [{ type: "SET_FIELD"|"ASSIGN"|"ADD_COMMENT"|"CALL_WEBHOOK", config: <object> }]
actorUserId: <uuid, non-null>
```
액션별 응답 config(객체):
- SET_FIELD: `{field, value}` (value = 임의 JSON — string/number/string[])
- ASSIGN: `{assigneeId}` (uuid string | null)
- ADD_COMMENT: `{body}`
- CALL_WEBHOOK: `{url, method, headers, body}`

요청 `Create/PatchAutomationRuleRequest`:
```
actions: [{ type: <string>, config: <JSON 문자열> }]   // config는 문자열!
actorUserId: <uuid | null>                              // create null=생성자, patch null=미변경
```
SET_FIELD 지원 필드 6종(그 외 실행 시점 FAILED): summary/description/environment(String), priority(Int 1..5),
impact(Int 1..3), labels(List<String>).

## 엣지 케이스

- **EC1. config 비대칭 혼동** — 응답은 객체, 요청은 문자열. 읽기/쓰기 경로를 분리하지 않으면 `[object Object]`
  직렬화 버그. → `serializeActionConfig`/`parseActionConfig` 쌍으로 명시 분리 + 단위테스트.
- **EC2. priority/impact 범위** — select가 1~5 / 1~3만 노출(범위 밖 값 생성 불가). 자유 숫자 입력 금지.
- **EC3. ASSIGN 해제 vs 미선택** — "담당자 해제"(assigneeId:null, 유효)와 "아직 미선택"(저장 불가)을 구분.
- **EC4. actorUserId 미해석** — 저장된 actor가 현재 프로젝트 멤버 목록에 없으면(멤버 제외 등) "알 수 없는 사용자"
  표시하되 값은 보존(임의로 생성자로 덮어쓰지 않음).
- **EC5. 빈 액션 리스트** — 액션 0개 룰 유효(트리거만 있는 룰). actions:[] 저장 허용.
- **EC6. 편집 대상 전환 stale** — 다이얼로그 열린 채 다른 룰 편집 시 key 재마운트로 이전 액션/actor 잔존 방지.
- **EC7. CALL_WEBHOOK 템플릿 url** — url에 `{{ }}` 포함 가능(백엔드 prefix만 검증). 프론트도 http(s) prefix만 검사.
- **EC8. labels 중복 태그** — 동일 라벨 중복 추가 방지(기존 fields 태그 패턴 재사용).
- **EC9. priority/impact 숫자 강제 (brainstorming gap#1)** — HTML select 값은 문자열. JSON 직렬화 전 `Number()`로
  정수 변환해 `{"value":3}`(숫자)로 전송(`"3"` 문자열 아님). value가 숫자여야 백엔드 decodeValue(Int) 통과.
- **EC10. 알 수 없는 SET_FIELD field (brainstorming gap#3)** — API로 6종 외 field가 저장된 기존 룰 로드 시,
  드롭다운에 없는 field는 텍스트 값 위젯으로 fallback 표시(값 보존, 임의 변경 없음).
- **EC11. Zod config 표현 (brainstorming gap#4)** — 응답 config는 타입별 형태가 달라 `z.record(z.string(), z.unknown())`
  loose 스키마로 받고, 폼의 `parseActionConfig`가 type에 따라 구조화. 타입별 discriminated union은 과도(brittle).
