## 사용자 시나리오 (Given-When-Then)

### S1. 상태 이력이 있는 프로젝트의 CFD
- **Given** 프로젝트 `PROJ`에 BROWSE 권한이 있는 사용자. 여러 이슈가 지난 30일간 여러 상태를 거침(status 전이 이력 존재)
- **When** `GET /api/v1/projects/PROJ/cfd?from=2026-06-04&to=2026-07-03`
- **Then** 200 OK. 창(window) 내 각 UTC 날짜마다 `{ date, todoCount, inProgressCount, doneCount }` 한 점. 날짜 오름차순.

### S2. 이슈가 없는 프로젝트 / 빈 창
- **Given** BROWSE 권한 있는 사용자. 창 내 존재하는 이슈 0개
- **When** CFD 조회
- **Then** 200 OK. 각 날짜 점의 세 카운트 모두 0(점 자체는 창 길이만큼 존재).

### S3. 기밀 이슈 누출 차단
- **Given** 프로젝트에 사용자가 볼 수 없는(이슈 보안 수준) 이슈가 섞여 있음
- **When** CFD 조회
- **Then** 보이지 않는 이슈는 어느 날짜·어느 카테고리 카운트에도 합산되지 않음.

### S4. 권한 없음
- **Given** 프로젝트에 BROWSE 권한이 없는 사용자
- **When** CFD 조회
- **Then** 403.

### S5. 미인증
- **Given** 인증 토큰 없음
- **When** CFD 조회
- **Then** 401 (리소스 조회 이전에 actor 추출 실패로 거부 — 존재 probe 차단).

### S6. 워크플로우 스킴 미할당 타입
- **Given** 이슈 타입에 워크플로우 스킴이 할당되지 않음(상태→카테고리 매핑 불가)
- **When** CFD 조회
- **Then** 500이 아니라 200. 해당 타입 이슈의 상태는 TODO 카테고리로 폴백(EpicProgress 선례).

### S7. 잘못된 시간 창
- **Given** `from > to` 또는 파싱 불가 날짜 또는 창 길이 상한 초과
- **When** CFD 조회
- **Then** 422 (Validation). 500 아님.

### S8. 상태 전이 이력이 없는 이슈
- **Given** 생성 후 상태 전이가 한 번도 없는 이슈(또는 V018 이전 생성 이슈)
- **When** CFD 조회
- **Then** 그 이슈는 존재 기간 내내 `current_state_key`의 카테고리로 집계(한계 — ADR D2 명시).

### S9. 소프트 삭제 이슈
- **Given** 창 중간에 소프트 삭제된 이슈
- **When** CFD 조회
- **Then** 삭제일까지는 집계, 삭제일 다음 날부터 어느 카테고리에도 미포함(카운트 감소).

## 기능 요구사항 (FR)

- **FR1** 프로젝트 + 시간 창 `[from, to]`에 대해, 창 내 각 UTC 날짜마다 CFD 한 점(`CfdPoint`)을 반환한다.
  각 점은 `todoCount` / `inProgressCount` / `doneCount`(그 날 각 카테고리에 있던 가시 이슈 수)를 담는다.
  - **"누적(Cumulative)"의 의미**: 시간 누적 합이 아니라, 각 날짜의 **순간(point-in-time) 카운트를 카테고리별로
    쌓은(stacked) 영역**을 뜻한다(전형적 CFD 정의). 세 카운트 합 = 그 날 존재하는 가시 이슈 총수.
    재오픈(DONE→IN_PROGRESS)이면 doneCount가 줄 수 있다(현재 상태 정밀 추적 — monotonic done 아님).
- **FR2** day D 카운트 = 다음을 만족하는 각 가시 이슈를 그 날 카테고리로 분류해 합산.
  - **존재 판정**: `created_at::date ≤ D` AND (`deleted_at IS NULL` OR `deleted_at::date > D`).
  - **그 날 상태 (end-of-day 스냅샷)**: `issue_change_item(field='status')`를 `(group.created_at ASC, group.id ASC)`
    순으로 적용해, `created_at::date ≤ D`인 **마지막** 전이의 `to_value`. 같은 날 여러 전이가 있으면
    그 날 종료 시점(마지막)이 이긴다. 그런 전이가 없으면 **초기 상태**. (tie-break `id ASC`로 결정성 확보 —
    index `idx_issue_change_group_issue(issue_id, created_at DESC, id DESC)`의 안정 정렬과 정합)
  - **초기 상태**: 시간상 첫 status 전이의 `from_value`. status 전이가 전혀 없으면 `issues.current_state_key`.
- **FR3** 상태 키 → 카테고리 매핑은 `WorkflowStateCatalog.listStates(projectKey, issueTypeKey)`의
  `category`(TODO/IN_PROGRESS/DONE)를 이슈 타입별로 캐싱(N+1 차단, FR-EP-02·벨로시티 선례).
  카탈로그에 없는(삭제된) 상태 키 → **TODO 폴백**(EpicProgress EC2/EC3 동형).
- **FR4** `WorkflowStateCatalog.listStates`가 스킴 미할당으로 예외(`WorkflowSchemeNoDefaultException`,
  simpleName 판정)면 해당 타입은 빈 카테고리 맵 → 그 타입 이슈 상태 전부 TODO 폴백. 운영 500 차단.
  `IsolatedWorkflowStateLookup`(REQUIRES_NEW)로 격리 호출 — 공유 트랜잭션 rollback-only 오염 방지(벨로시티 선례).
- **FR5** 시간 창. `from`/`to`는 UTC 날짜(ISO `yyyy-MM-dd`). 둘 다 optional.
  - 둘 다 생략 시 기본 = 최근 30일(`to`=오늘 UTC, `from`=`to`−29일). **'오늘'은 주입된 `Clock`(UTC) 기준**
    — 테스트 결정성(번다운/벨로시티/export의 Clock default 선례). 창은 both-ends 포함, 길이 ≤ 180일.
  - 한쪽만 주면 나머지는 기본 규칙으로 채움(`to`만 → `from`=`to`−29 / `from`만 → `to`=today).
  - **창 길이 상한 = 180일**. 초과 시 422(클램프 아님 — 명시적 거부로 오해 방지).
  - `from > to` 또는 파싱 불가 → 422.
- **FR6** 점은 **날짜 오름차순**(오래된→최신). 차트 X축 좌→우 시간 진행. 창의 모든 날짜에 대해 점 생성(빈 날도 0점).

## 비기능 요구사항 (NFR)

- **NFR1 (N+1 차단)** 쿼리 유계. (a) 프로젝트 가시 이슈 메타(id·created_at·deleted_at·current_state_key·type_id) 배치 1쿼리,
  (b) 그 이슈들의 status 전이 이력 배치 1쿼리(`field='status'`), (c) 카테고리 맵은 이슈 타입별 1회 캐싱.
  이슈/날짜 루프는 in-memory(요청당 상수 쿼리 수).
- **NFR2 (성능 경계)** 창 상한 180일 + 이슈는 프로젝트 스코프로 유계. in-memory 재구성은 이슈별 전이 델타를
  날짜에 누적하는 방식(O(이슈×전이 + 날짜×3))으로 날짜×이슈 이중 루프를 피한다(구현 세부는 plan).
- **NFR3 (보안)** 프로젝트 BROWSE + 이슈별 가시성 필터(`IssueRepository.filterVisibleIssueKeys` →
  `buildActiveSecureWhere` 재사용). 전용 보안 술어 신설/복제 금지(isomorphic-clone 회귀 방지).
- **NFR4 (BC 격리)** issue-tracking이 모든 데이터를 로컬 소유(issues·issue_change). 워크플로우 상태만
  shared-kernel `WorkflowStateCatalog` SPI로 접근. **신규 cross-BC 포트 불필요**(번다운/벨로시티와 달리 스프린트 미참조).
- **NFR5 (완제품)** 401/403/422 코드·핸들러는 신규 컨트롤러 전용 advice 또는 기존 issue-tracking advice 확장.
  catch-all이 401/403/422를 500으로 변질시키지 않도록 `ResponseStatusException` passthrough 유지
  (catch-all-exceptionhandler-swallows / domain-exception-http-handler-basepackage-scope 선례).

## API 인터페이스 (REST)

### `GET /api/v1/projects/{projectKey}/cfd`

- **Query**: `from` (ISO date `yyyy-MM-dd`, optional), `to` (ISO date, optional). FR5 기본/상한 규칙.
- **200 OK** — `DataResponse<CfdResponse>`:

```json
{
  "data": {
    "projectKey": "PROJ",
    "from": "2026-06-04",
    "to": "2026-07-03",
    "points": [
      { "date": "2026-06-04", "todoCount": 12, "inProgressCount": 5, "doneCount": 30 },
      { "date": "2026-06-05", "todoCount": 11, "inProgressCount": 6, "doneCount": 30 }
    ]
  }
}
```

- `from`/`to`는 **해석된(기본값 적용 후) 실제 창**을 echo — 프론트가 실제 범위를 앎.
- `points`는 날짜 오름차순, 창의 모든 날짜 포함(빈 날 0점).
- **401** 미인증 / **403** BROWSE 미충족 / **422** 잘못된 창.
- 프로젝트 미존재·무권한 처리는 issue-tracking의 프로젝트 스코프 조회 선례(FR-SR-01 이슈 필터 등)를 따른다
  (존재 probe 차단 방식 일치 — plan에서 정확한 진입점 확정).

### 응답 DTO 형태
- `CfdResponse(projectKey: String, from: LocalDate, to: LocalDate, points: List<CfdPointResponse>)`
- `CfdPointResponse(date: LocalDate, todoCount: Int, inProgressCount: Int, doneCount: Int)`
- `BurndownResponse`/`VelocityResponse`처럼 `from(result)` companion 매핑. `DataResponse`로 래핑.

## 새 도메인 개념 (VO, 영속 아님)

- **CfdResult** — 프로젝트 CFD 조회 결과 read-model. `{ projectKey, from, to, points: List<CfdPoint> }`.
- **CfdPoint** — 시계열 한 점. `{ date, todoCount, inProgressCount, doneCount }`. 애그리거트/테이블 없음.
- 순수 집계 로직(이슈 상태 타임라인 → 날짜별 카테고리 카운트)은 테스트 가능한 순수 함수/도메인 계산기로 분리
  (`BurndownCalculator` 선례).

## Brainstorming Check

✅ 통과 (1회 iteration). 자체 적대 검토로 4건 보강 + 1건 plan 위임.
- **G1 (정확성)** 같은 날 다중 status 전이의 tie-break 미정의 → FR2에 `(created_at ASC, id ASC)` + end-of-day 스냅샷
  semantics 명시(index 안정 정렬과 정합).
- **G2 (테스트 결정성)** 기본 창의 '오늘'이 비결정적 → FR5에 `Clock`(UTC) 주입 명시(번다운/벨로시티/export 선례).
- **G3 (오해 방지)** "누적"을 시간 합으로 오구현할 위험 → FR1에 stacked point-in-time 카운트 정의 + 재오픈 시 done 감소 명시.
- **G4 (성능)** field='status' 필터가 status 아닌 이력 다수를 스캔할 위험 → 데이터모델 §에 부분 인덱스 조건부 추가(D3 db 판정).
- **plan 위임**: (a) issue-tracking 프로젝트 BROWSE 체크 진입점(FR-SR-01 이슈 필터 선례 대조) + 프로젝트 미존재 403 vs 404,
  (b) in-memory 델타-누적 알고리즘 최종 형태, (c) 신규 index 실제 필요 여부(쿼리 플랜).
