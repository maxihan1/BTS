## 배경 — 실증된 상태

`comment/{domain,application,repository,web}` 4계층이 모두 존재하지만 **`CommentController` 는
`@GetMapping` 하나뿐**이고 POST·PATCH·DELETE 가 **0건**이다. 프론트 `*comment*` 는 **0건**.

출처가 이유를 말한다 — `029dd82fe [feature] FR-IM-01 PR3 — 댓글/Worklog Import (#224)`.
**댓글 백엔드는 댓글 기능이 아니라 Import 의 부산물**이다. **REST 미노출 = 기능 없음.**

`FR-MN-01`(멘션) · `FR-IS-06`(클론) · `FR-HS-01`(이력)이 *"댓글 FR 도입 시"* 로 명시 이연하며 대기 중이다.

## ★설계를 가르는 사실 2개

### 사실 1 — Worklog 가 같은 문제를 이미 다 풀어놨다

댓글은 새 설계가 필요한 기능이 아니라 **형제 선례를 미러링하는 기능**이다.

| 축 | Worklog (완성) | Comment (현재) | 이 PR |
|---|---|---|---|
| REST 경로 | `/api/v1/issues/{key}/worklogs` | `/api/v1/issues/{key}/comments` | 유지 |
| HTTP 매핑 | POST · GET · PATCH · DELETE | **GET 만** | **POST 추가** |
| POST 응답 | `201` + `DataResponse(data=…)` (`:36`) | — | **동일** |
| 요청 검증 | 컨트롤러에서 `ResponseStatusException(BAD_REQUEST)` (Bean Validation 미사용) | — | **동일** |
| 작성 권한 | `IssuePermission.UPDATE` (`:111`) | `UPDATE` (`:85`) | 유지 |
| 조회 권한 | `VIEW` (`:369`) | `VIEW` (`:142`) | 유지 |
| 권한 scope | `IssueScope.Issue` | `IssueScope.Issue` | 유지 |
| 전용 예외 핸들러 | `WorklogExceptionHandler` | `CommentExceptionHandler` (전체 미러) | 유지 |
| 사람 경로 저작자 | `create()` 가 `authorId = actor.value` **내부 강제** (`:120`) | **호출자 지정** | **강제로 전환** |
| Import 경로 저작자 | `createImported(…, authorId, …)` **별도 메서드** (`:178`) | 같은 `create()` 재사용 | **분리** |
| UI | `components/issue/WorklogSection.tsx` | 없음 | **`CommentSection.tsx` 미러** |

### 사실 2 — `create()` 의 `authorId` 가 저작자 위조 표면이다

현재 시그니처는 `create(actor, issueKey, body, authorId, createdAt)` 로, **저작자를 호출자가 지정**한다.
이대로 POST 를 노출하면 요청자가 `authorId` 를 남의 UUID 로 보내 **남의 이름으로 댓글을 쓸 수 있다.**

이것은 리팩토링 항목이 아니라 **노출 전에 닫아야 하는 보안 요구**다. 파라미터를 열어둔 채 노출하면
안전성이 컨트롤러의 성실성에만 의존하고, 그 의존은 테스트로 고정되지 않는다.

**`create()` 의 현재 호출자는 2곳이며 둘 다 issue-tracking 모듈 내부다** (cross-module 파급 없음).

| 호출자 | 현재 | 전환 후 |
|---|---|---|
| `IssueImportAdapter.kt:729` | `create(actor, key, body, ActorId(authorId), importComment.createdAt)` | **`createImported(…)`** |
| `AutomationIssueMutationAdapter.kt:144` | `create(actor, key, body, authorId = actor)` | **`create(actor, key, body)`** — 이미 `authorId == actor` 라 의미 변화 0 |

## 사용자 시나리오 (Given-When-Then)

### S1. 댓글 작성 (정상 경로)

```
Given 프로젝트 ATLAS 의 이슈 ATLAS-1 이 있고
  And 사용자 A 가 그 이슈에 UPDATE 권한을 가지며
  And 프로젝트가 아카이브 상태가 아닐 때
When A 가 POST /api/v1/issues/ATLAS-1/comments { "body": "확인했습니다." } 를 보내면
Then 201 + { data: { id, authorId: A, body, bodyHtml, createdAt, updatedAt } } 를 받고
  And comments 행이 1건 생기며 authorId = A 이고
  And 같은 트랜잭션에서 IssueCommented 가 발행된다
```

### S2. 저작자 위조 시도 — 구조적으로 불가능해야 한다

```
Given 사용자 A 가 인증돼 있고 사용자 B 의 UUID 를 알 때
When A 가 요청 본문에 authorId / author / userId 등 어떤 형태로든 B 를 넣어 보내면
Then 그 필드는 무시되고 저장된 댓글의 authorId 는 항상 A 다
  And 요청 DTO 에 저작자 필드가 존재하지 않아 애초에 받아들일 창구가 없다
```

### S3. 자기 댓글에 자기가 알림받지 않는다 — 사람 저작에서 처음 의미를 갖는다

```
Given 이슈 ATLAS-1 의 REPORTER 가 사용자 A 이고
  And A 가 그 이슈의 WATCHER 이기도 할 때
When A 가 스스로 댓글을 작성하면
Then A 에게는 인앱 알림이 가지 않는다 (작성자 제외)
  And REPORTER/ASSIGNEE/WATCHER 중 A 가 아닌 사람에게만 간다
```

> **왜 이 시나리오가 새로운가.** 기존 생산자(automation `AddCommentAction`)는 `actor = 룰 actor`
> 였으므로 "작성자 제외" 가 실질 의미를 갖지 않았다. 사람 경로는 `actor = 작성자` 라서
> **이 규칙이 처음으로 실제로 발화**한다.

### S4. 권한 없는 사용자

```
Given 사용자 C 가 이슈 ATLAS-1 에 UPDATE 권한이 없을 때
When C 가 POST /api/v1/issues/ATLAS-1/comments 를 보내면
Then 403 을 받고 comments 행이 생기지 않으며 이벤트도 발행되지 않는다
```

### S5. 기밀 이슈 — 보안등급 우회 차단

```
Given 이슈 ATLAS-9 에 보안등급(FR-PM-06)이 설정돼 사용자 D 가 그 이슈에 접근할 수 없고
  And D 는 프로젝트 ATLAS 에는 UPDATE 권한을 가질 때
When D 가 POST /api/v1/issues/ATLAS-9/comments 또는 GET .../comments 를 보내면
Then 403 을 받는다 (권한 scope 가 IssueScope.Issue 라 프로젝트 권한으로 넘어오지 못한다)
```

### S6. 아카이브된 프로젝트 — 읽기 전용 잠금

```
Given 프로젝트 ATLAS 가 아카이브 상태이고
  And 사용자 A 가 UPDATE 권한을 가질 때
When A 가 댓글을 작성하면
Then 거부된다 (ProjectArchiveGuard, FR-PJ-04 읽기전용 잠금)
  And 목록 조회(GET)는 정상 200 이다
```

### S7. 미존재 / 삭제된 이슈

```
Given 이슈 ATLAS-999 가 없거나 소프트 삭제됐을 때
When 권한 있는 사용자가 댓글을 작성하면
Then 404 를 받는다
  And 미인증 사용자는 404 가 아니라 401 을 받는다 (리소스 존재 probe 차단 — 권한/actor 추출이 조회보다 먼저)
```

### S8. Markdown 렌더 — XSS 차단

```
Given 사용자 A 가 본문에 <script>alert(1)</script> 또는 <img onerror=…> 를 넣을 때
When 댓글을 작성하고 목록을 조회하면
Then body 는 원문을 그대로 보존하고
  And bodyHtml 은 MarkdownRenderer.renderSafe 결과로 스크립트/이벤트 핸들러가 제거돼 있다
```

### S9. 화면 — 이슈 상세에서 댓글 읽고 쓰기

```
Given 사용자가 이슈 상세 화면을 열었을 때
When 활동 영역의 "댓글" 탭을 선택하면
Then 댓글 목록이 작성 시각 오름차순으로 보이고 각 항목에 작성자 이름과 시각이 표시되며
  And 아래 작성 폼에 본문을 입력하고 제출하면 목록이 갱신되고 성공 토스트가 뜬다
  And 권한이 없어 403 이면 작성 폼 대신 권한 안내가 보인다 (빈 폼으로 두지 않는다)
```

### S10. Import 회귀 — 원본 저작자·시각이 계속 보존된다

```
Given Jira CSV/JSON 에 원작성자 X, 작성시각 2020-01-01 인 댓글이 있을 때
When Import 를 실행하면
Then 생성된 댓글의 authorId = X 이고 createdAt = 2020-01-01 이다
  And 이는 createImported 전용 경로로만 가능하며 REST 경로로는 재현할 수 없다
```

### ★ 상한을 서비스에 두는 이유 — Worklog 선례가 여기선 전이되지 않는다

Worklog 는 **컨트롤러**에서 길이·범위를 검증한다. 그게 성립한 이유는 **쓰는 곳이 컨트롤러 하나뿐**이어서
컨트롤러가 전수 감시지점이었기 때문이다.

댓글은 **생산자가 둘**이다.

| 생산자 | 경로 | 컨트롤러 검증에 걸리나 |
|---|---|---|
| 사람 | `CommentController.addComment` | ✅ |
| automation | `ActionExecutor:233` → `IssueMutationPort.addComment` → `AutomationIssueMutationAdapter:144` → `create()` | ❌ **우회** |

그리고 `TemplateRenderer.render` 에는 **길이 제한이 없다**(실측). 즉 컨트롤러에만 걸면 폭증 템플릿을
가진 자동화 룰 하나가 상한을 그냥 지나가고, 목록이 전량 HTML 렌더인 탓에 그 이슈 화면이 죽는다.

**따라서 검증은 `create()` 안에 둔다** — 두 생산자를 한 지점에서 구속한다 (Maxi 확정 D7).

**`createImported` 는 면제한다.** Import 는 관리자가 수동 실행하며 `authorId`·`createdAt` 도 동일하게
면제하는(원본 보존) 계약이다. 잔여 위험으로 등재한다.

### ★ `ko.test.ts` 는 자동으로 덮지 않는다

`ko.test.ts` 는 `import { issueDetailStrings, mfaStrings, …, worklogStrings, epicChildrenStrings } from './ko'`
처럼 **named import 로 검사 대상을 명시 열거**한다. 따라서 `commentStrings` 를 새로 만들어도
**import 목록에 추가하지 않으면 검증이 조용히 비어 있다**(vacuous). FR-21 이 이걸 막는다.

### ★ 열거가 눈가리개다 — 기존 탭 테스트

`IssueActivityTabs.test.tsx:90` 의 테스트 이름이
`(b) 기본 활성 탭은 이력이다 — IssueChangelog만 초기 렌더되고 작업로그/연결은 미마운트` 다.

미마운트를 단정하는 대상이 **"작업로그/연결" 2개로 하드코딩**돼 있다. 댓글 탭을 추가하면 이 테스트는
**여전히 초록인 채로** 댓글 섹션의 초기 마운트 여부를 보지 못한다. 기본 탭을 이력으로 유지하기로
했으니(D8) 댓글도 초기 미마운트여야 하며, **그 단정을 명시 추가**하지 않으면 회귀가 잠복한다.
`guard-handler-matrix-blindfold` · `archunit-vacuous-rule-silent-pass` 가 경고한 형태와 같다.

## API 인터페이스 / 데이터 모델

### 신설 — 댓글 작성

```
POST /api/v1/issues/{key}/comments
```

### 데이터 모델

**마이그레이션 0건.** `V035__comments.sql` 이 이미 필요한 전부를 갖췄다 —
`id`·`issue_id`(FK ON DELETE CASCADE)·`author_id`(FK 미적용, BC 격리)·`body TEXT`·`created_at`·
`updated_at`·`deleted_at` + `(issue_id, created_at) WHERE deleted_at IS NULL` 부분 인덱스.
