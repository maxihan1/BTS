# FR-AT-03 조건 분기 D6/D7 — 조건 빌더 UI + E2E 스펙

> BC. automation | 날짜. 2026-07-13 | slug. fr-at-03-d6-d7-ui | 선행. PR #262(백엔드 D1~D5)
> 범위. **순수 프론트**(백엔드 0 변경). FR-AT-01/02 D6/D7 선례 동형.

## 배경

FR-AT-03 백엔드(D1~D5, PR #262)가 자동화 룰에 **조건 게이트**를 도입했다. 조건은 sealed
`Condition` 트리(And/Or/Not/Comparison)를 JSONLogic 부분집합 JSON으로 저장/직렬화하며, 룰이
발화해도 조건이 거짓이면 액션을 `SKIPPED` 한다. 백엔드 REST 계약(`condition` 필드)은 이미
POST/PATCH/GET에 존재하나, **이를 편집·표시하는 UI가 없다**. 이번 슬라이스는 기존
`AutomationRuleFormDialog`에 **조건 빌더 섹션**을 추가하고(D6) E2E로 검증한다(D7).

## 백엔드 계약 (실측, 소스 grep 확정)

- **와이어 포맷(JSONLogic 부분집합)** — `Condition.kt` 실측.
  - `And` → `{"and": [cond, ...]}` · `Or` → `{"or": [cond, ...]}` · `Not` → `{"not": cond}`
  - `Comparison` 이항(`==` `!=` `>` `>=` `<` `<=` `in`) → `{"<op>": [{"var":"issue.field"}, <리터럴>]}`
    (`in`만 역순 `{"in":[<리터럴>, {"var":field}]}` 허용)
  - `Comparison` 단항 `!`(EMPTY)·`!!`(EXISTS) → `{"!": {"var":field}}` (리터럴 없음)
  - **빈 `And` `{"and":[]}` = 항등원(참)** — `ConditionEvaluator`가 `conditions.all{}` → 빈 리스트 true.
- **필드 화이트리스트 9종** — `issue.key / issue.type / issue.status / issue.priority /
  issue.assignee / issue.reporter / issue.labels / issue.summary / issue.projectKey`.
- **리터럴** — 문자열/숫자/불리언/null 또는 문자열·숫자 배열(≤100). 서수 비교(`>` 등)는 양쪽 숫자일 때만 참.
- **상한** — `MAX_DEPTH=10`, `MAX_NODES=100` (백엔드 저장 시 검증, 위반 시 400 `INVALID_CONDITION_EXPRESSION`).
- **엔드포인트(기존 재사용, 신규 0)** — base `/api/v1/projects/{projectKey}/automation/rules`.
  - `POST` — `CreateAutomationRuleRequest.condition: String?`(null=조건 없음).
  - `PATCH /{id}` — `PatchAutomationRuleRequest.condition: String?`(**null=미변경**).
  - `GET`·`PATCH` 응답 — `AutomationRuleResponse.condition: String?`(JSON 문자열, `rule.condition?.toJson()`).
- **에러** — `INVALID_CONDITION_EXPRESSION`(400) 별도 핸들러 노출(`AutomationRuleController` 실측).

## 결정 (Maxi 확정)

- **[D1] 조건 제거 = empty-AND (프론트 전용)**. PATCH `condition=null`은 "미변경"이라 진짜 null 제거
  경로가 없다. 대신 **빈 조건 트리 ↔ `{"and":[]}`(항등원=참)** 왕복으로 처리한다. 조건을 전부 지우고
  저장하면 `{"and":[]}`(항상 통과)를 전송해 게이트가 실질 제거된다. **백엔드 0 변경**(3-state 래퍼 배제).
  - 저장값은 null이 아닌 `{"and":[]}`가 되나 기능 동일(양쪽 다 항상 통과). DB 직접 관찰자만 인지.
- **[D2] 값 위젯 = 재사용 가능한 것만 드롭다운**. `priority`/`impact`=숫자 select, `assignee`/`reporter`=
  `ProjectMemberSelect`(재사용). `status`/`type`/`labels`/`key`/`summary`/`projectKey`=텍스트 입력.
  status/type 유효값 드롭다운(워크플로우상태·이슈타입 fetch)은 후속 향상. 백엔드가 검증 권위 —
  잘못된 필드=400, 잘못된 값=조건 거짓→SKIPPED(fail-safe)라 오타가 보안/정합성 문제로 이어지지 않음.

## 사용자 시나리오 (Given-When-Then)

- **S1**. Given 관리자가 룰 생성, When 조건을 비운 채 저장, Then 조건 없음(항상 통과) — 기존 동작 보존.
- **S2**. Given 룰 편집 폼, When 조건 빌더에서 `issue.priority > 3` Comparison 추가 후 저장,
  Then PATCH에 `{">":[{"var":"issue.priority"},3]}` 전송, 우선순위 3 이하 이슈엔 액션 SKIPPED.
- **S3**. Given 조건 빌더, When And 그룹 안에 Comparison 2개 + 중첩 Or 그룹 구성, Then 트리 JSON 정상 직렬화.
- **S4**. Given 조건이 있는 룰, When 편집 폼 열기, Then 저장된 조건이 빌더에 로드/표시되어 수정 가능.
- **S5**. Given 조건이 있는 룰, When 조건을 전부 제거하고 저장, Then `{"and":[]}` 전송 → 항상 통과([D1]).
- **S6**. Given 조건 빌더, When 화이트리스트 밖 필드나 형식 위반으로 저장, Then 백엔드 400
  `INVALID_CONDITION_EXPRESSION` → 한국어 에러 메시지 표시(폼 유지).
- **S7**. Given 조건이 있는 룰 편집 중 다른 곳에서 먼저 변경, When 저장, Then 409 → 폼 닫고 refetch(기존
  `handleSubmitFailure` 재사용).

## 기능 요구사항 (FR)

- **FR1. 조건 섹션**. `AutomationRuleFormDialog`에 "조건" 섹션(5번째, 액션과 실행주체 사이 또는 뒤)을
  `ActionListEditor` 위임 패턴 동형으로 추가. `<ConditionBuilder projectKey value onChange />`.
- **FR2. 트리 편집**. And/Or/Not 그룹 노드 + Comparison leaf 추가/삭제/중첩. 그룹은 자식 조건 리스트를
  가지며, 그룹 타입(And↔Or) 전환·Not 토글 가능.
- **FR3. Comparison 편집**. 필드(화이트리스트 9종 select) + 연산자(9종 select) + 값 위젯. 연산자 arity에
  따라 값 위젯 표시 분기 — 이항(값 1개)·`in`(값/배열)·단항 `!`/`!!`(값 없음).
- **FR4. 값 위젯([D2])**. `priority`/`impact`=숫자 select, `assignee`/`reporter`=`ProjectMemberSelect`,
  나머지=텍스트 입력. `priority`/`impact`는 저장 시 숫자 강제(액션 EC9 선례 — 서수 비교가 숫자 요구).
- **FR5. 직렬화/역직렬화**. `automation-rules.types.ts`에 `parseConditionExpression(json: string | null)
  : ConditionNode`(JSON→트리 폼 상태)·`serializeConditionExpression(node): string`(트리→JSON) 신규.
  `parseActionConfig`/`serializeActionConfig` 선례 동형. **왕복 불변식**: null/`{"and":[]}` ↔ 빈 트리.
- **FR6. Zod 계약 확장**. `automationRuleResponseSchema`에 `condition: z.string().nullable()` 추가.
  `CreateAutomationRuleInput`·`PatchAutomationRuleInput`에 `condition?: string` 추가. API 클라이언트
  (`createAutomationRule`/`patchAutomationRule`)는 body에 이미 input 전체를 전달하므로 통과.
- **FR7. 제출 배선(G1 반영)**. `FormBody.onValid`에서 조건 트리를 `serializeConditionExpression`으로
  직렬화해 body에 포함. **null→empty-AND 플립 방지** — 무관한 편집(이름만 변경 등)이 조건을 바꾸지
  않도록 조건은 아래 규칙으로만 전송한다.
  - **create**. 빈 트리 → `condition` 생략(null 유지). 비어있지 않으면 직렬화 JSON 전송.
  - **patch**. (a) 트리 비어있지 않음 → 직렬화 JSON 전송. (b) 트리 비었고 `editingRule.condition`이
    있었음(제거 의도) → `{"and":[]}` 전송([D1]). (c) 트리 비었고 원래도 null → **생략**(미변경, 플립 회피).
- **FR7b. 빈 그룹 prune(G2 반영)**. `serializeConditionExpression`은 자식 없는 그룹을 제거한다 —
  `Or([])`는 항등원이 **거짓**이라 빈 Or 그룹이 남으면 조건 전체가 항상 거짓이 되어 룰이 영영 액션을
  실행 못 하는 footgun이 된다. 직렬화 전 빈 그룹(자식 0)을 트리에서 잘라내고, 결과가 빈 트리면 [D1]
  규칙을 따른다. 빌더 UI도 빈 그룹은 시각적으로 "조건 추가 필요" 힌트를 준다(선택).
- **FR8. 프론트 사전검증(경량)**. 화이트리스트 필드만 선택 가능(select라 구조적 보장), 상한 근처 경고는
  선택. 최종 검증 권위는 백엔드(400). 빈 Comparison(필드 미선택)은 저장 차단 or 무시.
- **FR9. 에러 처리**. `INVALID_CONDITION_EXPRESSION` → `AUTOMATION_ERROR_MESSAGES`에 한국어 매핑 추가.

## 엣지 케이스

- **EC1**. 조건 없는 기존 룰(condition=null) 로드 → 빈 빌더.
- **EC2**. `{"and":[]}` 로드 → 빈 빌더(왕복 불변식, [D1]).
- **EC3**. 응답에 화이트리스트 밖 필드(백엔드 검증상 발생 불가) → 방어적 파싱(값 보존, 텍스트 fallback).
- **EC4**. `in` 역순 `{"in":[리터럴,{"var":field}]}` 로드 → 정규형(`{"var"}` 선두)으로 표시(백엔드 toJson과 동형).
- **EC5**. 단항 `!`/`!!` → 값 위젯 없음(필드+연산자만).
- **EC6**. `priority`/`impact` 값 → 숫자 직렬화(`{"value":3}`, `"3"` 아님, EC9 선례).
- **EC7**. 상한 초과(깊이 10·노드 100) 트리 저장 → 백엔드 400 → 에러 메시지(프론트 사전 차단은 선택).
- **EC8**. 409 OCC → 기존 `handleSubmitFailure`(폼 닫기+refetch+토스트) 재사용, 조건도 fresh 재오픈.
- **EC9**. `open`/`editingRule.id` key 재마운트 시 조건 상태도 초기화(react-usestate-stale-key-prop, 기존 EC6 확장).
- **EC10**. 빈 Comparison(필드/연산자 미완성) 제출 → 저장 차단 or 직렬화 제외(불완전 노드 배제).
- **EC11(G1)**. 조건 null인 룰을 이름만 바꿔 저장 → condition 생략 전송 → null 유지(empty-AND로 안 뒤집힘).
- **EC12(G2)**. 빈 Or 그룹(또는 빈 And 중첩 그룹) → serialize 시 prune → 항상-거짓 footgun 회피.

## 제약 조건

- BC 격리 — automation 프론트만. cross-BC UI 데이터 fetch 없음([D2]로 status/type 텍스트 선택).
- MSW — `automation-rule-fixtures.ts`에 `condition` 추가, `automation-rule-handlers.ts`
  create/patch가 `condition` echo(create `body.condition ?? null`, patch `body.condition !== undefined ?
  body.condition : stored.condition`), 응답 DTO에 `condition` 포함. 전역 등록은 이미 됨
  (`handlers.ts`에 `automationRuleHandlers` 있음 — msw-global-handler-registration-gap 무관).

## 측정 가능한 완료 기준

- 조건 빌더로 And/Or/Not 그룹 + Comparison(9필드×9연산자) 트리 구성/편집/삭제 가능.
- 조건 있는 룰 편집 시 로드→수정→제거([D1]) 전 경로 동작.
- `parseConditionExpression`/`serializeConditionExpression` 왕복 단위 테스트(null·empty-AND·중첩·in역순·단항).
- `ConditionBuilder` 컴포넌트 테스트(그룹 추가/삭제·Comparison 편집·값 위젯 분기).
- Zod `condition` 확장 후 기존 automation 단위/컴포넌트 회귀 0.
- E2E 신규 `automation-conditions.spec.ts` — 조건 추가→저장→목록/재오픈 반영, 조건 편집, 조건 제거(S5).
  기존 E2E 12개(rules 8 + actions 4) 회귀 0.
- `pnpm verify`(lint+typecheck+test+build) green, E2E green.
