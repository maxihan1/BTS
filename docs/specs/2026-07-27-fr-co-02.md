# FR-CO-02 이슈 댓글 수정 + 삭제 (소프트) — 스펙

> 날짜: 2026-07-27
> FR: `FR-CO-02` (기등록, 카운트 **불변 131**)
> BC: issue-tracking 단일
> ADR: [`2026-07-27-fr-co-02-comment-moderation.md`](../decisions/2026-07-27-fr-co-02-comment-moderation.md)
> 선행: [`FR-CO-01`](2026-07-27-fr-co-01.md) (#315) · plan `docs/plans/2026-07-27-fr-co-02.md` · PR #316

## 배경 — 실증된 상태

FR-CO-01 이 댓글을 Import 부산물에서 정식 기능으로 승격하며 **작성 + 목록**까지 열었다.
현재 `CommentController` 는 `GET` + `POST` 2종이고, `CommentRepository` 는 `insert`·`listByIssue`
2개뿐이다. 수정·삭제는 **서비스 메서드 자체가 없다.**

FR-CO-01 §D2 가 *"누가 남의 댓글을 지울 수 있나"* 정책 결정을 이 FR 로 명시 위임했다.

## ★설계를 가르는 사실 3개

### 사실 1 — Worklog 선례가 전이되지 않는다 (생산자 비대칭)

메모리 `sibling-precedent-validation-placement-depends-on-producer-count` 의 판별식을 재적용했다.
**FR-CO-01 D7(본문 상한 위치)에 이어 같은 축이 두 번째로 갈린다.**

| 생산자 | Worklog | Comment |
|---|---|---|
| REST (사람) | `create` | `create` |
| Import | `createImported` | `createImported` |
| **automation** | **0건** (automation 모듈 전수 grep 에 worklog 언급 자체 없음) | **`AddCommentAction` 존재** |

자동화 댓글의 저작자 체인 (전 구간 실측).

```
ActionExecutor.kt:159   ExecutionEnv(rule.actorUserId, …)
ActionExecutor.kt:236   issueMutationPort.addComment(AddCommentCommand(env.actorId, …))
AutomationIssueMutationAdapter.kt:153   commentApplicationService.create(actor, key, body)
CommentApplicationService.kt:99         authorId = actor
```

작성자 한정을 그대로 적용하면 자동화 댓글은 **룰 소유자 한 사람만** 지울 수 있다.
Worklog 에는 이 생산자가 없어 문제 자체가 없었다 — **선례가 조용했던 이유는 답이 같아서가 아니라
질문이 없어서다.**

`WorklogService:254`(update)·`:328`(delete) 의 작성자 한정 자체는 기록대로 정확하며 관리자 우회 분기는 0건.

### 사실 2 — 모더레이션에 새 권한이 필요 없다

```
IssuePermission.SOFT_DELETE
  → IdentityAccessIssuePermissionResolver.kt:178   "DELETE_ISSUE"
  → V008__permission_schemes_and_role_permissions.sql:66   PROJECT_ADMIN 단독
     (:64 주석 — "MEMBER: CREATE_ISSUE + EDIT_ISSUE (2행, DELETE 제외)")
```

FR-CO-01 §D3 이 폭발 반경으로 기각한 "신규 권한 enum" 을 **통째로 피해간다** —
신규 enum 0 · 신규 시드 마이그레이션 0 · 신규 resolver 분기 0.

### 사실 3 — 수정 이력 저장소가 이미 있다 (마이그레이션 0건 유지)

Maxi 가 D3=C(이력 보존)를 택했다. 새 테이블이 필요해 보였으나 **FR-HS-01 의 append-only 감사
이력을 그대로 쓸 수 있다.**

| 확인 항목 | 실측 |
|---|---|
| 저장 구조 | `issue_change_group` + `issue_change_item` (`V018__issue_change_history.sql`) |
| 본문 길이 수용 | `from_value`/`to_value` **`TEXT NULL`** — 32,000자 상한 수용 (`:41-43`) |
| append-only | `deleted_at`·`updated_at` **없음**. 한 번 기록되면 수정·삭제 불가 (DATA.md §3) |
| 부모 삭제 내성 | issues·users 로의 **FK 미적용** — 댓글이 소프트 삭제돼도 이력은 남는다 |
| 조립 기록 진입점 | `IssueHistoryRecorder.recordImported(group)` — detector/resolver 없이 **이미 조립된 그룹**을 기록 (`:119`) |
| 프론트 미지 field 내성 | `resolveFieldLabel:146-147` `label ?? field` — **깨지지 않고 원문 표시** |

## 사용자 시나리오 (Given-When-Then)

### S1. 작성자가 자기 댓글을 수정한다 (정상 경로)

- **Given** `alice` 가 `ATLAS-1` 에 댓글을 남겼고 `UPDATE` 권한을 보유한다
- **When** `PATCH /api/v1/issues/ATLAS-1/comments/{id}` 로 본문을 바꾼다
- **Then** 200 + 갱신된 `CommentResponse`. `updatedAt` 이 갱신되고 `createdAt` 은 불변
- **And** 변경 이력이 1건 기록된다 (사실 3 경로)
- **And** 목록에서 그 댓글에 **"(수정됨)"** 이 표시된다

### S2. 제3자가 남의 댓글을 수정하려 한다 → 403

- **Given** `bob` 이 `UPDATE` 권한은 있으나 그 댓글의 작성자가 아니다
- **Then** **403**. 본문에 거부 사유(권한·scope) 판별자가 실려야 한다 (vacuous 방지)
- **And** 댓글 본문·`updatedAt` 무변경, 이력 기록 **0건**

### S3. ★PROJECT_ADMIN 이 남의 댓글을 수정하려 한다 → **403**

- **Given** `carol` 이 `SOFT_DELETE`(=`DELETE_ISSUE`) 를 보유한 PROJECT_ADMIN 이다
- **When** 남의 댓글에 `PATCH` 를 시도한다
- **Then** **403**

> **이 시나리오가 B안의 핵심 판별자다.** 여기가 200 이면 C안(수정까지 모더레이션)으로 새어나간
> 것이다. 삭제 권한 보유가 수정 권한으로 번지지 않음을 고정한다.

### S4. 작성자가 자기 댓글을 삭제한다 (정상 경로)

- **Then** 204. `deleted_at` 설정(소프트). 목록에서 사라진다
- **And** 그 댓글의 **기존 수정 이력은 남는다** (append-only, 사실 3)

### S5. `SOFT_DELETE` 보유자가 남의 댓글을 삭제한다 → 정상 (모더레이션)

- **Given** `carol` 이 `UPDATE` + `SOFT_DELETE` 를 보유하고 댓글 작성자가 아니다
- **Then** 204. 소프트 삭제 성공

### S6. `UPDATE` 만 있고 `SOFT_DELETE` 없는 제3자가 삭제 시도 → 403

- **Given** `bob` 이 `UPDATE` 보유, `SOFT_DELETE` 미보유, 작성자 아님
- **Then** **403**. 삭제 3클래스(작성자 200 · 모더레이터 200 · 제3자 403)의 세 번째 축

### S7. 자동화가 만든 댓글을 모더레이터가 삭제한다

- **Given** 자동화 룰이 `AddCommentAction` 으로 댓글을 남겼다 (`authorId = rule.actorUserId`)
- **When** 룰 소유자가 **아닌** PROJECT_ADMIN 이 삭제한다
- **Then** 204

> **사실 1 이 든 근거가 실제로 해소되는지를 확인하는 시나리오다.** 근거로 쓴 이상 검증도 해야 한다.

### S8. 삭제된 댓글은 목록에서 사라진다 — 목록 계약 무변경

- **Given** `CommentRepository.listByIssue:64` 가 이미 `DELETED_AT.isNull` 필터를 적용한다
- **Then** 목록 API 의 요청·응답 스키마 변경 **0**. 기존 목록 테스트 **무수정 green**

### S9. 수정하면 이력이 남고 "(수정됨)" 이 보인다

- **When** 댓글을 2회 수정한다
- **Then** 이력 항목이 **2건** 누적된다 (append-only — 덮어쓰기 아님)
- **And** 이슈 상세 "이력" 탭에서 각 수정의 이전/이후 본문을 볼 수 있다
- **And** 댓글 자체에는 `updatedAt != createdAt` 기준으로 "(수정됨)" 이 표시된다

### S10. 삭제된 댓글의 수정 이력은 보존된다

- **Given** 수정 이력이 있는 댓글을 소프트 삭제한다
- **Then** 이력 항목은 **그대로 남는다** (DATA.md §3 감사 로그 삭제 금지)
- **And** 이력 탭에는 계속 보인다 — 이것이 감사 추적의 목적

### S11. Markdown 서식이 화면에 적용된다 + XSS 차단

- **Given** 댓글 본문이 `**굵게**` 와 `<script>alert(1)</script>` 를 포함한다
- **When** 이슈 상세에서 댓글을 본다
- **Then** `**굵게**` 는 **굵게** 렌더된다 (`bodyHtml` 소비)
- **And** `<script>` 는 실행되지 않는다 — 백엔드 `MarkdownRenderer.renderSafe` 가 이미 정화한 값만 사용
- **And** 프론트는 **정화를 재수행하지 않는다** (단일 지점 유지). 대신 정화 회귀 테스트로 고정

### S12. 수정 본문에도 상한·공백 검증이 걸린다

- **When** 32,001자 또는 공백만으로 수정한다
- **Then** 400. `create` 와 **동일한 도메인 예외**(`CommentBodyTooLongException`·`CommentBodyBlankException`)
- **And** 검증은 **서비스**에 둔다 — FR-CO-01 D7 과 같은 이유(컨트롤러에 두면 우회 경로가 생긴다)

### S13. 기밀 이슈 · 아카이브 프로젝트 · 미존재 대상

- 보안등급 보유 이슈에서 권한 없는 actor → **403** (`IssueScope.Issue` 고정 유지)
- 아카이브된 프로젝트 → 기존 `archiveGuard` 로 차단
- 미존재 이슈 / 미존재 commentId / **다른 이슈에 속한 commentId** → **404**
- 이미 삭제된 댓글에 `PATCH`/`DELETE` → **404** (활성 댓글만 대상)

### ★ G1 — `PATCH` 응답의 `bodyHtml` 도 같은 지점에서 나와야 한다

`CommentView.of` 의 KDoc 이 스스로를 *"Markdown 렌더링의 단일 지점"* 이라 선언하며 근거를 적었다 —
*"렌더러를 두 곳에서 직접 부르면 한쪽만 정책이 바뀌어 XSS 방어가 비대칭이 되는 형태의 회귀가
가능해진다."* 그런데 그 KDoc 이 명시한 소비자는 **목록과 작성 2개뿐**이다.

수정이 **세 번째 소비자**로 합류한다. `PATCH` 핸들러가 `MarkdownRenderer.renderSafe` 를 직접
부르면 KDoc 이 경고한 비대칭이 정확히 그 형태로 생긴다. 응답은 반드시 `CommentView.of` 를 경유한다.
→ KDoc 의 소비자 목록도 3개로 갱신한다.

### ★ G2 — 삭제 게이트의 OR 분기는 throwing 헬퍼로 쓸 수 없다

`CommentApplicationService.checkPermission:250-260` 은 **거부 시 던진다.** 삭제의 모더레이터
분기에 이걸 그대로 쓰면(`checkPermission(actor, key, SOFT_DELETE)`) `SOFT_DELETE` 미보유자는
작성자여도 즉시 403 이 되어 **FR-4 의 작성자 경로가 조용히 죽는다.**

OR 분기는 비-throwing 질의형 `permissionResolver.hasPermission(actor.value, SOFT_DELETE, scope)` 로
판정하고, 최종 거부만 한 번 던진다. S4(작성자 삭제 204)가 이 사고의 판별자다.

### ★ 수정 권한이 삭제 권한으로 번지지 않는다 — 판별식

`SOFT_DELETE` 보유자는 삭제만 할 수 있다. 구현에서 두 게이트를 **한 헬퍼로 합치면 안 된다** —
합치는 순간 수정에도 모더레이터가 통과한다. FR-3 과 FR-4 는 **서로 다른 술어**다.

S3 이 이 사고의 유일한 자동 판별자다.

### ★ `Comment` 도메인의 `val` 을 해제하지 않는다 (product 문서 D1 과의 deviation)

`docs/plan/product/issue-tracking.md:388` 의 D1 이 *"`Comment` 본문 변경 허용(전 필드 `val` 해제)"*
라고 적혀 있으나, **이는 착수 전 추정이고 채택하지 않는다.**

`Comment` 는 `data class` 이므로 `copy(body = …, updatedAt = …)` 로 새 인스턴스를 만들 수 있다.
`var` 로 바꿀 이유가 없고, 바꾸면 FR-CO-01 이 세운 불변 도메인 원칙이 깨진다. 소프트 삭제를
도메인에 노출하지 않는 방침(현 KDoc)도 유지한다 — `deletedAt` 필드를 추가하지 않는다.

→ **product 문서 D1 문구를 이 PR 에서 정정한다** (§명세 동기화 대상).

## API 인터페이스 / 데이터 모델

### 신설 — 댓글 수정

```
PATCH /api/v1/issues/{key}/comments/{commentId}
Content-Type: application/json

{ "body": "수정된 본문" }
```

| 응답 | 조건 |
|---|---|
| `200` + `CommentResponse` | 작성자 본인 + `UPDATE` |
| `400` | 공백 본문 / 32,000자 초과 |
| `403` | `UPDATE` 미보유 **또는** 작성자 아님 (**PROJECT_ADMIN 포함**) |
| `404` | 이슈·댓글 미존재, 이슈-댓글 불일치, 이미 삭제됨 |

요청 DTO 에 **저작자 필드 없음** (FR-CO-01 D4 계승). `UpdateCommentRequest(body)`.

### 신설 — 댓글 삭제

```
DELETE /api/v1/issues/{key}/comments/{commentId}
```

| 응답 | 조건 |
|---|---|
| `204` | 작성자 본인 **또는** `SOFT_DELETE` 보유 (둘 다 `UPDATE` 필요) |
| `403` | 위 조건 미충족 |
| `404` | 이슈·댓글 미존재, 이슈-댓글 불일치, 이미 삭제됨 |

### 무변경 — 댓글 목록 / 작성

### ★ 증명 책임의 계층 분리 (Maxi 확정 D6 = A안)

프론트 테스트는 MSW(가짜 서버)를 쓴다. `comment-handlers.ts:129` 가 `bodyHtml` 을
**`` `<p>${body}</p>` `` 로 감싸기만** 한다 — 마크다운을 변환하지도, 정화하지도 않는다.
따라서 프론트에서 *"마크다운이 렌더된다"* 나 *"스크립트가 차단된다"* 를 주장하면
**진짜 변환기를 한 번도 거치지 않은 거짓 초록**이 된다.

메모리 `already-works-is-not-proof-unless-real-server`(9/10) 가 경고한 형태 그대로다 —
#314 에서 ADR 의 결정적 근거가 이 방식으로 거짓이었고 outside voice 가 반증했다.

| 주장 | 증명 위치 | 판정 대상 |
|---|---|---|
| 마크다운이 HTML 로 변환된다 | **백엔드** (T5) | `MarkdownRenderer.renderSafe` 실제 출력 |
| `<script>`·이벤트 핸들러가 제거된다 | **백엔드** (T5) | 같음 |
| 받은 HTML 을 텍스트가 아니라 HTML 로 렌더한다 | **프론트** (T7) | `dangerouslySetInnerHTML` 결선 여부 |
| 사용자가 서식 있는 댓글을 본다 | **브라우저 눈확인** (T9, C12) | 실제 화면 |

**프론트 테스트는 "서버가 준 HTML 을 HTML 로 넣었는가" 까지만 단언한다.** 그 이상을 단언하면
모크를 검증하는 것이다. `comment-handlers.ts` 에 이 한계를 주석으로 못 박는다 (T6).
