# ADR — FR-UX-05 키보드 단축키: 프론트 전용 + 커스텀 훅(의존성 0) + MVP 범위

- 날짜: 2026-07-05
- 상태: 채택 (Accepted)
- 관련 FR: FR-UX-05
- 관련 PR: #237

## 맥락 (Context)

product 문서(`docs/plan/product/personalization.md §4.3`)는 FR-UX-05(키보드 단축키)를
`personalization` 그룹에 분류하고, D 단계를 다음과 같이 명세한다.

- D1. 도메인 — Shortcut
- D2. 명세 — 기본 단축키 매핑 (Gmail/Linear 스타일 참조)
- D3. 데이터 모델 — (코드 상수 + §3.3 커스텀), 신규 테이블 없음
- D4/D5. 백엔드 — 해당 없음
- D6. 프론트 UI — **react-hotkeys-hook** + 도움말 (`?`)
- D7. E2E

SDD 20.9는 표준 단축키 9종을 나열한다: `?`(도움말) · `c`(이슈 생성) · `g i`(내 이슈) ·
`g d`(대시보드) · `/`(검색) · `j / k`(다음/이전) · `e`(편집) · `m`(담당자) · `s`(상태) ·
`cmd+k`(Command Palette, FR-UX-04에서 이미 구현).

코드베이스 조사 결과.

1. **`react-hotkeys-hook`는 미설치.** `apps/web/package.json`에 `cmdk`만 존재. product 문서가
   언급한 이 라이브러리를 쓰면 신규 외부 의존성 도입(`DEVELOPMENT.md §외부 의존성` → Maxi 승인 대상)이다.
2. **FR-UX-04는 라이브러리 없이 커스텀 훅으로 구현.** `useCommandPalette.ts`가 native `document`
   keydown 리스너 + `enabled`(비로그인 미등록) 가드 + `preventDefault` 패턴으로 `Cmd+K` 토글을
   처리한다. "의존성 0 커스텀 훅" 선례가 이미 확립돼 있다.
3. **`react-hotkeys-hook`는 조합키(`ctrl+k`) 위주.** Gmail식 `g i`·`g d` 시퀀스(연타)를 깔끔히
   지원하지 않아 leader-key 상태머신을 별도로 짜야 한다 — 라이브러리를 써도 시퀀스는 결국 자작이 된다.
4. **일부 단축키는 컨텍스트 의존.** `j/k`(리스트 이동) · `e`(편집) · `m`(담당자) · `s`(상태)는
   이슈 상세/보드 컴포넌트의 액션 UI와 깊은 결선이 필요해 cross-cutting scope가 크다.
   반면 `?` · `c` · `/` · `g i` · `g d`는 전역 네비게이션(mutation 0)으로 자기완결적이다.
5. **선례 존재.** FR-UX-04가 프론트 전용 + 네비게이션 전용(액션 명령 0) 철학을 확립했고
   (`docs/decisions/2026-07-04-fr-ux-04-slash-cmd.md`), personalization의 논리≠물리 분리도 동일.

## 결정 (Decision)

### D1. 아키텍처 — 프론트 전용 (백엔드 없음)

키보드 단축키를 **프론트 전용**으로 구현한다. 단축키 정의는 프론트 코드 상수로 두고, 훅이 keydown을
파싱해 기존 라우터로 dispatch하거나 도움말 모달을 연다. product 문서의 D3~D5(데이터 모델/백엔드/
백엔드 테스트)는 이미 "해당 없음"이라 deviation 없음. 커스텀 키맵(FR-PF-03, `user_keymap` 테이블)은
별도 FR로 이 작업 범위 밖.

### D2. 구현 — 커스텀 훅 (신규 의존성 0), react-hotkeys-hook 미도입

FR-UX-04 `useCommandPalette` 선례대로 native `document` keydown 기반 커스텀 훅
(`useKeyboardShortcuts`)을 자작한다. **product 문서 D6의 `react-hotkeys-hook`는 도입하지 않는다.**

근거.
- 신규 의존성 회피 — cmdk 외 프론트 단축키 라이브러리 0을 유지(CLAUDE.md §2 Simplicity First).
- `g i`·`g d` 시퀀스는 leader-key 상태머신이 필요하며, 이는 react-hotkeys-hook로도 자작해야 한다.
  라이브러리를 도입해도 핵심 로직(시퀀스)은 직접 짜야 하므로 의존성 추가의 이득이 적다.
- FR-UX-04 커스텀 훅과 스타일 일관성 유지.

훅 요건.
- native `document` keydown 리스너.
- leader-key 상태머신 — `g` 입력 후 타임아웃(예 1초) 내 `i`/`d`면 시퀀스 성립, 아니면 리셋.
- 입력 포커스 가드 — `input`/`textarea`/`contentEditable`/cmdk 팔레트 오픈 중에는 단일키 무시
  (사용자가 텍스트 입력 중 `c`/`/` 등이 발화하지 않게).
- `enabled`(비로그인 미등록) 가드 — FR-UX-04와 동일.

### D3. MVP 범위 — 전역 네비게이션 5종 + 도움말, 컨텍스트 의존 단축키는 후속

MVP 단축키는 5종. 모두 전역 네비게이션(mutation 0)으로 자기완결적이다.
- `?` — 단축키 도움말 모달 열기.
- `c` — 새 이슈 폼(`/issues/new`)으로 이동.
- `/` — 검색(검색 입력 포커스 또는 이슈 검색 라우트로 이동).
- `g i` — 내 이슈로 이동.
- `g d` — 대시보드로 이동.

`j/k`(리스트 이동) · `e`(편집) · `m`(담당자) · `s`(상태)는 이슈 상세/보드 컴포넌트와 깊은
결선이 필요해 이 PR 범위에서 제외하고 후속 FR로 미룬다(Maxi 결정 2026-07-05).
`cmd+k`는 FR-UX-04에서 이미 구현됨.

### D4. 논리적 FR 소속은 personalization 유지 (논리 ≠ 물리)

`docs/plan/fr-index.md`의 FR-UX-05 BC 매핑(`personalization`)은 변경하지 않는다. 물리 구현은
`apps/web`(프론트 전용)이지만 FR의 논리적 소속은 개인화 영역으로 유지한다.
→ fr-index의 카운트/BC 합계 변경 없음(전수 동기화 카운트 영향 0).

## 결과 (Consequences)

- **product 문서 deviation.** `personalization.md §4.3` D6의 `react-hotkeys-hook`를 "커스텀 훅
  (의존성 0)"으로 조정하고, D6 범위를 전역 네비게이션 5종 + 도움말로 한정(컨텍스트 의존 단축키 후속
  명시). 이 조정은 구현 PR 안에서 전수 동기화한다(CLAUDE.md §명세/범위 변경 시 전수 동기화).
  fr-index BC 매핑·카운트는 불변.
- **frontend + qa 중심.** backend/security/db sub-agent 태스크 0.
- **키맵 충돌 확인.** MVP 단축키(`?` `c` `/` `g i` `g d`)가 기존 전역 단축키(`Cmd+K`만 사용 중)와
  충돌하지 않음. 단일키는 입력 포커스 가드로 텍스트 입력과 분리.
- **접근성/성능 게이트.** 도움말 모달 WCAG 2.1 AA, 단축키 동작률 100%(E2E 전수) — §NFR 측정표.
- **후속 FR.** 컨텍스트 의존 단축키(`j/k/e/m/s`)와 FR-PF-03(커스텀 키맵)이 이 훅 위에 확장된다.
