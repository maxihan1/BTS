# FR-UX-09 F3 — 이슈 생성 진입점의 컨텍스트 반영 범위

> **FR**. FR-UX-09 (이슈 생성 흐름 — 모달 · 진입점) §4.7
> **PR**. #333 · **선행**. #328(B1 백엔드) · #331(F2 모달)
> **BC**. 논리 = agile-planning(보드·백로그·스프린트) / 물리 = `apps/web` 프론트 전용
> **관련 ADR**. [2026-08-01-fr-ux-09-f2-create-issue-dialog](2026-08-01-fr-ux-09-f2-create-issue-dialog.md) ·
> [2026-07-31-fr-ux-09-b1-create-issue-fields](2026-07-31-fr-ux-09-b1-create-issue-fields.md)

## 배경 — 버튼이 약속하는 것과 계약이 줄 수 있는 것이 어긋난다

F2(#331)가 `CreateIssueDialog` 를 **라우터 훅 import 0** 으로 완성해, 진입점이 URL 변경 없이
제자리에서 열 수 있는 설계 조건을 확보했다. F3 은 그 진입점을 보드·백로그·스프린트에 붙인다.

문제는 **칸별 버튼이 칸을 약속한다**는 점이다. 칸마다 「+」를 달면 사용자는
「여기서 누르면 여기에 생긴다」로 읽는다. 그런데 생성 계약이 그것을 받지 못한다.

**실측 (2026-08-03).** `CreateIssueRequest.kt` 가 받는 필드는
`projectKey` · `typeId` · `summary` · `description` · `componentIds` · `securityLevelId` ·
`customFields` · `assigneeId`(3-state) · `priority` · `labels` **뿐이다**.
**`sprintId` 도 상태(`stateKey`)도 없다.** 즉 「스프린트 칸에서 만들면 그 스프린트에」와
「보드 진행 중 칸에서 만들면 진행 중으로」는 지금 계약으로 **1회 제출이 불가능**하다.

곁가지 사실 2건도 실측했다.

- 스프린트 배정은 **기존 API 가 있다** — `POST /api/v1/sprints/{id}/issues`
  (`api/backlog.ts:222 assignToSprint`). 생성 후 1회 더 부르면 반영된다.
- 보드 컬럼은 `stateKey` 를 갖고 있으나(`api/boards.ts:82`), 임의 상태로의 이동은
  워크플로우 전환(`POST /issues/{key}/transition`)를 거쳐야 하고 **초기 상태에서 그 컬럼으로
  가는 전환이 없으면 애초에 불가능**하다. 스킴마다 다르므로 「될 때만 되는」 동작이 된다.

## D-1. 컨텍스트 반영 범위 — 스프린트만 반영한다 (2026-08-03 Maxi 확정)

**결정.** 스프린트 칸의 진입점만 컨텍스트(그 스프린트)를 반영한다.
보드와 백로그는 반영하지 않는다.

**대안 3안을 놓고 Maxi 가 B 를 선택했다.**

| 안 | 내용 | 기각/채택 사유 |
|---|---|---|
| A | 진입점만 붙이고 반영 0 | 칸 6~7개의 「+」가 전부 같은 결과 — **버튼 위치가 사용자를 속인다** |
| **B** | **스프린트만 반영 + 보드는 배치 조정** | **채택.** 기대 불일치가 가장 큰 곳을 기존 API 로 메우고, 못 메우는 곳은 배치로 해소 |
| C | 백엔드에 `sprintId`·초기 상태 추가 | 프론트 전용 PR 이 백엔드 2 BC 로 번져 분량·위험 2~3배. 별도 FR 후보 |

**백로그 칸은 반영이 필요 없다** — 스프린트 미지정이 곧 백로그이므로 기본 동작이 이미 정답이다.

## D-2. 스프린트 반영은 2회 호출이고, 부분 성공을 숨기지 않는다

`POST /issues` → `POST /sprints/{id}/issues` 순서로 2회 호출한다.

**이것은 B1(#328)이 없앤 「반제품 이슈」 문제의 축소판을 되들이는 것이다.** 다만 성질이 다르다 —
B1 이 없앤 것은 **이슈 자체가 반쯤 만들어진 상태**(필드가 빈 채로 남음)였고, 여기서 실패해도
**이슈는 온전하다.** 스프린트 배정만 빠지고, 그 이슈는 백로그에 있으며 드래그로 옮길 수 있다.

**그러므로 조용히 실패하지 않는 것이 조건이다.**

- 1차(생성) 실패 → 기존 F2 에러 표시 그대로. 모달 유지.
- 2차(배정) 실패 → **이슈는 만들어졌음을 먼저 알린다.** 「이슈는 만들어졌지만 스프린트에
  넣지 못했다」는 취지를 이슈 키와 함께 노출한다. 생성 성공을 취소하거나 되돌리지 않는다.
- 성공 판정은 **두 호출이 모두 성공했을 때만** 「스프린트에 추가됨」으로 말한다.

🛑 **2차 실패를 1차 실패처럼 다루면 안 된다** — 사용자가 다시 만들어 **중복 이슈**가 생긴다.

## D-3. 보드 진입점은 컬럼별이 아니라 보드 헤더 1곳으로 옮긴다

컬럼별 「+」는 컬럼을 약속하는데 D-1 이 그 약속을 못 지키게 했다. 지키지 못할 약속은
**하지 않는 쪽**이 정답이다. 보드 화면의 진입점은 **보드 헤더 1곳**으로 둔다.

**대가 — 정본 서술을 이 PR 에서 고쳐야 한다.** `docs/plan/product/personalization.md §4.7` 의
F3 항목이 `BoardColumn.tsx` 배선을 명시하고 있다. **정정 노트만 달지 않고 원문을 고친다** —
FR-UX-08 PR-A 의 `?assignee=me` 정정과 같은 이유로, 원문을 남기면 다음 세션이 틀린 전제 위에 짓는다.

**같은 문단의 선재 drift 1건도 함께 고친다.** 정본 §4.7 F3 의 산문은 진입점을
「보드 컬럼 · 백로그 섹션 · **목록 헤더**」로 적어 놓고 파일 목록은 `BoardColumn.tsx` ·
`BacklogColumn.tsx` · **`SprintColumn.tsx`** 를 적었다 — 산문과 파일 목록이 서로 다르다.
ADR [F2 D-1](2026-08-01-fr-ux-09-f2-create-issue-dialog.md) 이 이미 「진입점 3곳
(`BoardColumn` · `BacklogColumn` · `SprintColumn`)」로 확정했으므로 **산문 쪽이 stale** 이다.

## D-4. 프로젝트는 기존 기본값 경로에 맡긴다 (신규 배선 0)

**실측.** 진입점 3곳은 전부 `/projects/$projectKey/board` · `/projects/$projectKey/backlog`
아래에 있고, `ShellLayout` 의 `useTrackActiveProject`(`hooks/use-track-active-project.ts`)가
그 경로 파라미터를 활성 프로젝트 저장값에 기록한다. `IssueCreateForm` 의
`useDefaultProjectSelection` 은 활성 프로젝트를 기본값으로 넣는다.
**따라서 보드/백로그에서 모달을 열면 프로젝트는 이미 그 페이지 프로젝트로 채워진다.**

**단, 이것은 전역 스토어를 경유하는 간접 결합이다.** 페이지는 `projectKey` 를 직접 알고 있는데
스토어를 한 바퀴 돌아 받는 구조라, 기록 가드(`isKnownProject`)가 아직 통과하지 못한 순간에는
빈 값일 수 있다. **명시 전달(`initialProjectKey` prop 신설)로 바꿀지는 스펙 단계에서 정한다** —
여기서는 「신규 배선 없이도 동작한다」는 사실만 확정하고, 명시화 여부는 열어 둔다.
