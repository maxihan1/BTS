# ADR — FR-PR-03 부재중(Out of Office): OutOfOffice 도메인 + user_ooo 테이블 + 자동 위임 스코프

> 날짜: 2026-07-07
> 상태: 결정됨 (Maxi 확정)
> 관련 FR: FR-PR-03 (부재중 — 기간 + 대체 담당자 + 자동 응답)
> 관련 slug: fr-pr-03-ooo
> 선행 ADR: [2026-07-06-fr-pr-02-user-status.md](2026-07-06-fr-pr-02-user-status.md), [2026-07-05-fr-pr-01-user-profile-placement.md](2026-07-05-fr-pr-01-user-profile-placement.md)

## 맥락

personalization BC(`docs/plan/product/personalization.md §2.3`)의 세 번째 백엔드 FR. 부재중(OOO) — 기간 + 대체 담당자 + 자동 응답. FR-PR-01(프로필)/FR-PR-02(상태)가 확립한 "논리 BC personalization ≠ 물리 모듈 identity-access" + `user_profiles`/`user_statuses` 1:1 미러 테이블 패턴을 계승한다.

이 FR 고유의 미결 결정은 product D4 "**할당 시 자동 위임**"이었다. OOO 데이터는 identity-access에 있으나 이슈 할당(assignee)은 issue-tracking에 있어, "부재중이면 대리자로 자동 전환"을 실제로 배선하면 identity-access + shared-kernel(`UserLookupPort`) + issue-tracking 3개 모듈을 건드려야 한다. 이는 절대 규칙 "한 PR = 한 BC"와 충돌한다.

BTS의 cross-BC 관례 조사 결과: BC 간 데이터는 pgmq 이벤트가 아니라 shared-kernel 읽기 포트(`UserLookupPort` → identity-access `UserLookupAdapter`)로 동기 흐름. issue-tracking `IssueApplicationService.changeAssignee`(assignee 검증)와 `DefaultAssigneeResolver`(자동배정 폴백 체인)가 이미 이 포트를 소비한다.

## 결정

### D1. 모듈 = identity-access (FR-PR-01/02 계승)

FR-PR-01 ADR D1과 동일 근거. `users`/`/api/v1/users/me/*`가 identity-access에 있고 OutOfOffice는 User와 1:1이라 같은 모듈이면 cross-BC 우회 없이 JOIN·whoami view-layer 확장이 가능하다. UserProfile/UserStatus와 나란히 `identity/ooo` 패키지에 둔다. 백엔드는 raw JDBC(`NamedParameterJdbcTemplate`).

### D2. 테이블 = user_ooo 신설 (user_statuses 미러, V029)

```
user_ooo (신규, V029)
  user_id           PK/FK → users.id (ON DELETE CASCADE)
  starts_at         timestamptz NOT NULL   -- 부재 시작(절대)
  ends_at           timestamptz NOT NULL   -- 부재 종료(절대)
  delegate_user_id  uuid NULL → users.id (ON DELETE SET NULL)  -- 대체 담당자, 없어도 OOO 성립
  message           text NULL              -- 자동 응답 안내 메시지(표시용)
  updated_at        timestamptz NOT NULL DEFAULT NOW()
  CHECK (ends_at > starts_at)
```

**근거.**
- FR-PR-02 `user_statuses`와 동일한 1:1 확장 테이블 패턴. `NamedParameterJdbcTemplate` + `INSERT ... ON CONFLICT (user_id) DO UPDATE` UPSERT로 lazy 생성 + 멱등성. OOO는 통째로 교체/해제되는 원자적 값(단일 UPSERT 또는 DELETE).
- `delegate_user_id`는 `ON DELETE SET NULL` — 대리자 계정이 삭제돼도 OOO 자체는 유지(대리자만 소멸). `user_id`는 `ON DELETE CASCADE`(본인 삭제 시 OOO 소멸).
- identity-access가 `users`를 소유하므로 delegate 실재 검증은 자체 SELECT로 가능(cross-BC 불필요).
- init_codegen.sql 미러 불요 — identity-access는 jdbc-only(jOOQ 코드젠 대상 아님, V027/V028 관례).

### D3. 자동 위임 스코프 = 단일 BC, 표시만 (Option A, Maxi 확정)

**이번 PR은 identity-access 안에서 완결한다.** OOO CRUD + 부재중 표시 + 대리자 지정/저장/표시까지. `delegate_user_id`는 저장하고 조회 응답·whoami·프론트에 노출하되, **이슈 할당 시 실제 assignee를 대리자로 자동 전환하는 배선은 하지 않는다.**

**근거.**
- 절대 규칙 "한 PR = 한 BC" 준수. 폭발 반경 최소.
- personalization BC의 실용적 스코핑 선례(FR-UX-04 백엔드 executor deviation, FR-UX-05 react-hotkeys-hook 미도입 — 모두 YAGNI 방향).
- OOO 기능 자체는 완결: 사용자가 부재 기간·대리자·안내 메시지를 설정하고, 팀원이 "부재중, 대리자는 X"를 확인할 수 있다. 실제 자동 재배정은 issue-tracking 소유 로직이므로 그 BC 맥락에서 별도로 다루는 게 깨끗하다.

**기각.**
- Option B(풀 자동 전환): shared-kernel `UserLookupPort`에 대리자 조회 추가 + `IssueApplicationService.changeAssignee`/`DefaultAssigneeResolver` 훅. product D4 완전 충족이나 identity-access+shared-kernel+issue-tracking 3-BC PR → 절대 규칙 예외, 리뷰/테스트 부담 큼.
- Option C(포트만 노출): 소비자 없는 shared-kernel 포트 메서드는 dead code(YAGNI 위배).

**후속.** 실제 assignee 자동 전환은 후속 FR/PR에서 issue-tracking 맥락으로 다룬다(shared-kernel 포트 추가 + changeAssignee 훅). 통합점은 조사에서 확인됨: `IssueApplicationService.changeAssignee` line 790~798, `resolveDefaultAssignee`/`DefaultAssigneeResolver`.

### D4. 자동 응답 = 표시용 안내 메시지 (identity-access 내)

"자동 응답"은 이메일/알림 자동회신(notification BC 연동, 대공사)이 아니라, **부재 사유/안내 텍스트를 저장해 표시하는 메시지**로 해석한다(FR-PR-02 상태 텍스트와 같은 결). `user_ooo.message` 컬럼에 저장하고 OOO 조회 응답·프로필·(선택) whoami에 노출. 실제 멘션/할당 시 자동 회신 발송은 범위 밖. 길이 상한 등 상세는 spec에서 확정.

### D5. 활성 판정 = 조회 시 lazy 필터 (Clock 주입, FR-PR-02 선례)

OOO는 `starts_at <= now < ends_at`일 때만 "활성(부재중)". 조회(GET/whoami) 시 이 조건으로 필터링하며, 미래 예약 OOO(starts_at이 미래)는 저장되지만 아직 활성 아님. 스케줄러/배치 없이 조회 시 자연 판정. `Clock` 주입으로 테스트 결정성 확보(FR-PR-02 `UserStatusService` 선례). 만료 행 물리 삭제는 필수 아님(다음 조회에서 비활성 취급).

### D6. whoami view-layer 확장 (FR-PR-01/02 선례)

D6 product 요구("부재중 표시")를 위해 whoami 응답에 부재중 여부를 노출한다. `WhoamiController`가 이미 `userProfileRepository`/`userStatusRepository`를 협력자로 주입하는 "view-layer 집약점" 패턴을 따라 OOO 조회를 추가. 노출 필드(예: `oooActive`/`oooUntil`/`oooDelegateName`)와 만료 필터 적용은 spec에서 확정. PAT 분기는 항상 null(봇 컨텍스트).

## 영향

- 신규 마이그레이션: `V029__user_ooo.sql` (identity-access) — **머지 직전 V번호 재확인**(동시 브랜치 충돌 회귀 방지, 현재 최고 V028).
- 신규 엔드포인트: `GET/PATCH /api/v1/users/me/ooo`(product의 `POST` 표기는 GET/PATCH 관례로 수렴 — spec에서 확정). clear는 PATCH 빈값/DELETE로 흡수.
- 신규 도메인: `OutOfOffice`, `OutOfOfficeService`, `OutOfOfficeRepository`/`JdbcOutOfOfficeRepository`.
- whoami 응답 +부재중 필드(view-layer).
- 프론트: OOO 설정 폼(설정 페이지 또는 Header 근처) + `apps/web/src/api/ooo.ts` + E2E `ooo.spec.ts`.
- 신규 용어: "부재중 (Out of Office)" — glossary 추가 후보(머지 시 Obsidian sync).
- issue-tracking 무변경(자동 전환 후속).
