🛠 이 프로젝트는 어떻게 만들어지나

BTS는 Maxi 한 사람과 Claude Code(AI 개발 도우미)가 함께 만든다. 사람이 코드를 일일이 지시하는 대신, 하네스라 부르는 정해진 작업 틀을 따른다. 하네스(harness)란 작업자에게 채우는 "안전벨트·작업 틀"로, AI가 제멋대로 가지 않도록 정해둔 작업 순서와 안전장치 묶음이다. 요청을 받아 → 계획하고 → 만들고 → 검수하는 과정을 항상 같은 순서로 진행하고, 중요한 길목 두 곳에서 반드시 당신(사람)의 승인을 받는다.

아래는 그 전체 그림이다. 스크롤하며 순서대로 읽으면 된다.

1. 작업 흐름 — 한마디 요청에서 완성까지

🗣
사용자 한마디 요청
"이슈에 마감일 기능 넣어줘" 같은 평범한 말 한마디로 시작.
▼
📖
선행 읽기 — 지식 노트부터 확인
옵시디언에서 색인(_index) · 최근 작업 이력(history) · 과거 교훈(learnings)을 자동으로 먼저 읽고 시작한다.
▼
📐 1부 · 계획 단계
무엇을, 어떻게 만들지 사람과 AI가 함께 정한다. 아직 코드는 안 짠다.
1
시작/bts-start
요청을 종류별로 자동 분류하고, 본체를 건드리지 않을 별도 작업공간(worktree)과 검토 요청서(초안 PR)를 만든다.
2
도메인 점검/bts-domain
쓸 용어·규칙·과거 결정을 확인한다. 옵시디언의 용어 사전(glossary)과 해당 영역 도메인 노트를 읽어 엉뚱한 방향을 막는다.
3
스펙(명세) 작성/bts-spec
무엇을 만들지 — 사용자 시나리오·요구사항·예외 상황 — 를 글로 또렷하게 정리한다.
4
계획 세우기/bts-plan
스펙을 잘게 쪼갠 작업 목록으로 바꾼다. 각 작업은 "테스트 먼저" 순서.
5
계획 리뷰/bts-review-plan
엔지니어·사업·디자인·개발경험 등 여러 관점에서 계획을 미리 점검한다.
▼
🛑
게이트 1 — 계획 승인
여기서 멈춘다. 당신이 계획을 확인하고 승인해야 비로소 코드를 짜기 시작한다.
▼
🔨 2부 · 구현 단계
승인된 계획대로 실제 코드를 만들고 검수한다.
6
구현/bts-impl
일꾼(에이전트)들이 테스트를 먼저 쓰고(빨강) → 통과시키고(초록) → 다듬는다. 겹치지 않는 작업은 동시에.
7
코드 리뷰/bts-codereview
완성된 코드 전체를 한 번에 모아 규칙 위반·결함이 없는지 검수한다.
▼
🛑
게이트 2 — 머지 승인
다시 멈춘다. 당신이 "합쳐도 좋다"고 승인해야 완료된다.
▼
✅
자동 머지 + 정리 + 지식 기록
본체(main)에 합치고 작업공간을 지운다. 그리고 옵시디언에 작업 이력(history)·새 결정(decisions)·교훈(learnings)을 다시 정리해 둔다 — 다음 작업의 선행 읽기 재료가 된다.

2. 옵시디언 지식 순환 — 정리하고, 다시 읽고 시작한다

매 작업은 빈 종이에서 시작하지 않는다. 옵시디언(Maxi의 메모 보관소)에 쌓인 지식을 먼저 읽고, 끝나면 새로 배운 걸 다시 정리해 둔다.

자동 · 작업 시작 전
📥 1. 먼저 읽는다
  • _index — 전체 노트 색인
  • history — 최근 작업 이력(끝 50줄)
  • learnings — 과거 사고·교훈(회귀 방지)
→
②도메인 단계
📖 2. 더 읽는다
  • glossary — 도메인 용어 사전
  • domain/<영역> — 해당 업무 영역 노트
→
머지 직후
📤 3. 다시 정리한다
  • history에 이번 작업 1줄 추가
  • 새 결정·계획을 decisions로 복사
  • learning: 라벨 시 learnings에 교훈 추가
⟲ 다음 작업은 이렇게 정리된 기록을 다시 "1. 먼저 읽는다"로 흡수한다 — 그래서 순환이다
한 방향으로만 흐른다. 정리는 항상 코드 저장소 → 옵시디언 방향이다. 옵시디언은 Maxi의 사고 공간이라, 거기 적은 메모가 코드 영역으로 자동 반영되지는 않는다.

3. Git과 작업공간(worktree) — 안전하게 고치는 법

코드를 다루는 토대다. 먼저 용어부터 한 줄씩.

🔁 Git
코드의 모든 변경을 시점별로 저장하는 "무한 되돌리기" 장치. 언제든 과거 상태로 돌아갈 수 있다.
💾 커밋 (commit)
변경 한 묶음을 저장하는 게임의 "세이브 포인트". 메시지로 무엇을 바꿨는지 남긴다.
🏛 main (본체)
모두가 공유하는 진짜 최신본. 검증 안 된 변경을 여기에 직접 올리지 않는다.
🧰 worktree (작업공간)
본체를 복사해 따로 펼친 "작업용 책상". 여기서 마음껏 고쳐도 본체는 안전하다.
📨 PR (Pull Request)
"이 변경을 본체에 합쳐도 될까요?" 하고 검토를 요청하는 결재 서류.
🔀 머지 (merge)
검토와 승인을 통과한 변경을 본체(main)에 합치는 것.
왜 이렇게 하나. 본체(main)에는 항상 검증된 코드만 둔다. 실험은 별도 책상(worktree)에서 하고, 합치기 전 반드시 검토(PR)와 당신의 승인(게이트)을 거친다. 잘못돼도 본체는 멀쩡하니 언제든 되돌릴 수 있다.

작업공간 하나의 일생

📋
작업 시작
요청이 들어오면 본체와 분리된 작업공간 .worktrees/<이름> 을 새로 만든다.
💾
첫 커밋 → 초안 PR
첫 변경을 저장하는 순간 "초안 PR(검토 요청서)"이 자동으로 열린다.
🧪
test: → 💻 feat:
테스트 커밋이 기능 커밋보다 반드시 먼저 와야 한다 (컴퓨터가 기록을 검사).
🛑
게이트 통과
코드 리뷰가 끝나고 당신이 머지를 승인하면 다음으로 간다.
🔀
머지 + 정리
본체에 합친 뒤 작업공간을 자동으로 삭제하고 지식 노트를 갱신한다.

지금 무슨 작업이 어느 단계인지 어디서 보나

진행 중체크아웃된 작업공간(worktree) + 열려 있는 PR
리뷰 대기초안이 해제된 열린 PR
완료(머지 후)docs/completed-work-log.md + 지식 노트(history.md)에 자동 기록
커밋 메시지 약속. 변경마다 종류를 앞에 붙인다. feat: 기능 · test: 테스트 · fix: 버그 수정 · chore: 잡무 · docs: 문서. 덕분에 기록만 봐도 무엇을 왜 바꿨는지 알 수 있고, 한 번에 하나의 변경만 담아 언제든 되돌리기 쉽다.

4. 일꾼들 — 6명의 전문 에이전트

구현 단계에서 작업 종류에 맞는 전문 일꾼(AI 서브에이전트)이 투입된다.

🔐 보안 security-engineer
로그인·2단계 인증·SSO·권한 검사처럼 잘못되면 폭발 반경이 큰 영역을 전담한다.
⚙️ 백엔드 backend-engineer
이슈·워크플로우·자동화 등 화면 뒤에서 도는 서버 로직 일반 (Kotlin/Spring).
🎨 프론트엔드 frontend-engineer
눈에 보이는 화면 부분 (React). 디자인 스펙을 실제 동작하는 화면으로 구현한다.
✏️ 디자이너 designer
새 화면의 레이아웃·색·여백을 정하고 목업을 만든다. 코드 구현은 하지 않는다.
🗄 DB db-engineer
데이터를 담는 표(테이블) 구조와 그 변경 이력(마이그레이션)을 관리한다.
🧪 QA qa-engineer
사용자 흐름 전체를 자동으로 눌러보는 E2E 테스트와 테스트 환경을 담당한다.

6. 절대 지키는 핵심 규칙

🧪 테스트 먼저 (TDD)
코드보다 테스트를 먼저 쓴다. 컴퓨터가 git 기록을 보고 "test: 커밋이 feat: 커밋보다 앞에 있는지" 검사해, 어기면 작업을 막는다.
왜. 정답지(테스트)를 먼저 만들고 나서 문제(코드)를 푸는 셈. 만든 게 정말 의도대로 도는지 항상 증명된다.
🧰 작업공간 격리 (worktree)
모든 코드 편집은 별도 작업공간 안에서만 일어난다. 본체(main)는 직접 건드릴 수 없다.
왜. 공용 원본은 금고에 두고 사본으로만 작업하는 것. 실수해도 본체는 멀쩡하니 언제든 되돌릴 수 있다.
🧩 영역 격리 (BC)
한 번의 작업 = 한 업무 영역만. 다른 영역은 직접 부르지 않고 "메시지"로만 알린다.
왜. 부서끼리 남의 책상을 직접 뒤지지 않고 쪽지(이벤트)를 보내는 것. 한 곳을 고쳐도 다른 곳이 안 깨진다.
👁 한 번에 검수 (PR 단위 리뷰)
작업마다 잘게 검수하지 않고, 완성된 변경 전체를 PR 단위로 한 번 모아서 검수한다.
왜. 조각조각 보다 완성본 전체를 보면 앞뒤가 맞는지 한눈에 판단할 수 있다.
